GLM 5.2的出现，确实有点强，而且在coding能力上对标的是Claude Opus级别的模型。它其实有两个明显的优点：

第一， **1M 上下文终于可以达到可用的地步** 。官方文档已经给出 glm-5.2[1m] 的接入方式，并要求把 Claude Code 的自动压缩窗口配置到 1000000，这说明它直接面向大型代码仓、长会话、长链路 Agent 任务设计的。OpenClaw 配置里也写了 1000000 context window 和 131072 maxTokens。

![](https://picx.zhimg.com/v2-48e58190266de89aa82755468ea50ba3_1440w.jpg)

第二， **它直接对标 Claude Opus 级别的复杂工程模型** 。Z.ai 文档直接把 GLM-5.2 和 GLM-5-Turbo 放在“premium / advanced models comparable to Claude Opus”的位置，并建议复杂任务用 GLM-5.2，日常任务继续用 GLM-4.7，避免额度消耗太快。 本质上在目前Agent能力评估上，GLM 5.2甚至在日常的简单任务上能够替代掉Opus模型。

同时在一些三方测试中，GLM 5.2和GPT5.5、Claude Opus 4.8等国外的大模型打得有来有回。

![](https://pic1.zhimg.com/v2-71e09f040d7561202298b2a72adc989a_1440w.jpg)

从公开测试看，GLM-5.2 在 5 个工程项目中拿到 3 个 A 档，说明它对需求理解比较准确，执行过程也较少出错，整体成绩基本持平 Opus 4.8。相比前代 GLM-5.1，GLM-5.2 的进步非常明显，后者此前无法完成这 5 个项目。

在两个非公开高难度隐藏工程中，GLM-5.2 虽然只拿到 C 档，但都完成了项目，而且是首次参与，背题可能性较低。扣分主要来自少数高挑战环节，需要反复修改 2 到 3 次，但整体可用性仍然明显强于大多数国产模型。

更值得注意的是，GLM-5.2 在能力接近 Opus 4.8 的情况下，消耗更低。以 F 项目为例，Opus 4.8 调用了 564 次工具、输出 260K token，而 GLM-5.2 调用了 557 次工具、输出 170K token，说明 GLM-5.2 的工程执行效率更高。不过这个对比也有前提：GLM-5.2 用的是 max 档，Opus 4.8 用的是 high 档，二者并不是完全同档位对比。

## 模型架构

整体的架构可以参考，GLM-5 系列已经公开的技术路线。GLM-5 技术报告显示，它是 **744B 总参数、40B 激活参数的 MoE 模型** ，专家数扩展到 256 个，层数减少到 80 层，用来降低专家并行通信开销。而这一次的GLM-5.2理论上应该是在数据集上做了清洗和筛选。

![](https://picx.zhimg.com/v2-1f7605f41d41f1473d41d795912f2051_1440w.jpg)

**第一，DSA 稀疏注意力。**

GLM-5 集成 DeepSeek Sparse Attention，用动态分配注意力资源的方式降低训练和推理成本，同时尽量保持长上下文理解能力。官方技术报告称，DSA 让模型规模扩展到 744B，同时训练 token 预算提升到 28.5T。

**第二，MLA / Multi-latent Attention。**

报告里提到 GLM-5 使用 Multi-latent Attention，通过压缩 KV 表示来节省显存，并提升长上下文处理效率；同时他们对 Muon optimizer 做了适配，让 MLA 的效果接近 GQA-8。

**第三，长上下文中训练。**

GLM-5 的中训练阶段把上下文逐步扩展到 32K、128K、200K，并增加长文档和合成 Agent 轨迹数据，用来提升长文档、多文件代码仓和复杂 Agent 工作流能力。

**第四，Slime 异步强化学习。**

GLM-5 使用 Slime 异步 RL 基础设施，把生成和训练解耦，提升 GPU 利用率，并支持更大规模的 Agent 轨迹探索。官方也提到异步 Agent RL 主要是为了提升模型在长程交互中的规划、自我修正和复杂任务执行能力。

## 调用费用

目前智谱提供了Coding Plan，能够直接使用 GLM-5.2。GLM-5.2 / GLM-5-Turbo 属于高阶模型， **高峰期按 3 倍额度扣，非高峰期按 2 倍额度扣** ；限时福利是到 9 月底，非高峰期只按 1 倍扣。高峰期是北京时间 14:00–18:00。

![](https://pic2.zhimg.com/v2-2223b42f85cd4b6173ba0f65d88df4dd_1440w.jpg)

官方说明一次 prompt 在 Agent 执行中通常会触发约 15–20 次模型调用，实际消耗会受项目复杂度、代码库大小、是否开启 auto-accept 影响。

## 网友体验反馈

**整体口碑偏正面，尤其是 Coding Agent 场景。**

目前大家最认可的是它在复杂工程任务里的执行感：能长时间推理、工具调用比较准、代码输出更干净。有 Reddit 用户直接评价它“能长推理、思路聪明、工具用得对”，但同时也吐槽希望速度更快。

![](https://pic1.zhimg.com/v2-69f87957b638179db9187d2a0be48978_1440w.jpg)

**前端/产品感反馈不错。**

AICodeKing 在 X 上测 GLM-5.2 的 KingBench 后，评价它“taste 很好”，更擅长 UX 而不是单纯 UI，代码干净，适合 one-shot 完成一些高质量小项目。这个反馈比较关键，因为很多模型会写功能，但交互、布局、细节感比较差；GLM-5.2 似乎在这块有明显提升。
