## 一、三段核心话术速点（完整版在 [`01_方法体系/00_总论`](../01_方法体系/00_总论_LLMforRecommendation.md) §八）

1. **大模型做推荐的方法** → 按成熟度四层：特征增强（落地最多）→ 端到端生成式（OneRec/HSTU/PLUM）→ 对话式 → 用户仿真。先讲框架，再挑一层能讲透的。
2. **怎么用起来+怎么用得起** → 微调路线（TALLRec/LoRA）vs 生成式检索（semanticID）；成本=缓存+蒸馏剪枝量化+离线 Embedding/软标签、在线零 LLM 调用。
3. **在应用商店/游戏中心/海外应用商店能做什么** → 三层：内容深度理解（含 MDA 框架游戏理解）、冷启动缓解（Coupang -45.8%）、跨语言语义对齐；并明说大模型不擅长在线实时排序（P99<50ms）。

## 二、高频 Q&A 速查（完整逐字稿在 §九）

| 追问 | 一句话答案 |
|---|---|
| 延迟太高？ | 定位离线内容理解，不进实时排序；蒸馏/量化后的小模型或缓存 Embedding；极端用 CoVE Token 化 100 倍加速 |
| 物品规模装不下？ | 哈希压缩 Embedding + 分层检索，物品表征与 LLM 词表解耦 |
| 幻觉推荐不存在物品？ | 约束解码 + RAG，生成必须命中物品库 |
| 成本高？ | 小模型做候选、LLM 只做精排；或 LLM 离线产 Embedding/软标签、在线零调用 |
| 比传统推荐增量在哪？ | 把"数据驱动"推向"知识驱动"，补内容理解/跨语言/冷启动/知识推理 |

## 四、一句话开场定位（背这个）

> "大模型在推荐系统的落地优先级是：**先离线/缓存场景（召回向量、冷启内容理解）→ 再逐步渗透在线精排**。核心矛盾是质量提升 vs 延迟成本，工业界最优解是用大模型做内容理解与特征生成，在线侧让轻量模型接力。"
