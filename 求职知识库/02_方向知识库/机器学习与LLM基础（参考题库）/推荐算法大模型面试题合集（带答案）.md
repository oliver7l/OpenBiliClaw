## 一、淘天生成式推荐面试题（15题）

### 1. 简单讲下项目里的推荐框架，业务背景

**答题要点：**
- 整体架构：召回→粗排→精排→重排→混排
- 业务场景：电商推荐（首页猜你喜欢、商品详情页推荐、购物车推荐等）
- 核心指标：CTR、CVR、GMV、人均停留时长
- 技术栈：特征平台、模型训练平台、在线推理服务
- 个人贡献：负责哪个环节、解决了什么问题、带来多少指标提升

### 2. 多目标是怎么选择的，稀疏的问题怎么解决，目标之间跷跷板有做过优化吗

**答题要点：**
- **多目标选择**：根据业务目标选择（CTR、CVR、收藏、加购、停留时长等），用 MMoE/PLE/ESMM 等结构
- **稀疏问题解决**：
  - 正样本少：用负采样、加权、Focal Loss
  - 特征稀疏：用 Embedding、特征交叉、预训练
  - 场景稀疏：用迁移学习、多场景联合建模
- **跷跷板优化**：
  - 目标加权：用帕累托最优、动态权重（如根据业务阶段调整）
  - 梯度平衡：用 Gradient Surgery、PCGrad 防止梯度冲突
  - 结构改进：PLE（Progressive Layered Extraction）比 MMoE 更好地处理目标冲突

### 3. 伪负样本消偏怎么做的，具体原理

**答题要点：**
- **什么是伪负样本**：用户没点击不代表不喜欢，可能是没看到（曝光位置偏差）、没注意到（注意力偏差）
- **消偏方法**：
  1. **IPW（逆倾向加权）**：给每个样本加权 1/P(曝光|特征)，修正曝光偏差
  2. **DR（Doubly Robust）**：结合 IPW 和模型预测，更稳健
  3. **全空间多任务（ESMM）**：用 pCTR × pCVR = pCTCVR，在曝光空间建模 CVR，避免样本选择偏差
  4. **负样本筛选**：用确定性负样本（如曝光后长时间未点击）代替随机负样本
  5. **因果推断**：用 DCN、因果图等方法去除混淆变量影响

### 4. 对于国家行业有做过特别建模吗？最终为什么推特征侧改造？网络上有做过尝试吗？

**答题要点：**
- **国家/行业特别建模**：不同国家/行业用户行为差异大，可以做：
  - 分场景建模（每个国家/行业单独模型）
  - 多场景联合建模（STAR、PLE 等共享+专属结构）
  - 特征侧改造（加入国家/行业 Embedding、场景特征）
- **为什么推特征侧改造**：
  - 维护成本低：一个模型 vs 多个模型
  - 数据共享：小场景可以借助大场景数据
  - 迭代快：特征迭代比模型结构迭代更快
- **网络侧尝试**：
  - 试过 MMoE/PLE 多任务结构
  - 试过场景感知的 Attention（如根据场景动态调整网络权重）
  - 最终发现特征侧改造收益更稳定、维护成本更低

### 5. DIEN这块怎么做的？为什么不直接在DIN上加时序特征，有没有做过消偏？为什么不用transformer

**答题要点：**
- **DIEN 原理**：
  - DIN：用 Attention 机制捕捉用户兴趣与候选物品的相关性
  - DIEN：在 DIN 基础上加了 GRU 序列建模，捕捉用户兴趣的演化过程
  - 核心改进：兴趣抽取层（GRU）+ 兴趣进化层（Attention-based GRU）
- **为什么不直接在 DIN 上加时序特征**：
  - DIN 只能捕捉静态兴趣，无法捕捉兴趣随时间的演化
  - 简单拼接时序特征无法建模序列依赖关系
  - DIEN 的 GRU 能更好地捕捉兴趣演化的动态过程
- **消偏**：
  - 位置偏差：加入位置特征，或用 IPW 加权
  - 曝光偏差：用全空间建模（ESMM 思路）
  - 选择偏差：用因果推断方法
- **为什么不用 Transformer**：
  - 计算成本高：Self-Attention 是 O(n²)，用户行为序列长时开销大
  - 数据量：推荐场景数据量大，但 Transformer 需要更多数据才能充分训练
  - 线上延迟：Transformer 推理慢，不适合高 QPS 在线场景
  - 实际效果：GRU 在序列建模上已经足够，且更轻量

### 6. 生成式推荐了解多少，OneRec的原理知道吗？或者有没有想过用RankMixer做Scaling Up

**答题要点：**
- **生成式推荐**：
  - 传统推荐：判别式（给用户和物品，预测评分/概率）
  - 生成式推荐：生成式（直接生成推荐结果，如用 LLM 生成推荐理由、用生成模型生成物品 Embedding）
  - 代表工作：OneRec、TIGER、生成式检索（Generative Retrieval）
- **OneRec 原理**：
  - 把推荐任务转化为序列到序列（Seq2Seq）生成任务
  - 输入：用户行为序列（物品 ID 序列）
  - 输出：下一个推荐物品的 ID（自回归生成）
  - 用 T5/BART 等 Encoder-Decoder 架构，把物品 ID 当作 token
  - 优势：统一框架（召回+排序+解释）、可扩展性强、能利用 LLM 能力
- **RankMixer / Scaling Up**：
  - RankMixer：用 MLP-Mixer 思想做排序，混合特征维度和样本维度
  - Scaling Up：扩大模型规模（参数、数据、特征），用大模型能力提升推荐效果
  - 思路：可以用 RankMixer 作为轻量排序模型，配合大模型做特征预训练/知识蒸馏

### 7. 召回怎么做的？几路召回，除了线上实验如何验证召回价值？有没有衡量每路贡献度

**答题要点：**
- **几路召回**：
  - 协同过滤（CF）：UserCF、ItemCF、Matrix Factorization
  - 向量召回（Embedding）：双塔模型、GraphSAGE、对比学习
  - 内容召回：基于内容标签、文本相似度
  - 热门召回：全局热门、分类热门、实时热门
  - 社交召回：好友行为、关注达人
  - 场景召回：上下文感知、实时行为
- **验证召回价值（除线上实验）**：
  - 离线指标：召回率（Recall@K）、命中率（Hit Rate）、NDCG
  - 覆盖度：召回物品的多样性、长尾覆盖率
  - 增量分析：AB 实验中看每路召回的增量贡献（去掉某路后指标下降多少）
  - 漏斗分析：召回→粗排→精排→曝光→点击的转化率
- **衡量每路贡献度**：
  - 归因分析：每路召回的物品最终贡献了多少点击/GMV
  - 消融实验：去掉某路召回，看指标下降幅度
  - 边际贡献：在已有其他路的基础上，新增某路带来的增量
  - 路径分析：追踪每个曝光物品来自哪路召回

### 8. Agent这块怎么做的，业务背景是什么

**答题要点：**
- **业务背景**：
  - 传统推荐是被动的（用户刷什么推什么）
  - Agent 推荐是主动的（能理解用户意图、主动规划、调用工具、多轮交互）
  - 场景：智能导购、个性化搜索、复杂任务推荐（如旅游规划、购物清单）
- **Agent 推荐架构**：
  - 感知层：理解用户 query、上下文、历史行为
  - 规划层：用 LLM 做任务规划（Plan-and-Execute / ReAct）
  - 工具层：调用搜索、推荐、知识库、计算等工具
  - 执行层：执行推荐、生成解释、多轮交互
- **关键技术**：
  - LLM 作为推理核心（理解意图、规划、生成解释）
  - RAG（检索增强生成）：注入用户画像、商品知识
  - ReAct / Plan-and-Execute：决策模式
  - 工具调用：Function Calling、Tool Use
  - 记忆机制：短期记忆（对话上下文）+ 长期记忆（用户画像）

### 9. 了解Codex这些Harness的框架吗？和你们实际业务使用的有什么不同

**答题要点：**
- **Codex Harness**：
  - OpenAI Codex 是代码生成模型，Harness 是围绕它的工程框架
  - 核心能力：代码补全、代码生成、代码解释、Bug 修复
  - 工程框架：Prompt 管理、上下文管理、工具调用、安全沙箱、评估体系
- **与业务推荐 Agent 的不同**：
  - **领域不同**：Codex 是代码领域，推荐 Agent 是电商/内容领域
  - **工具不同**：Codex 调用代码执行/文件操作，推荐 Agent 调用搜索/推荐/知识库
  - **评估不同**：Codex 用代码通过率/测试用例，推荐 Agent 用 CTR/CVR/用户满意度
  - **安全不同**：Codex 需要代码沙箱，推荐 Agent 需要内容安全/隐私保护
  - **延迟要求**：推荐 Agent 对延迟更敏感（在线实时），Codex 可以容忍更长延迟

### 10. 为什么Claude Code不用RAG而是用grep这种检索方式呢

**答题要点：**
- **RAG 的问题**：
  - 检索不精确：语义检索可能返回不相关的代码片段
  - 上下文浪费：检索结果可能包含大量无关代码，浪费 Token
  - 代码结构丢失：语义检索破坏了代码的层级结构和调用关系
  - 延迟高：Embedding + 向量检索增加了延迟
- **grep 的优势**：
  - 精确匹配：符号名、函数名、类名精确匹配，召回准确
  - 轻量快速：本地文件系统检索，延迟极低
  - 保留结构：可以结合 AST 分析、文件跳转，保留代码结构
  - 可控性强：开发者可以精确控制检索范围和关键词
- **Claude Code 的实际做法**：
  - 用 grep/ripgrep 做符号检索（函数名、类名、变量名）
  - 用文件系统浏览（ls/cat）做上下文探索
  - 用 LSP（Language Server Protocol）做代码跳转和引用分析
  - 结合 Agent 循环：先 grep 定位，再读取相关文件，再深入分析
- **本质区别**：代码是结构化的、有精确符号的，grep 比语义检索更适合；自然语言是模糊的，才需要 RAG

### 11. 知道推荐里AUC和GAUC的区别吗？为啥推荐里比较倾向于用GAUC

**答题要点：**
- **AUC（Area Under ROC Curve）**：
  - 衡量模型整体排序能力，不区分用户
  - 计算：随机选一个正样本和一个负样本，模型给正样本打分高于负样本的概率
  - 问题：推荐场景中，不同用户的活跃度差异大，活跃用户的样本会主导 AUC
- **GAUC（Group AUC）**：
  - 按用户分组，先算每个用户的 AUC，再按用户加权平均
  - 权重：通常按每个用户的曝光数或点击数加权
  - 优势：消除用户活跃度差异的影响，更能反映模型对每个用户的排序能力
- **为什么推荐倾向用 GAUC**：
  - 推荐是个性化的：每个用户的排序质量才是关键，整体 AUC 可能被活跃用户带偏
  - 业务对齐：GAUC 更贴近用户体验（每个用户看到的排序是否合理）
  - 实验敏感：AB 实验中 GAUC 比 AUC 更容易检测出模型改进
  - 消除偏差：不同用户的正负样本比例差异大，GAUC 分组计算更公平

### 12. 你们会用到PCOC吗？做校准之类的

**答题要点：**
- **什么是 PCOC**：
  - PCOC（Predicted Click Over Click）：预测点击率 / 实际点击率
  - 用来衡量模型预测的校准程度（calibration）
  - PCOC = 1 表示完美校准，>1 表示高估，<1 表示低估
- **为什么需要校准**：
  - 推荐排序：如果 CTR 预测不准，会影响排序（尤其是多目标融合时）
  - 出价/竞价：广告场景中，CTR 预测直接影响出价，必须校准
  - 业务决策：GMV 预估、流量分配都依赖准确的概率预测
- **校准方法**：
  -  Platt Scaling：用逻辑回归对模型输出做校准
  - Isotonic Regression：保序回归，更灵活的校准方法
  - 在线校准：实时监控 PCOC，动态调整校准参数
  - 分场景校准：不同场景（首页、详情页、搜索结果）分别校准
- **实际应用**：
  - 广告场景：必须做校准（影响出价和计费）
  - 推荐场景：排序为主时校准要求低，但多目标融合/混排时需要校准
  - 监控指标：PCOC 是模型上线后的重要监控指标，偏离 1 太多需要告警

### 13. 双塔里为什么要做负采样修正？负采样修正怎么做的

**答题要点：**
- **为什么需要负采样修正**：
  - 双塔模型用对比学习（InfoNCE Loss）训练，需要负样本
  - 全量负样本计算量太大，通常用采样的负样本
  - 但采样会引入偏差：热门物品被采样概率高，模型会偏向热门物品（流行度偏差）
  - 负采样修正就是为了消除这种采样偏差
- **负采样修正方法**：
  1. **LogQ Correction**：在 softmax 中减去 log(Q(i))，其中 Q(i) 是物品 i 被采样的概率
     - 公式：logit(i) = s(u,i) - log(Q(i))
     - 原理：抵消采样概率的影响，让模型学到真实的相似度
  2. **Importance Sampling**：给每个负样本加权 1/Q(i)，修正期望
  3. **Hard Negative Mining**：不做随机采样，而是选择难负样本（与正样本相似但未交互的），减少偏差影响
  4. **Batch Negative + Correction**：用 batch 内其他样本作为负样本，配合修正项
- **实际效果**：
  - 修正后模型对长尾物品更友好，推荐多样性提升
  - 召回的物品更精准，不会过度偏向热门
  - 是双塔召回的标准做法（如 Facebook DPR、Google双塔都用了类似修正）

### 14. 为什么在推荐里经常只训练一轮？CV就会训练很多轮，原因是什么

**答题要点：**
- **推荐只训一轮的原因**：
  1. **数据量大**：推荐场景样本量巨大（亿级/天），一轮已经覆盖了足够多的模式
  2. **实时性要求**：用户兴趣变化快，需要快速更新，多轮训练延迟上线
  3. **特征工程主导**：推荐效果更多依赖特征（用户画像、上下文、交叉特征），模型相对简单
  4. **过拟合风险**：推荐数据噪声大（用户行为有随机性），多轮容易过拟合
  5. **在线学习**：很多推荐系统是流式增量训练，天然就是"一轮一轮"来的
  6. **负采样动态变化**：每次训练负采样不同，一轮已经看到了足够多的正负组合
- **CV 训很多轮的原因**：
  1. **数据量相对小**：ImageNet 才 120 万张，需要多轮才能充分利用
  2. **模型复杂**：ResNet/ViT 参数量大，优化空间崎岖，需要多轮收敛
  3. **层次化特征**：需要从边缘→纹理→部件→物体逐层抽象，每层需要多轮稳定
  4. **数据增强**：每次训练用不同的增强（裁剪、翻转、颜色抖动），多轮等于看到更多数据
  5. **正则化需求**：Dropout、权重衰减等需要多轮才能发挥作用
  6. **学习目标难**：细粒度分类/检测/分割需要反复调整决策边界
- **一句话总结**：推荐是"数据驱动"（样本多、信号强、一轮看遍），CV 是"模型驱动"（参数多、层次深、需要反复打磨）

### 15. RQVAE怎么做的，有和VQVAE做过对比吗？最后手撕了一个动态规划

**答题要点：**
- **VQVAE（Vector Quantized VAE）**：
  - 用离散码本（codebook）对特征做向量量化
  - 编码器输出连续特征，量化为码本中最近的向量
  - 解码器用量化后的向量重建
  - 问题：码本利用率低（很多 code vector 用不到）、量化误差大
- **RQVAE（Residual Quantized VAE）**：
  - 用残差量化（Residual Quantization）代替单次量化
  - 第一层量化后，对残差再做量化，多层残差堆叠
  - 相当于用多个简单码本的组合来表示一个特征
  - 优势：码本利用率高、表示能力强、可以用浅层码本组合出复杂表示
- **对比**：
  - VQVAE：单个码本，简单但利用率低，适合简单任务
  - RQVAE：多层残差码本，表示能力强，适合复杂任务（如生成式检索、语义哈希）
  - 应用：RQVAE 常用于生成式推荐（OneRec）、语义检索（用残差码表示文档 ID）
- **动态规划手撕**：
  - 常见题型：最长递增子序列（LIS）、编辑距离、背包问题、最长公共子序列（LCS）
  - 答题要点：状态定义、状态转移方程、初始化、遍历顺序、空间优化
  - 面试官常追问：去重、剪枝、空间优化、时间复杂度分析

## 二、ReAct 高频面试题（12题，带答案）

### 1. 你如何理解 ReAct？它的核心思想是什么？

ReAct 即 Reasoning + Acting，核心是让模型在推理和与外部环境交互之间循环，而不是只在内部完成推理。模型根据当前状态判断下一步行动，通过工具获得新的 Observation，再利用新信息修正后续决策，直到完成任务。

它解决的核心问题是：仅靠模型参数知识无法获得实时信息、执行外部操作，也难以根据执行结果动态调整策略。

### 2. ReAct 的完整执行流程是怎样的？

典型流程是：
- **Thought**：分析当前状态并决定下一步
- **Action**：选择工具并生成调用参数
- **Observation**：执行工具，将结果返回模型

模型把 Observation 加入上下文后继续下一轮 Thought → Action → Observation，直到判断任务完成并输出 Final Answer。

### 3. ReAct 中 Thought、Action 和 Observation 分别起什么作用？

- **Thought**：表示模型对当前状态的分析以及下一步决策
- **Action**：表示模型对外部环境采取的动作，例如搜索、查询数据库或调用 API
- **Observation**：是 Action 的执行结果，是下一轮决策的新依据

三者形成"推理 → 行动 → 获取反馈 → 再推理"的闭环。

### 4. ReAct 与传统 Chain-of-Thought 的核心区别是什么？

- **CoT**：核心是"只推理"，模型依赖已有上下文和参数知识逐步推导答案
- **ReAct**：是"推理 + 行动"，推理过程中可以调用工具获取外部信息，再根据 Observation 调整后续推理

因此 ReAct 更适合需要实时信息、外部操作或多轮环境交互的任务。

### 5. ReAct Agent 的 Agent Loop 通常是如何实现的？

Agent Loop 本质上是一个状态驱动循环：
调用 LLM → 检查模型输出 → 如果存在 Tool Call，则执行工具 → 把 Tool Result 写回上下文 → 再次调用 LLM。

如果模型给出满足要求的最终输出，则结束循环。

工程上通常还会在 Loop 外增加最大轮数、超时、取消、异常处理和状态持久化等控制。

### 6. ReAct 中模型是如何决定是否调用工具以及调用哪个工具的？

通常会把可用工具的名称、描述和参数 Schema 提供给模型。模型结合用户目标、当前上下文和工具描述，预测下一步应该直接回答还是生成 Tool Call，并选择具体工具及参数。

因此工具描述是否清晰、工具之间语义是否重叠、Schema 是否简单明确，都会直接影响工具选择准确率。

### 7. ReAct Agent 通常在什么条件下结束循环？

最正常的情况是模型判断任务已经完成，不再产生 Tool Call，而是返回最终答案。

生产系统还需要设置强制终止条件，例如最大迭代次数、最大 Token/成本预算、整体超时或用户主动取消。

某些确定性工具也可以配置为调用后直接结束，避免没有必要地再次进入模型循环。

### 8. 如何防止 ReAct Agent 陷入重复调用工具或死循环？

1. 设置 max turns、整体超时和 Token/成本预算，保证循环一定存在硬上限
2. 记录近期 Tool Call，可对"相同工具 + 相同参数 + 相同结果"的重复轨迹进行检测
3. 要求模型在失败后改变策略，并通过状态机、工具调用策略或 Harness 限制非法状态转换

### 9. ReAct 中某次工具调用失败后，Agent 应该如何进行错误恢复？

不要把所有错误都直接重试，应先区分错误类型：
- **可重试错误**（超时、限流、临时网络异常）：可以使用有限次数重试和指数退避
- **参数错误**：通常应把结构化错误信息返回模型，让模型修正参数
- **不可重试错误**（权限不足、资源不存在）：应立即换策略或终止，避免重复调用

### 10. ReAct 在长程、多步骤任务中容易出现哪些问题？

主要问题是状态会不断累积，导致上下文膨胀、成本和延迟增加，并可能出现早期信息被遗忘。

由于每一步主要根据当前上下文做局部决策，还可能出现目标漂移、重复探索、错误逐步传播和无效循环。

因此长程任务通常需要显式规划、阶段状态、上下文压缩、检查点和预算控制，而不是无限扩展 ReAct Loop。

### 11. ReAct 和 Plan-and-Execute 分别更适合什么类型的任务？

- **ReAct**：更适合路径事先不明确、需要频繁读取环境反馈并动态决定下一步的任务，例如搜索、排障和交互式操作
- **Plan-and-Execute**：更适合目标明确、步骤较多且能够提前形成整体计划的长程任务

实际系统也经常混合两者：先生成高层 Plan，再在每个步骤内部使用 ReAct 动态执行。

### 12. 为什么实际生产系统通常不会直接使用最原始的 ReAct，而会在外层增加 Harness 或其他控制机制？

原始 ReAct 主要描述"推理—行动—观察"的决策模式，但生产系统还需要解决可靠性、安全性和可控性问题。

Harness 通常负责管理 Prompt、Tools、Context、Agent Loop，并加入超时、重试、权限、Guardrail、状态持久化、Tracing 和人工介入等机制。

因此 ReAct 更像 Agent 的决策模式，而 Harness 负责把这种决策模式约束成一个可运行、可观测、可恢复的工程系统。

## 三、作业帮大模型一面面试题（11题）

### 1. 常规自我介绍

**答题要点**：教育背景、工作经历、核心项目、技术栈、求职意向，控制在 2-3 分钟

### 2. 针对简历上的全部项目做深度追问，深挖落地细节

**答题要点**：
- 每个项目准备 STAR 法则（情境、任务、行动、结果）
- 深挖：为什么这么做、有什么替代方案、遇到什么困难、怎么解决的、指标提升多少
- 准备好被追问技术细节（模型结构、特征工程、训练方法、线上部署）

### 3. 是否使用过 DeepSpeed？请讲解 ZeRO 不同阶段的实现逻辑，以及整套方案的显存优化底层原理

**答题要点：**
- **DeepSpeed ZeRO**：Zero Redundancy Optimizer，通过切分优化器状态、梯度、参数来减少显存冗余
- **ZeRO-1**：切分优化器状态（Optimizer States），每个 GPU 只存部分优化器状态，显存减少 ~4x
- **ZeRO-2**：切分优化器状态 + 梯度（Gradients），每个 GPU 只存部分梯度，显存减少 ~8x
- **ZeRO-3**：切分优化器状态 + 梯度 + 模型参数（Parameters），每个 GPU 只存部分参数，显存减少 ~Nx（N=GPU数）
- **底层原理**：数据并行中每个 GPU 都存完整的模型参数、梯度、优化器状态，存在大量冗余；ZeRO 通过把这些状态切分到不同 GPU，需要时再 all-gather 聚合，用通信换显存
- **其他优化**：激活检查点（Activation Checkpointing）、混合精度训练、梯度累积、CPU Offload

### 4. 对比 LayerNorm 与 BatchNorm 的差异，解释 Transformer 架构为何选择 LayerNorm 而非 BatchNorm

**答题要点：**
- **BatchNorm**：
  - 在 batch 维度上做归一化（对每个特征通道，在 batch 样本间计算均值和方差）
  - 依赖 batch size，batch 小时统计量不准
  - 对序列数据不友好：不同样本序列长度不同，batch 内 padding 会影响统计
  - 训练和推理行为不一致（训练用 batch 统计，推理用移动平均）
- **LayerNorm**：
  - 在特征维度上做归一化（对每个样本，在所有特征维度上计算均值和方差）
  - 不依赖 batch size，单个样本也能计算
  - 对序列数据友好：每个 token 独立归一化，不受序列长度影响
  - 训练和推理行为一致
- **Transformer 选 LayerNorm 的原因**：
  1. 序列长度可变，BatchNorm 的 batch 统计会被 padding 干扰
  2.  batch size 通常较小（受显存限制），BatchNorm 统计不准
  3. LayerNorm 对每个 token 独立归一化，更适合自注意力机制
  4. 训练/推理一致性好，不需要维护移动平均统计量

### 5. 算法手撕：三数之和（排序+双指针，重点处理去重、剪枝）

**答题要点：**
- 思路：排序后，固定第一个数，用双指针找另外两个数
- 去重：
  - 第一个数去重：if i > 0 and nums[i] == nums[i-1]: continue
  - 左指针去重：while left < right and nums[left] == nums[left+1]: left += 1
  - 右指针去重：while left < right and nums[right] == nums[right-1]: right -= 1
- 剪枝：
  - if nums[i] > 0: break（排序后第一个数大于0，后面不可能凑出0）
  - if nums[i] + nums[i+1] + nums[i+2] > 0: break（最小的三个数都大于0）
  - if nums[i] + nums[-1] + nums[-2] < 0: continue（最大的两个数都不够）
- 时间复杂度：O(n²)，空间复杂度：O(1)（不计排序空间）

### 6. 大模型主流微调方案有哪些？分别说明全参数微调、LoRA、QLoRA 三者对应的落地场景

**答题要点：**
- **全参数微调（Full Fine-Tuning）**：
  - 更新模型所有参数
  - 场景：数据量大、任务差异大、有足够算力、需要最大化效果
  - 优点：效果最好；缺点：算力需求大、存储成本高（每个任务一份完整模型）
- **LoRA（Low-Rank Adaptation）**：
  - 冻结原模型，只训练低秩矩阵（A×B），注入到 Attention 层
  - 场景：数据量中等、算力有限、需要快速迭代、多任务部署
  - 优点：训练参数少（~1%）、推理时可合并回原模型、多任务只需存多个小 LoRA
  - 缺点：效果略低于全参数微调
- **QLoRA（Quantized LoRA）**：
  - 在 LoRA 基础上，把原模型量化为 4bit（NF4），用分页优化器管理显存
  - 场景：算力极度受限（单卡消费级 GPU）、大模型（65B+）微调
  - 优点：显存需求极低（65B 模型只需 48GB 显存）；缺点：训练速度慢、效果可能略降
- **选择建议**：
  - 追求极致效果 + 算力充足 → 全参数微调
  - 平衡效果和效率 + 多任务 → LoRA
  - 大模型 + 消费级 GPU → QLoRA

### 7. 讲清楚 PPO 算法里的 clip 裁剪机制；区分在线强化学习与离线强化学习的核心差异

**答题要点：**
- **PPO 的 clip 机制**：
  - PPO 是策略梯度算法，目标是最大化优势函数，但要限制策略更新幅度
  - Clip 目标：L(θ) = E[min(r(θ)·A, clip(r(θ), 1-ε, 1+ε)·A)]
  - 其中 r(θ) = π_θ(a|s) / π_old(a|s) 是重要性采样比率
  - 当 A > 0（动作好）：r 被限制在 1+ε 以内，防止过度更新
  - 当 A < 0（动作差）：r 被限制在 1-ε 以上，防止过度更新
  - 本质：用 clip 限制策略更新步长，保证训练稳定
- **在线 vs 离线强化学习**：
  - **在线 RL**：智能体与环境实时交互，边收集数据边更新策略（如 PPO、DQN）
    - 优点：数据分布与策略一致，训练稳定；缺点：需要环境交互，成本高
  - **离线 RL**：用预先收集的固定数据集训练，不与环境交互（如 CQL、BCQ、IQL）
    - 优点：不需要环境交互，可利用历史数据；缺点：存在分布偏移（OOD）问题，容易高估 Q 值
  - **核心差异**：在线 RL 的数据分布随策略更新而变化，离线 RL 的数据分布固定，需要处理分布偏移
  - **RLHF 中的应用**：PPO 是在线 RL（用当前策略生成 response，再用 RM 打分），但也有离线变体（如 DPO、IPO 直接用偏好数据训练，不需要在线采样）

### 8. 在 RLHF 流程中 KL 散度的出现位置与实际作用？KL 散度数值偏大、偏小分别会带来哪些问题

**答题要点：**
- **KL 散度在 RLHF 中的位置**：
  - RLHF 流程：SFT（监督微调）→ RM（奖励模型）→ RL（PPO 强化学习）
  - 在 PPO 训练时，奖励函数 = RM 打分 - β·KL(π_θ || π_SFT)
  - KL 散度衡量当前策略 π_θ 与 SFT 模型 π_SFT 的差异
- **KL 的实际作用**：
  - 防止策略偏离 SFT 模型太远，保持语言模型的基本能力（流畅性、知识性）
  - 防止策略为了追求高奖励而生成"投机取巧"的输出（如重复、冗长、模式崩溃）
  - 作为正则化项，保证训练稳定
- **KL 偏大的问题**：
  - 策略偏离 SFT 太远，可能丢失基本语言能力
  - 输出质量下降（不流畅、不相关、幻觉增加）
  - 可能是 β 太小，需要增大 β
- **KL 偏小的问题**：
  - 策略没有充分优化，过于保守，没有学到偏好对齐
  - 奖励提升不明显，对齐效果差
  - 可能是 β 太大，需要减小 β
- **β 的选择**：通常用自适应 KL（根据 KL 大小动态调整 β），目标是让 KL 保持在合理范围（如 6-10 nats）

### 9. 简述 RAG 完整工作链路，梳理现存的痛点短板，说说可以如何改善检索结果不准确的问题

**答题要点：**
- **RAG 完整链路**：
  1. **索引阶段**：文档切分 → 向量化（Embedding）→ 存入向量数据库
  2. **检索阶段**：用户 Query → 向量化 → 向量检索（Top-K）→ 召回相关文档
  3. **生成阶段**：Query + 召回文档 → Prompt → LLM 生成答案
- **痛点短板**：
  - 检索不准：召回的文档不相关或遗漏关键文档
  - 切分不合理：chunk 太大/太小，语义不完整
  - Embedding 质量差：语义表示不准确
  - 上下文窗口限制：召回太多文档塞不下
  - 幻觉：LLM 忽略检索内容，自己编造
  - 延迟：检索 + 生成延迟高
- **改善检索不准确的方法**：
  1. **Query 改写**：用 LLM 改写用户 Query（扩展、拆解、纠错），提升检索召回
  2. **混合检索**：向量检索 + 关键词检索（BM25）+ 知识图谱检索，互补
  3. **重排序（Rerank）**：先用向量检索召回 Top-50，再用 Cross-Encoder 精排 Top-5
  4. **分层索引**：粗粒度（文档级）+ 细粒度（段落级），先粗筛再精筛
  5. **自适应切分**：按语义边界切分（标题、段落），而不是固定长度
  6. **多跳检索**：复杂问题拆解为多步，逐步检索
  7. **反馈学习**：用用户点击/反馈数据微调 Embedding 模型
  8. **元数据过滤**：结合时间、来源、类型等元数据过滤，提升精准度

### 10. 对比 DPO 和 SFT，分析二者各自的优势与不足；说明 DPO 偏好数据对的构建方式

**答题要点：**
- **SFT（Supervised Fine-Tuning）**：
  - 用高质量问答对训练，学习"标准答案"
  - 优点：简单稳定、数据要求低（只需标准答案）、效果有保障
  - 缺点：只能模仿，不能超越标注者水平；容易模式崩溃（输出单一）；无法处理开放式问题的多答案
- **DPO（Direct Preference Optimization）**：
  - 直接用偏好对（chosen > rejected）训练，不需要显式奖励模型和 PPO
  - 优点：训练简单（比 PPO 稳定）、不需要在线采样、对齐效果好、能处理偏好
  - 缺点：需要偏好对数据（构建成本高）、对数据质量敏感、可能过拟合偏好
- **对比**：
  - SFT 是"学习正确答案"，DPO 是"学习偏好排序"
  - SFT 适合有明确标准答案的任务，DPO 适合开放式、主观偏好任务
  - 实际流程通常是：先 SFT 打底，再 DPO/RLHF 对齐偏好
- **DPO 偏好数据对构建方式**：
  1. **人工标注**：对同一个 Prompt，让模型生成多个 response，人工选择更好的（chosen）和更差的（rejected）
  2. **基于规则**：用自动指标（如事实准确性、长度、格式）筛选 chosen/rejected
  3. **基于奖励模型**：先用 RM 打分，高分作为 chosen，低分作为 rejected
  4. **在线反馈**：用用户点击/点赞/停留时长作为偏好信号
  5. **Self-Play**：用强模型生成 chosen，弱模型生成 rejected
  - 注意：偏好对需要保证两个 response 有明显差异，且 chosen 确实优于 rejected；数据质量直接影响 DPO 效果

### 11. 大模型主流的位置编码方案有哪些？讲解 RoPE 的工作原理，以及它的优缺点

**答题要点：**
- **主流位置编码方案**：
  1. **绝对位置编码**：
     - 正弦位置编码（Sinusoidal，原 Transformer）：PE(pos, 2i) = sin(pos/10000^(2i/d))
     - 可学习位置编码（Learned，BERT/GPT-2）：直接学习位置 Embedding
  2. **相对位置编码**：
     - T5 的相对位置偏置（Relative Position Bias）
     - Transformer-XL 的相对位置编码
  3. **旋转位置编码（RoPE，Rotary Position Embedding）**：LLaMA、GPT-NeoX、PaLM 等用
  4. **ALiBi（Attention with Linear Biases）**：直接在 attention score 上加线性偏置
  5. **NoPE（No Position Encoding）**：不加位置编码，靠数据自然学习
- **RoPE 工作原理**：
  - 核心思想：用旋转矩阵对 Query 和 Key 的向量做旋转，旋转角度与位置相关
  - 对每个位置 pos，把 Embedding 维度两两分组，每组用旋转矩阵 R(pos·θ_i) 旋转
  - 旋转后，两个向量的内积（attention score）只与它们的相对位置差有关
  - 公式：q̃_m = f(q, m) = R_m Θ q，k̃_n = R_n Θ k，内积 <q̃_m, k̃_n> = <q, R_{n-m} k>
  - 这样 attention score 天然包含了相对位置信息
- **RoPE 的优点**：
  1. 相对位置编码：attention score 只依赖相对位置差，符合直觉
  2. 外推性好：理论上可以处理训练时没见过的长序列（长度外推）
  3. 计算高效：只需对 Q/K 做旋转，不增加额外参数
  4. 稳定：训练稳定，已被 LLaMA 等主流模型验证
- **RoPE 的缺点**：
  1. 实际长序列外推仍有问题：虽然理论上支持相对位置，但实际长序列时 attention 分布会异常（需要 NTK 缩放、YaRN 等方法修复）
  2. 旋转角度的选择（base 值）需要调参
  3. 对局部位置信息的建模不如绝对位置编码直接

1. **训练工程**：DeepSpeed/ZeRO、分布式训练、混合精度、梯度累积、激活检查点
2. **微调方法**：全参数、LoRA、QLoRA、Adapter、Prefix Tuning
3. **对齐方法**：RLHF（PPO）、DPO、RLAIF、Constitutional AI
4. **推理优化**：量化（GPTQ、AWQ）、KV Cache、PagedAttention、连续批处理
5. **RAG/Agent**：检索增强、工具调用、ReAct、Plan-and-Execute、Harness

### 面试技巧
