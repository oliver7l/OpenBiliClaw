## 关键方法 · 模型 · 指标
- 现有流程的架构请参见 km 文档，不做赘述
- 业务独立性：一个图谱只针对某一个领域进行构建
- 知识图谱分为百科知识图谱（全领域）和领域知识图谱
- 二期对不同图谱的规则进行抽取，从通用图谱中剥离出
- 当前构建流程中的图谱为百科知识图谱，有以下局限性：
- Type与数据源绑定，继而与图谱绑定，所以直接复用
- 建立独立的数据接入体系，将不同的图谱接入数据分区存储
- 基于以上，提出构建特定领域知识图谱的通用解决方案，满足：
- Schema （包括层级关系、属性等）数据在不同业务图谱中一致
- 所以完整领域图谱分为两期，一期尽可能的复用现有图谱规则，便于维护
- 一个领域图谱包含多个数据源，同时，一个数据源也可能出现在多个图谱中
- 而面向特定领域的图谱，数据相对较小且单一，流程也较为简单，构建时间较短
- 融合规则因与 Type 或 Schema 绑定也在不同的业务图谱中一致
- 在存储方式上，为了保持各个图谱相互独立，构建出的图谱按照图谱名称分区存储
- 领域图谱复用现有图谱的流程，保留这三种接入方式，只要求图谱的数据源独立于通用图谱
- 由于本方案设定为基于现有百科图谱的改进，所以有必要对目前已有的图谱构建流程进行分析
- 由于Schema可通过Type得出，而Type与数据源绑定，继而与图谱绑定，所以直接复用
- 将现有百科图谱构架流程改造为领域图谱，重点是分领域构建，随之而来的问题是各个领域不同规则如何划分
- 基于 4 中假设，可将数据源（ Source_ID + Data_type ）与图谱 ID 绑定
- Type 数据（包括层级关系、冲突关系等）在不同业务图谱中一致，如：体育相关的 Type 信息在“腾讯体育图谱”和“新浪体育图谱”中一致
- 本着“代码和流程复用”的原则（减少后续维护成本） ，在现有流程的基础上新增图谱 ID ，来实现分领域的目的，每个图谱 ID 对应着一个领域图谱
- 当前图谱构建流程输出为百科知识图谱，包含了人物、影视、体育等领域，因各个领域的数据特点不同，考虑的因素较多，其数据量大，构建流程复杂，构建时间长
- 由于现实中可能会出现极少数特殊的情况，如：同一份数据在不同图谱中应用不同的规则、不同图谱中概念体系不同等，所以有必要对这种特例进行规避，做出如下假设：
- 同一个数据源（ source_id + data_type 相同），即使在不同的业务图谱中其规则也一致，即规则与 source_id 和 data_type 绑定
- 为了保持各个图谱间的独立性，采用”物理“隔离的方式，将不同的领域图谱分区存储，每处理一个环节就分区保存一次，下一个环节读取上一个环节中各分区数据分别处理，如下图所示：
- 所以，可以将原来规则与图谱的关系转化为数据源与图谱的关系，即原来需要将大量的规则绑定在某一个图谱上的工作，只需将数据源绑定在该图谱上，简化问题复杂性，且可以复用现有的规则
- 本方案立足于4中的假设制定，但正如上文所说，存在某些少数情况——不同领域图谱的Schema不同，这是需要对数据源和Type、Schema进行解绑，针对不同的领域，分别制定不同的规则
- 一方面，概念和 Schema 相对比较稳定，多数情况下不同的垂类图谱可以复用一套概念或者 Schema 体系，如腾讯体育图谱和新浪体育图谱的体育相关概念层级基本相同，每个概念下的属性（ schema ）也类似
- 当前百科图谱构建流程中主要的配置规则包括属性映射规则、属性值清洗规则、融合规则，以及其他自定义的规则，经分析，前三者的规则与数据源、概念、 Schema 绑定，其他自定义规则（如指定 RID 或 EID 的类别）与 RID 或 EID 绑定，如下图所示：
