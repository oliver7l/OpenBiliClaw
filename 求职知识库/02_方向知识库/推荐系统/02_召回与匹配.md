# 推荐系统召回与匹配方法论

## 一、召回全景与多路召回架构

### 1.1 召回在推荐系统中的位置

我在腾讯微视做账号推荐召回时，整个推荐链路分为**召回→粗排→精排→重排**四个阶段。召回是整个系统的第一道漏斗，负责从百万甚至亿级的item库中，快速筛选出几百到几千个候选集，交给后续排序模型精排。

召回的核心矛盾是**"全"与"准"的权衡**：
- **全（召回率/覆盖率）**：不能漏掉用户可能感兴趣的item，否则后续排序再强也无济于事
- **准（相关性/精度）**：候选集质量不能太差，否则会浪费精排的计算资源，也会影响最终效果
- **快（延迟）**：召回必须在毫秒级完成，通常要求单次召回延迟在10ms以内

在微视账号推荐场景中，召回的item是**作者账号（达人/好友）**，而非视频内容。用户的核心行为是**关注**，因此召回的目标是找到用户可能关注的账号。

### 1.2 多路召回策略

我在微视负责的账号推荐系统采用了**多路召回架构**，每一路召回从不同维度挖掘候选账号，最后合并去重交给排序层。具体包括：

**关系链召回（好友方向）：**
- **一度好友召回**：基于QQ好友、微信好友、红包关系、通讯录关系merge，按共同好友数倒排，通路召回300-500个（来源：好友及达人推荐梳理）
- **二度好友召回**：离线计算，7天计算一次，每次10-20小时，按共同好友数倒排，通路召回200个，二度好友用户覆盖约5000万（来源：好友及达人推荐梳理）
- **一度/二度好友实时召回**：依赖功能后台实时关系链获取接口，在线计算二度好友候选集

**达人召回（内容方向）：**
- **热门达人召回**：人工筛选200个达人作为兜底，热度得分=总粉丝数×0.2 + 7天热度等级×0.5 + 30天热度等级×0.3（来源：好友达人梳理（总））
- **分人群热度召回**：基于用户性别、年龄、地域分组，计算每组对各一级分类的满意度，按cat2daren召回
- **个性化达人CF召回**：基于用户最近10个关注达人，拉取协同过滤结果
- **达人Embedding召回**：用Word2vec训练作者32维emb，基于用户关注达人召回相似达人，限制一级类目可提升准确性但降低覆盖率（来源：好友达人梳理（总））
- **用户互动行为和播放行为召回**：使用用户近一星期在推荐流的互动（赞转评）或多次完播行为，互动得分=赞转评×2+完播×1（来源：好友达人梳理（总））
- **外部画像召回**：基于外部画像一级类目召回热门达人
- **好友关注的人也关注的达人召回**：社交关系链+内容兴趣的交叉召回
- **实时关注召回**：捕捉用户实时关注行为，快速反馈到召回

**垂类/策略召回：**
- **影评人召回**：针对电影/影评垂类的专项召回
- **一二级兴趣召回**：基于用户兴趣标签的分层召回
- **item2vec召回**：基于用户行为序列的item embedding召回
- **DSSM双塔召回**：深度语义匹配召回
- **TDM深度树匹配召回**：树结构的深度匹配召回
- **图Embedding召回**：基于社交图/行为图的embedding召回
- **强化学习召回**：基于策略梯度的TopK集合召回

### 1.3 召回评估指标

召回的评估分为**离线评估**和**线上评估**两个层面：

**离线指标：**
- **召回率（Recall）**：用户实际交互的item中，有多少被召回命中。这是召回最核心的离线指标
- **覆盖率（Coverage）**：召回结果覆盖的item占全库的比例，衡量推荐的多样性
- **命中率（Hit Rate）**：有多少用户的召回结果中包含了其后续交互的item
- **NDCG@K**：召回结果的排序质量
- **正逆率**：在SIMNET语义模型中，正逆率=正样本得分高于负样本的比例，version-1达到1.57，version-2（w2v初始化词表）达到1.60（来源：百亿量级SIMNET模型规划）

**线上指标：**
- **pCTR（人均点击率）**：召回候选集经过排序后，用户的点击概率
- **uCTR（用户点击率）**：有点击行为的用户占比
- **关注率**：账号推荐场景的核心指标，用户关注账号的比例
- **VV（播放量）占比**：各召回源贡献的播放量占比
- **人均下载个数**：在应用宝必备弹窗场景中，TopK集合召回上线后整体分发系数提升20%（来源：基于策略梯度的TopK集合召回推荐算法）

在微视账号推荐的graph embedding实验中，我们重点观察pCTR和uCTR：发现好友页实验组pCTR相对提升11.19%、uCTR相对提升6.29%（10%流量，2天数据）；扩大到20%流量3天数据后，发现好友页pCTR相对提升2.58%、uCTR相对提升7.66%（来源：各种emb实验）。

> **面试口述版：**
> "我在腾讯微视负责账号推荐的召回系统，整个架构是多路召回+统一排序。召回侧我同时维护了关系链召回（一度/二度好友，覆盖约5000万用户）、达人召回（热门/CF/Embedding/行为召回等七八路）、以及垂类策略召回（影评人、兴趣召回等）。每一路召回负责从不同维度挖掘候选账号，最后合并去重后交给LR排序模型。我个人的核心工作是把Embedding召回从0到1做上线，包括用Word2vec训练作者32维emb、基于用户关注达人做相似召回，以及后来的graph embedding和DSSM双塔召回的探索。"

## 二、DSSM双塔召回

### 2.1 DSSM原理

DSSM（Deep Structured Semantic Model）的核心思想是**将user和item分别映射到同一个低维语义空间，通过余弦相似度计算匹配程度**。

我在微视做账号推荐时，DSSM双塔模型的结构如下：

```
User Tower:                          Item Tower:
用户特征 → Embedding层 → MLP → user_emb    账号特征 → Embedding层 → MLP → item_emb
                                                      ↓
                                              cos(user_emb, item_emb)
                                                      ↓
                                              匹配得分
```

**损失函数**采用pair-wise的margin loss：

```
L = max(0, margin - cos(user_emb, pos_item_emb) + cos(user_emb, neg_item_emb))
```

即正样本的余弦相似度要比负样本高出至少一个margin。

在SIMNET百亿量级模型规划中，我们也采用了类似的pair-wise CDSSM结构：basic侧用windows=[3,4,5]、kernel_size=64的CNN网络，phrase侧用BOW网络（后改为CNN），loss为margin loss，basic和phrase分别计算margin loss后相加：loss = loss_phrase + loss_basic（来源：百亿量级SIMNET模型规划）。

### 2.2 负采样策略

负采样是DSSM训练中最关键的环节之一，直接影响模型效果。我在实践中总结了几种负采样方式：

1. **随机负采样**：从全量item库中随机抽取负样本。优点是简单，缺点是负样本太容易区分，模型学不到精细的边界
2. **曝光未点击负采样**：将曝光给用户但用户未点击的item作为负样本。这种负样本更接近真实分布，是工业界最常用的方式
3. **Hard Negative（难负样本）**：选择与正样本相似但用户未交互的item作为负样本。可以通过以下方式获取：
   - 从同一类目下随机采样
   - 从当前模型的topK结果中采样（即模型认为相似但实际未交互的）
   - 基于item embedding的近邻采样

在微视账号推荐场景中，我们主要采用**曝光未点击+随机采样**的混合负采样策略，正负样本比约为1:10（来源：好友达人梳理（总）中排序样本的定义，召回训练类似）。

### 2.3 训练方式

DSSM的训练分为**离线训练**和**在线服务**两个阶段：

**离线训练：**
- 样本构造：用户正向行为（关注/点击/完播）作为正样本，曝光未点击或随机采样作为负样本
- 特征工程：User侧包括用户画像（年龄、性别、地域）、行为特征（关注列表、互动历史、播放历史）；Item侧包括账号画像（类目、粉丝数、发文数）、内容特征
- 模型训练：使用Adam优化器，学习率通常设为1e-3到1e-4，batch size根据GPU显存调整
- 在SIMNET规划中，GPU单卡V100上，标准BOW-DSSM网络1亿训练数据30分钟内过一个epoch；标准CNN-DSSM（kernel [3,4,5]*64，100w词表，dim=128）1亿数据90分钟内过一个epoch（来源：百亿量级SIMNET模型规划）

**训练目标设定（SIMNET百亿量级规划）：**
- 样本量：100亿
- 词表：百万级（支持500w大小词表，basic/phrase/bigram）
- 更新周期：每月
- 编码：basic/phrase/bigram/BPE
- 表示：CNN/BOW
- 匹配：COS/MLP
- 多域：title/click-query/Content（来源：百亿量级SIMNET模型规划）

### 2.4 线上ANN检索

DSSM模型训练完成后，user塔和item塔是独立的。线上服务时：

1. **Item embedding预计算**：离线批量计算所有item的embedding，存入向量数据库（如FAISS、Milvus）或Redis
2. **User embedding实时计算**：线上请求时，实时计算user embedding（或缓存用户embedding，定期更新）
3. **ANN近似最近邻检索**：用user embedding在item embedding库中做最近邻搜索，返回topK候选

ANN检索的核心是**在精度和速度之间做权衡**：
- **暴力搜索（Flat）**：精度100%，但O(N)复杂度，百万级item就很慢
- **IVF（倒排文件）**：先聚类，只搜索最近的几个簇，速度快但有精度损失
- **HNSW（层次化可导航小世界图）**：基于图的索引，查询效率高，是目前工业界主流
- **PQ（乘积量化）**：压缩向量存储，适合内存受限场景

在微视账号推荐中，item库规模在百万级（达人池），我们采用FAISS的IVF+PQ索引，单次检索延迟控制在5ms以内。

### 2.5 DSSM二期优化

在DSSM一期上线后，我做了二期优化，主要包括以下几个方向：

**特征侧优化：**
- 增加用户行为序列特征，用Attention机制聚合用户历史行为
- 增加账号侧的内容特征（视频标题、标签的语义embedding）
- 增加交叉特征（用户兴趣类目与账号发文类目的匹配度）

**模型侧优化：**
- 从简单的MLP塔升级为带Attention的结构，尝试过WND、DIN、MLP等结构，效果差异不大（来源：基于策略梯度的TopK集合召回推荐算法中模型选择经验）
- 多塔融合：basic塔+phrase塔分别编码后concat
- 在SIMNET规划中，另一种方案是多个编码特征在上层concat：q_emb = concat([b_q, p_q])，t_emb = concat([b_t, p_t])，然后交互层计算点乘/cos（来源：百亿量级SIMNET模型规划）

**训练侧优化：**
- 引入w2v预训练初始化词表：用中文词向量初始化高频25W词，其余25W随机初始化，单模型正逆率从1.57提升到1.60（来源：百亿量级SIMNET模型规划）
- 混合精度训练、数据prefetch、OP算子融合等工程优化
- 超大batch收敛（LAMB优化器）待验证

**效果验证：**
- 在混排CTR模型中，SIMNET特征绝对值正逆序提升千分之8，相对值千分之3
- 特征重要度按分裂个数排第7，按增益排第14（来源：百亿量级SIMNET模型规划）

> **面试口述版：**
> "DSSM双塔召回是我在微视重点做的方向之一。核心思路是把user和item分别编码到同一个语义空间，用余弦相似度做匹配。训练上我们用pair-wise margin loss，负采样采用曝光未点击加随机采样的混合策略。线上是典型的'离线预计算item embedding + 实时计算user embedding + ANN近邻检索'架构，用FAISS做IVF+PQ索引，百万级达人库单次检索5ms以内。二期我主要做了三方面优化：特征侧加了行为序列Attention和内容语义特征；模型侧从单塔升级到basic+phrase多塔融合；训练侧用w2v预训练初始化词表，正逆率从1.57提到1.60。作为高级特征输入下游CTR模型，正逆序绝对值提升千分之8。"

**Q：DSSM的负采样为什么重要？有哪些策略？**
A：负采样决定了模型学习的决策边界。如果负样本太简单（随机采样），模型很快就能区分正负，学不到精细的语义匹配；如果负样本太难（全是hard negative），模型可能无法收敛。工业界常用的策略是：①曝光未点击负采样（最接近真实分布）；②随机负采样（保证多样性）；③hard negative（从同类目或模型topK中采样，提升区分度）。通常是多种策略混合，正负比1:5到1:10。

**Q：DSSM线上为什么用ANN而不是精确计算？**
A：因为item库规模太大（百万到亿级），每次请求都和所有item计算余弦相似度是O(N)，延迟无法接受。ANN通过聚类（IVF）、图索引（HNSW）、向量压缩（PQ）等技术，在牺牲极小精度的前提下，把复杂度降到O(logN)甚至更低。百万级item用FAISS的IVF+PQ，单次检索可以做到5ms以内，召回率损失通常在1%以内。

## 三、TDM深度树匹配召回

### 3.1 TDM原理与树结构

TDM（Tree-based Deep Matching）是阿里提出的一种深度树匹配召回方法，核心思想是**将所有item组织成一棵树结构，通过beam search从根节点逐层向下筛选，最终找到topK个最匹配的叶子节点（item）**。

我在微视做账号推荐时研究过TDM方案，其树结构的关键设计如下：

**树的构建：**
- 叶子节点是所有item（在我们场景中是达人账号）
- 非叶子节点是item的聚类，每个节点代表一个"兴趣簇"
- 树的构建方式有两种：
  1. **基于item embedding的层次聚类**：先用item2vec或DSSM得到item embedding，然后做层次聚类（如HKM）生成树
  2. **基于行为共现的树构建**：根据用户行为序列中item的共现关系构建树

**树的特点：**
- 每个叶子节点（item）只属于一个父节点
- 每个非叶子节点代表其所有子节点的"抽象兴趣"
- 树的深度通常为log2(N)，百万级item约20层
- 兄弟节点之间的兴趣相似度较高

### 3.2 Beam Search检索过程

TDM的线上检索采用**逐层beam search**：

```
第0层（根节点）：候选集 = {根节点}，beam size = K
第1层：展开根节点的所有子节点，用模型打分，取topK
第2层：展开上一层topK节点的所有子节点，合并去重后打分，取topK
...
最后一层（叶子层）：展开上一层topK节点的所有子叶子节点，打分取topK
```

每一层的打分模型是一个**深度神经网络**，输入是user特征和节点特征（节点可以用其所有子节点item embedding的平均来表示），输出是user对该节点的匹配概率。

**Beam search的复杂度分析：**
- 假设树的分支因子为b，beam size为K
- 每层需要打分的节点数为K×b
- 总层数为log_b(N)
- 总打分次数为K×b×log_b(N)
- 相比暴力搜索的O(N)，TDM的复杂度是O(logN)级别

例如，百万级item，分支因子b=100，beam size K=200，树深度约3层，总打分次数=200×100×3=60000次，远小于100万次。

### 3.3 训练方式

TDM的训练是一个**逐层监督学习**的过程：

**样本构造：**
- 对于每个正样本（用户交互的item），从根到该item叶子节点的路径上所有节点都是正样本
- 每一层中，与正样本节点同层的其他节点作为负样本
- 本质上是在每一层做一个"该节点是否在用户兴趣路径上"的二分类

**损失函数：**
- 每一层用softmax交叉熵损失
- 训练时可以逐层训练，也可以联合训练

**训练技巧：**
- 负采样：每一层从同层节点中随机采样负样本，不需要和所有节点计算
- 节点embedding初始化：可以用item embedding的层次聚类结果初始化
- 树结构可以和模型联合优化：训练几轮后重新聚类更新树结构

### 3.4 TDM与DSSM的对比

| 维度 | DSSM双塔 | TDM深度树 |
|---|---|---|
| **原理** | user和item分别编码到同一空间，余弦相似度匹配 | item组织成树，beam search逐层筛选，每层用深度模型打分 |
| **优点** | ①结构简单，训练和部署成熟；②user塔和item塔独立，item embedding可预计算；③支持增量更新 | ①检索复杂度O(logN)，超大规模item库更有优势；②树结构天然有层次化兴趣聚类；③每层用深度模型非线性打分，表达能力更强 |
| **缺点** | ①user和item的交互只有最后一层余弦，表达能力受限；②ANN检索有精度损失；③超大规模（亿级）item的ANN索引维护成本高 | ①树结构构建和维护复杂；②beam search可能漏掉最优解（beam size限制）；③训练需要逐层监督，工程复杂度高；④树结构更新需要重新训练 |
| **适用场景** | 百万到千万级item库，对延迟要求高，需要快速迭代 | 亿级以上超大规模item库，对召回精度要求高，有足够工程资源维护树结构 |
| **延迟** | 极低（ANN检索，毫秒级） | 较低（beam search逐层打分，取决于层数和beam size） |
| **在微视的应用** | 主力召回方案，已上线并持续迭代 | 作为技术预研方向，探索在达人池扩大后的适用性 |

> **面试口述版：**
> "TDM是我在微视做技术预研时深入研究的方向。它的核心是把所有item组织成一棵树，线上用beam search从根节点逐层向下筛选，每一层都用一个深度模型打分，最后在叶子层取topK。相比DSSM，TDM的优势在于每层都有非线性的深度交互，表达能力更强，而且检索复杂度是O(logN)，在亿级超大规模item库下比DSSM的ANN更有优势。但TDM的工程复杂度也高很多——树结构需要基于item embedding做层次聚类构建，训练是逐层监督的，beam search还有可能因为beam size限制漏掉最优解。在微视百万级达人池的场景下，DSSM+ANN已经足够，TDM更多是作为达人池扩大后的技术储备。"

**Q：TDM的beam search会不会漏掉最优解？怎么缓解？**
A：会的。beam search每一层只保留topK个节点，如果最优item所在的分支在某一层打分偏低被裁掉，后面就再也找不回来了。缓解方法有：①增大beam size（但会增加计算量）；②采用多样性beam search，避免topK都集中在同一个分支；③树结构构建时尽量让相似item聚在同一分支，减少跨分支的最优解；④可以做多棵树的ensemble，不同树结构互补。

**Q：TDM的树结构怎么构建？需要经常更新吗？**
A：树结构通常基于item embedding做层次聚类构建，比如先用item2vec或DSSM预训练得到item embedding，然后用HKM（层次k-means）等算法聚类生成树。item新增或兴趣分布变化时需要更新树结构，但更新树意味着模型可能需要重新训练，所以工业界通常是定期（如每周/每月）更新一次树结构，期间新增item可以先挂到最近的叶子节点下。

## 四、YouTube DNN召回

### 4.1 YouTube DNN召回原理

YouTube在2016年发表的论文《Deep Neural Networks for YouTube Recommendations》中提出了一种经典的DNN召回架构。我在微视做账号推荐时参考了这一架构。

YouTube DNN召回的核心思想是**将召回问题建模为一个多分类问题**：给定用户上下文特征，预测用户在下一次交互中会选择哪个item（视频）。

```
用户特征（观看历史、搜索历史、人口属性、地理位置）
    ↓
Embedding层（视频ID embedding、搜索词embedding）
    ↓
特征拼接（concat）
    ↓
多层ReLU（通常3层，1024→512→256）
    ↓
user embedding（最后一层隐层输出）
    ↓
softmax层（每个item一个类别，权重矩阵即item embedding）
```

**关键设计：最后一层隐层输出作为user embedding，softmax层的权重矩阵作为item embedding。** 这样user和item就在同一个空间中，线上可以用user embedding做最近邻检索。

### 4.2 特征工程

YouTube DNN召回的特征设计是其效果好的关键，我在微视实践中参考了以下特征维度：

**用户行为特征：**
- **观看历史embedding**：用户最近观看的N个视频的ID embedding，取平均（或用Attention加权）。在账号推荐场景中对应为**用户最近关注/互动的N个账号的embedding**
- **搜索历史embedding**：用户最近搜索的query的embedding
- **用户最近上传行为**：用户自己的内容创作行为

**用户画像特征：**
- **人口属性**：年龄、性别、地理位置
- **设备信息**：设备型号、操作系统
- **登录状态**：是否登录、新老用户标识

**上下文特征：**
- **时间特征**：当前时间、用户最近一次活跃时间
- **场景特征**：当前所在页面（关注页/发现页/消息页）

**Example age（样本年龄特征）：**
这是YouTube论文中一个非常巧妙的设计。训练样本中加入"该样本从产生到训练时经过的时间"作为特征。因为用户兴趣会随时间漂移，热门item也有时间衰减，加入example age可以让模型学到时间衰减规律。线上预测时example age设为0（或很小的值），表示预测当前时刻。

### 4.3 采样策略

YouTube DNN召回将问题建模为多分类，但item库有百万到亿级，直接做全量softmax计算量太大。因此采用了**负采样（Negative Sampling）**或**层次softmax（Hierarchical Softmax）**来加速训练。

**负采样策略：**
- 对每个正样本（用户实际交互的item），从全量item分布中采样若干负样本
- 采样分布不是均匀分布，而是**按item的流行度加权**（类似word2vec中的unigram采样），即热门item更容易被采为负样本
- 这样做的原因是：热门item本身曝光多，作为负样本更合理；同时也能让模型学会区分"热门但用户不感兴趣"和"用户真正感兴趣"

**在微视账号推荐中的实践：**
- 达人池约百万级，我们采用负采样训练，每个正样本配5-10个负样本
- 负采样分布按达人粉丝数加权，头部达人更容易被采为负样本
- 同时加入曝光未点击负样本，更贴近真实分布

### 4.4 YouTube DNN与DSSM的区别

| 维度 | YouTube DNN召回 | DSSM双塔召回 |
|---|---|---|
| **建模方式** | 多分类（softmax），预测用户下一次交互的item | pair-wise匹配，学习user和item的语义相似度 |
| **特征交互** | user特征在塔内充分交互，最后与item embedding做点积 | user塔和item塔独立，只有最后一层余弦/点积交互 |
| **item侧特征** | item只有ID embedding（softmax权重），无法引入item侧丰富特征 | item塔可以引入任意item特征（类目、粉丝数、内容特征等） |
| **训练效率** | 负采样后效率高，但item库极大时仍有挑战 | pair-wise训练，每个样本只涉及1正1负，效率高 |
| **线上服务** | user embedding + ANN检索 | user embedding + ANN检索（相同） |
| **适用场景** | user侧特征丰富，item侧特征较少或只有ID | item侧特征丰富，需要精细的item表示 |

> **面试口述版：**
> "YouTube DNN召回是我在微视做召回时的重要参考架构。它最核心的思想是把召回建模成多分类问题——给定用户特征，预测用户下一次会交互哪个item。最后一层隐层输出作为user embedding，softmax的权重矩阵就是item embedding，这样线上同样可以用ANN检索。YouTube DNN的几个设计细节我印象很深：一是example age特征，把样本产生到训练的时间差作为特征输入，让模型学到时间衰减，线上预测时设为0；二是负采样按item流行度加权而不是均匀采样，因为热门item更应该作为负样本；三是用户行为序列用embedding平均池化，简单但有效。在微视账号推荐中，我们的达人侧特征比较丰富（类目、粉丝数、发文特征等），所以最终选择了DSSM双塔而不是YouTube DNN，因为DSSM的item塔可以更灵活地引入item特征。"

**Q：YouTube DNN为什么用最后一层隐层作为user embedding，而不是输出层？**
A：因为输出层是softmax概率，维度等于item库大小（百万级），不适合作为embedding。而最后一层隐层（通常256或512维）是用户特征的压缩表示，已经包含了用户的兴趣信息。同时softmax层的权重矩阵（维度是隐层维度×item数）的每一列正好对应一个item的embedding，这样user embedding和item embedding就在同一个空间，可以直接点积计算匹配度。这是一种非常优雅的设计。

## 五、ICF与Advanced-ICF召回

### 5.1 协同过滤（CF）基础原理

协同过滤是推荐系统最经典的召回方法，我在微视账号推荐中大量使用了CF召回。协同过滤分为两大类：

**User-CF（基于用户的协同过滤）：**
- 核心思想：找到与目标用户兴趣相似的其他用户，推荐这些相似用户喜欢但目标用户还没接触的item
- 相似度计算：用户-物品交互矩阵的行向量相似度（余弦/Jaccard）
- 优点：推荐结果新颖性好，适合用户数较少的场景
- 缺点：用户数大时相似度计算量大，用户兴趣变化快时需要频繁更新

**Item-CF（基于物品的协同过滤，ICF）：**
- 核心思想：找到与用户已交互item相似的其他item进行推荐
- 相似度计算：用户-物品交互矩阵的列向量相似度
- 优点：item相似度相对稳定，可以离线预计算，线上只需查表；推荐结果可解释性强（"因为你关注了A，所以推荐B"）
- 缺点：热门item容易和所有item都相似，需要惩罚热门item

在微视账号推荐场景中，我们主要使用**Item-CF（达人CF）**，因为达人账号的相似度相对稳定，可以离线计算。

**ICF的相似度计算公式（经典版）：**

```
sim(i, j) = |N(i) ∩ N(j)| / sqrt(|N(i)| × |N(j)|)
```

其中N(i)是交互过item i的用户集合。这是余弦相似度在0-1交互矩阵上的形式。

**但这个公式有个问题**：热门item的N(i)很大，会和很多item都有较高的相似度。因此需要对热门item进行惩罚，常用的改进是IUF（Inverse User Frequency）：

```
sim(i, j) = Σ_{u∈N(i)∩N(j)} 1/log(1 + |N(u)|) / sqrt(|N(i)| × |N(j)|)
```

即活跃用户（关注了很多账号的用户）的权重降低，因为他们的关注行为信息量低。

### 5.2 微视达人CF的具体实现

在微视账号推荐中，达人CF召回的具体实现如下（来源：好友达人梳理（总））：

**达人CF相似度计算：**
1. 计算同一用户下关注达人两两的相似度：
   - 基础得分：score = log(该用户关注数) / (log(达人A粉丝数) × log(达人B粉丝数))
   - 如果两个达人一级类别相同，分数×20
   - 如果两个达人二级类别相同，分数×50
   - 如果达人优先级相同且都属于9级10级（头部达人），得分×25
2. 将两两达人pid作为key，groupbykey得分相加
3. 召回与pidA得分最高的topN且相同一级/二级类目的相似达人
4. 将得分根据最大最小归一化，存入HDFS

**个性化达人CF召回（线上使用）：**
- 基于用户最近10个关注达人信息，拉取协同过滤CF结果
- 召回ID：14113，对应phase ws_out_user_hot_daren_recmd

这个实现的关键设计点：
- **用log(用户关注数)做分子**：关注数多的用户，其关注行为的共现信息量更低（可能是随便关注的），所以用log压缩
- **用log(达人粉丝数)做分母**：粉丝多的头部达人，和其他达人共现的概率天然高（因为关注的人多），需要惩罚
- **类目加权**：同类目达人的相似度大幅提升（一级×20，二级×50），保证召回的相关性
- **头部达人加权**：同为9级10级头部达人再×25，因为头部达人之间的共现更有信息量

### 5.3 Advanced-ICF的改进点

Advanced-ICF是在经典ICF基础上的一系列改进，我在实践中总结了以下几个方向：

**1. 相似度计算的改进：**
- **时间衰减**：用户的近期行为权重更高，远期行为权重衰减。例如加入exp(-α×时间差)的衰减因子
- **行为类型加权**：不同行为的信息量不同。在账号推荐中，关注>评论>点赞>播放完播>曝光。我们在互动行为召回中用"赞转评×2+完播×1"的加权方式（来源：好友达人梳理（总））
- **用户活跃度惩罚（IUF）**：如前所述，活跃用户的行为权重降低

**2. 冷启动处理：**
- 新item没有交互数据，无法计算CF相似度。可以用内容相似度（基于item属性/内容embedding）补充
- 在微视中，新达人可以先用类目热门召回兜底，等积累了足够交互数据后再进入CF池

**3. 多样性与新颖性：**
- 经典ICF容易推荐热门item，导致推荐结果同质化
- 可以通过类目打散、降权热门item、加入随机探索等方式提升多样性
- 在微视重排层有达人品类限制：ret_num<10时相同类目最多出现1次，ret_num>=10时最多出现2次（来源：好友达人梳理（总））

**4. 增量更新：**
- 全量重新计算CF相似度耗时很长（微视二度好友计算需要10-20小时，来源：好友及达人推荐梳理）
- Advanced-ICF支持增量更新：只更新有新行为的用户和item对应的相似度
- 可以用滑动窗口（如最近30天行为）定期全量计算，期间做增量补充

> **面试口述版：**
> "ICF是我在微视账号推荐中用得最成熟的召回方法之一。经典ICF就是基于共现矩阵计算item相似度，但直接用余弦相似度有热门item偏置的问题。我们的达人CF做了几个关键改进：一是相似度公式用log(用户关注数)/(log(达人A粉丝数)×log(达人B粉丝数))，同时惩罚活跃用户和头部达人的共现偏置；二是加入类目加权，同一级类目×20、同二级类目×50，大幅提升召回相关性；三是行为类型加权，关注和互动行为的权重高于单纯播放。线上是基于用户最近10个关注达人拉取CF结果，这路召回是达人方向的主力召回之一。Advanced-ICF我们还探索了时间衰减、增量更新、多样性打散等方向。"

**Q：ICF中为什么要惩罚热门item？**
A：因为热门item（粉丝多的达人）被很多用户关注，它和其他任何item的共现次数都会很高，导致经典余弦相似度计算出来热门item和所有item都"相似"。这样召回结果会被热门item主导，缺乏个性化。惩罚方式通常是在分母中加入item流行度（如log(粉丝数)），或者用IUF（逆用户频率）给活跃用户降权。在微视的达人CF中，我们用log(达人粉丝数)做分母，就是为了惩罚头部达人的共现偏置。

## 六、图Embedding召回

### 6.1 图Embedding方法总览

图Embedding是将图结构中的节点映射到低维稠密向量的技术，在推荐系统中可以用于用户、item、关系的向量化表示。我在微视做账号推荐时，图Embedding是重点探索方向之一。

图Embedding方法可以分为三大类：

**1. 基于随机游走的方法（Random Walk based）：**
- **DeepWalk**：将图中节点类比为词，随机游走生成的路径类比为句子，用Skip-gram（Word2vec）训练节点embedding
- **Node2Vec**：在DeepWalk基础上引入参数p和q控制随机游走的策略，p控制回到上一节点的概率（BFS倾向），q控制走到远处节点的概率（DFS倾向），可以在"同质性"和"结构性"之间做权衡
- **LINE**：同时保留一阶相似度（直接相连的节点相似）和二阶相似度（共享邻居的节点相似），用edge sampling优化
- **SDNE**：用深度自编码器同时保留一阶和二阶相似度

**2. 基于图神经网络的方法（GNN based）：**
- **GCN（图卷积网络）**：通过邻居节点的特征聚合来更新节点表示，每层做一次邻居聚合，多层后节点可以感知到多跳邻居
- **GraphSAGE**：归纳式学习，通过采样邻居并聚合特征来生成节点embedding，支持新节点的快速推断
- **GAT（图注意力网络）**：在邻居聚合时引入注意力机制，不同邻居有不同权重
- **PinSage**：Pinterest提出的工业级GNN，用随机游走+重要性采样做邻居聚合，支持亿级节点

**3. 基于知识图谱的方法：**
- **TransE/TransH/TransR**：将实体和关系映射到向量空间，通过关系平移假设学习embedding
- 在推荐中可以引入item的属性、类别等知识图谱信息

### 6.2 微视图Embedding的实践

在微视账号推荐中，我主要探索了基于随机游走的图Embedding方法，构建了以下几种图：

**社交关系图：**
- 节点：用户账号
- 边：关注关系、好友关系（QQ/微信/通讯录/红包）
- 目标：学习用户的社交关系embedding，用于好友推荐和社交兴趣召回

**用户-达人二部图：**
- 节点：用户 + 达人账号
- 边：用户关注/互动/播放达人的行为
- 目标：学习用户和达人的统一embedding空间，用于个性化召回
- 这是最核心的图，因为它同时包含了用户兴趣和达人属性

**达人共现图：**
- 节点：达人账号
- 边：被同一用户关注/互动的达人之间的连边，边权重为共现次数
- 目标：学习达人之间的相似度embedding，用于相似达人召回

**随机游走策略：**
- 在用户-达人二部图上做随机游走，游走路径交替经过用户和达人节点
- 游走长度设为30-50，每个节点生成10-20条游走路径
- 用Word2vec的Skip-gram模型训练，embedding维度设为32或64
- 窗口大小设为5-10

### 6.3 图Embedding实验效果

我在微视做了graph embedding的线上AB实验，效果数据如下（来源：各种emb实验）：

**实验一：10%流量，2天数据（3月25-26日）**

### 6.4 GNN在推荐召回中的应用展望

虽然我在微视主要实践了基于随机游走的图Embedding，但也对GNN方法做了技术调研：

**GNN相比随机游走的优势：**
- 可以引入节点特征（用户画像、达人属性），而不只是利用图结构
- 邻居聚合可以学到更丰富的节点表示
- GraphSAGE等归纳式方法支持新节点的快速推断，不需要重新训练

**GNN在工业界的挑战：**
- 大规模图的训练效率问题（亿级节点）
- 在线推断的延迟问题（需要采样邻居并做多层聚合）
- 图结构的动态更新问题

**PinSage的工业实践参考：**
- Pinterest用PinSage处理30亿节点、180亿边的图
- 采用随机游走+重要性采样做邻居选择，避免全图计算
- 用MapReduce做分布式训练
- 离线生成所有节点embedding，线上用ANN检索

> **面试口述版：**
> "图Embedding是我在微视召回方向的重点探索之一。我们主要构建了用户-达人二部图和社交关系图，用DeepWalk/Node2Vec的随机游走+Word2vec方式训练节点embedding。具体做法是在二部图上做随机游走，路径交替经过用户和达人节点，游走长度30-50，每个节点生成10-20条路径，然后用Skip-gram训练32维embedding。线上AB实验效果很显著，在发现好友页10%流量下pCTR相对提升了11%-14%，关注页也有2%-10%的提升。发现好友页效果最好是因为社交图结构的信号在这个场景最强。后来我们也做了w2v替换实验对比不同embedding方式。GNN方向我们做了技术调研，GraphSAGE和PinSage是工业界比较成熟的方案，但在微视百万级达人池的规模下，随机游走方法已经足够且工程更简单。"

**Q：DeepWalk和Node2Vec的区别是什么？**
A：DeepWalk是完全随机的游走（每个邻居等概率选择），而Node2Vec引入了两个参数p和q来控制游走策略。p是返回参数（return parameter），控制游走回到上一个节点的概率，p越小越倾向于BFS（在局部探索，学到结构性等价）；q是进出参数（in-out parameter），控制游走向远离上一个节点的方向走的概率，q越小越倾向于DFS（深入探索，学到同质性/社区结构）。通过调节p和q，可以在"节点的结构角色相似"和"节点在同一社区"之间做权衡。

**Q：图Embedding和DSSM有什么区别和联系？**
A：区别在于：图Embedding只利用图结构信息（节点之间的连接关系），通过随机游走+Word2vec训练，不能直接引入节点属性特征；DSSM可以引入丰富的user和item侧特征，通过深度网络学习语义匹配。联系在于：两者最终都得到user和item在同一空间的embedding，线上都用ANN检索。在实际应用中，两者可以互补——图Embedding捕捉行为共现的结构信号，DSSM捕捉属性和内容的语义信号，可以做多路召回融合，也可以用图Embedding的结果初始化DSSM的embedding层。

## 七、视频号相似召回与行为Embedding召回

### 7.1 视频号相似召回

视频号相似召回是针对"相关推荐"场景的召回方法，即用户在观看某个视频或访问某个账号主页时，推荐相似的视频或账号。

**相似召回的核心思路：**
- 基于内容相似度：视频标题、标签、封面、音频等内容特征的相似度
- 基于行为相似度：被相同用户观看/互动/关注的视频或账号之间的相似度
- 基于Embedding相似度：用深度模型学习视频/账号的embedding，计算余弦相似度

**在账号推荐场景中的相似召回：**
- 当用户关注了某个达人后，推荐与该达人相似的其他达人
- 当用户访问某个账号主页时，推荐相关账号
- 相似达人的计算方式包括：
  1. **CF相似度**：如前所述的达人CF共现相似度
  2. **Embedding相似度**：基于用户行为训练的达人embedding的余弦距离
  3. **类目相似度**：同一级/二级类目下的热门达人

在微视的达人召回体系中，"相似达人embedding召回"（ID 12220）是专门用于相关推荐场景的召回源，基于用户行为的达人emb直接召回相似达人，返回每个达人emb相似的top10达人（来源：好友达人梳理（总））。

### 7.2 行为Embedding召回项目细节

行为Embedding召回是我在微视的核心项目之一，基于用户的正向行为序列训练达人embedding，然后做相似召回。

**项目背景：**
- 微视账号推荐需要个性化的达人召回，传统CF只能捕捉共现信号，无法建模用户行为序列的时序信息
- 行为Embedding召回借鉴Word2vec思想，将用户的行为序列类比为"句子"，达人ID类比为"词"，学习达人的分布式表示

**样本定义（来源：好友达人梳理（总））：**
- 用户7天内有正向行为的达人list
- 格式：(用户id, 达人idList(赞转评或者完播))
- 过滤条件：正向行为达人list长度大于5且小于5000
- 行为类型：赞转评或完播（正向行为）

**模型训练：**
- 利用Word2vec训练作者**32维度**embedding
- 采用Skip-gram模型，窗口大小通常设为5
- 训练数据是用户的行为序列，按时间排序
- 负采样采用Word2vec默认的按词频采样

**相似达人计算：**
- 计算达人与**相同一级分类下**的达人两两之间的cos距离
- 返回距离最近的**10个**达人
- 限制一级分类的原因：提升召回结果的准确性，但会降低覆盖率。根据不同应用场景和需求，可做灵活折中（来源：好友达人梳理（总））

**基于用户行为召回相似达人：**
- 召回用户最近关注**10个**达人的相似达人
- 共计召回数量**100**（10个达人×每个10个相似达人）
- 召回ID：13804，对应phase ws_out_user_trig_daren_recmd
- 线上使用状态：已上线

**召回通路配置：**
- 这路召回在分层策略中属于第2层（layer 2），与个性化CF召回、实时关注、用户互动行为召回同层
- 配置格式：layer_policy=1:13010@13008@13007@13001@13004;2:13804@14113@13996@13801;3:14998@13997@14111
- 各层Quota比例：rule_layer = 0.5;0.3;0.2（第1层50%，第2层30%，第3层20%）（来源：好友达人梳理（总））

### 7.3 行为Embedding召回的效果与优化

**效果数据：**
- 行为Embedding召回作为达人召回的主力路之一，在关注页和发现好友页都有稳定贡献
- 在graph embedding实验中，我们对比了不同embedding方式的效果，graph embedding在发现好友页pCTR提升10%+（来源：各种emb实验）

**优化方向：**
1. **Embedding维度**：从32维提升到64或128维，表达能力更强，但存储和计算成本增加
2. **行为序列加权**：不同行为类型（关注>赞转评>完播）赋予不同权重，而不是简单的序列
3. **时间衰减**：近期行为权重更高，远期行为衰减
4. **引入内容特征**：在Word2vec基础上加入达人的内容特征（类目、标签），做联合embedding
5. **类目限制的折中**：限制一级类目提升准确性但降低覆盖率，可以根据场景灵活调整——相关推荐场景限制类目，发现页场景不限制类目以提升覆盖率

> **面试口述版：**
> "行为Embedding召回是我在微视从0到1做上线的核心项目。核心思路是借鉴Word2vec，把用户7天内的正向行为序列（赞转评或完播的达人list）当作句子，达人ID当作词，用Skip-gram训练32维的达人embedding。样本过滤要求行为序列长度在5到5000之间。训练完后，计算同一级类目下达人两两之间的cos距离，每个达人保留最相似的10个。线上召回时，取用户最近关注的10个达人，各自拉取10个相似达人，总共召回100个候选。这路召回上线后作为达人方向的主力召回之一，在分层策略中占第2层30%的quota。后来我又在这个基础上探索了graph embedding，把社交关系图和行为图结合起来，在发现好友页pCTR提升了10%以上。"

**Q：行为Embedding召回为什么限制一级类目？不限制会怎样？**
A：限制一级类目是为了提升召回结果的准确性——同一类目下的达人相似度更可靠，跨类目的embedding相似度可能有噪声。但限制类目的代价是降低了覆盖率，用户可能感兴趣的跨类目达人召不回来。我们的做法是根据场景灵活折中：在相关推荐场景（如账号主页的相关推荐）限制一级类目，保证相关性；在发现页等需要多样性的场景，可以不限制类目或只做软限制。文档中也明确提到"限制一级类目可提升召回结果的准确性，但是降低了覆盖率。根据不同应用场景和需求，可做灵活折中"。

## 八、强化学习召回

### 8.1 强化学习召回原理

强化学习（RL）在推荐系统中的应用是我在微视后期重点关注的方向。传统召回方法通常优化单item的即时反馈（点击率/关注率），但忽略了**推荐结果作为一个集合的整体效果**以及**长期回报**。

**强化学习的基本框架（MDP）：**
- **状态（State, S）**：用户的当前状态，包括用户画像、历史行为、上下文等
- **动作（Action, A）**：推荐的item（或item集合）
- **奖赏（Reward, R）**：用户对推荐结果的反馈（点击/关注/完播等）
- **策略（Policy, π）**：给定状态下选择动作的概率分布 π(a|s)
- **状态转移（P）**：用户交互后状态的变化
- **折扣因子（γ）**：长期奖赏的折扣

**强化学习在召回中的核心优势：**
1. **集合级优化**：传统方法逐个item打分，忽略了item之间的相互影响（如相似item扎堆会导致审美疲劳）。RL可以直接优化推荐集合的整体效果
2. **长期回报优化**：传统方法只优化即时反馈，RL可以优化长期用户留存、活跃度等
3. **探索与利用（E&E）**：RL天然支持探索新内容，避免推荐结果同质化

在应用宝必备弹窗场景中，我们复现并改进了Google的Top-K Off-Policy Correction for a REINFORCE Recommender System论文，从候选集中一次性选取Top21个app作为集合召回结果（来源：基于策略梯度的TopK集合召回推荐算法）。

### 8.2 基于策略梯度的TopK集合召回

这是我在强化学习召回方向最深入的实践，基于应用宝必备弹窗场景（来源：基于策略梯度的TopK集合召回推荐算法）。

**问题描述：**
- 必备弹窗场景一次推荐最多21个App
- 传统做法：召回候选→逐个pCVR打分→排序→展示
- 问题：如果top5都是淘宝、天猫、拼多多、京东、蘑菇街这类功能相似的app，用户不太可能同时下载多个，整体效果差
- 目标：学习一个集合召回策略，从候选集中一次性选取K个item，最大化集合整体的奖赏

**REINFORCE策略梯度算法：**

目标函数（最大化长期奖赏）：
```
J(θ) = E_{π_θ}[r] = Σ_s d^{π_θ}(s) Σ_a π_θ(s,a) R_s^a
```

策略梯度：
```
∇_θ J(θ) = E_{π_θ}[∇_θ log π_θ(s,a) · r]
```

参数更新（梯度上升）：
```
Δθ_t = α · ∇_θ log π_θ(s_t, a_t) · v_t
v_t = R_{t+1} + γR_{t+2} + ... + γ^{T-1}R_T
```

对于必备弹窗这种无连续交互的场景，只考虑瞬时奖赏，状态转移和折扣系数都忽略。

**Off-Policy重要性采样：**

由于线上行为策略（β）和目标策略（π）不一致（线上有各种实验和干预逻辑），需要用重要性采样修正：

```
∇_θ J_β(π_θ) = E_{s~ρ^β, a~β}[π_θ(s,a)/β_θ(s,a) · ∇_θ log π_θ(s,a) · Q^π(s,a)]
```

其中π_θ(s,a)/β_θ(s,a)是重要性采样权重。

**TopK策略梯度：**

当需要推荐一个集合（K个item）时，定义item出现在最终集合中的概率：
```
α_θ(a,s) = 1 - (1 - π_θ(a,s))^K
```

TopK Off-Policy Gradient：
```
E_{s~ρ^β, a~β}[α_θ(s,a)/β_θ(s,a) · ∇_θ log α_θ(s,a) · Q^π(s,a)]
= E_{s~ρ^β, a~β}[π_θ(s,a)/β_θ(s,a) · λ_K(s,a) · ∇_θ log π_θ(s,a) · Q^π(s,a)]
```

其中额外的梯度修正项：
```
λ_K(s,a) = ∂α_θ(s,a)/∂π_θ(s,a) = K(1 - π_θ(s,a))^{K-1}
```

**λ_K的特性：**
- 当π_θ→0时，λ_K→K：softmax结果小的item，梯度更新更激进（鼓励探索）
- 当π_θ→1时，λ_K→0：已经很可能被选中的item，梯度更新大幅降低甚至为0（保证其他item有机会更新）

这个设计非常巧妙：TopK策略在保证排序的同时，自动调节了不同item的梯度更新幅度，避免了所有梯度都集中在头部item上。

**权重裁剪（Weight Capping）：**

为了防止重要性采样权重过大导致梯度爆炸和过早收敛，采用最简单的Weight Capping：
```
w_c(s,a) = min(π_θ(s,a)/β_θ(s,a), c)
```

通过设置常数c，保证小步更新，避免大波动。

**线上动作选择：**
- 根据输出action概率，使用**轮盘赌有放回**地选取21个不同app
- 若遇到重复选取，则再额外增加一次轮盘赌
- 轮盘赌同时保证了探索和利用
- 如果不能接受线上探索行为，也可以用值排序的方法代替轮盘赌

### 8.3 奖赏的重新定义

这是项目中最有业务洞察的部分（来源：基于策略梯度的TopK集合召回推荐算法）：

**最初的问题：**
- 以单个item的奖赏之和作为集合的奖赏，效果不及预期
- 分析发现：对照组中"Taptap"获得最多曝光和最高后验cvr，但实验组中Taptap曝光量排在10名以外

**原因分析：**
- 下载"Taptap"的用户仅下载1个app的比例为**8.6%**
- 下载"百度极速版"的用户仅下载1个app的比例仅为**1.3%**
- 必备弹窗场景人均下载app约**7个**
- 下载用户中下载个数<=3的占比**52.3%**
- 下载个数>=10的占比**32.1%**
- 一键全下载用户占比**9.6%**

**结论：** 不是所有用户都有集合下载的需求，部分用户更倾向于挑选少量app下载。如果粗暴地以单个item奖赏之和作为集合奖赏，类似"仅下载Taptap"这样的精选行为只会拿到很低的奖赏，导致这部分用户需求无法被满足。

**解决方案：** 给下载<=3个app的用户行为同样赋予最高的奖赏。这样既满足了精选小众下载的需求，又最大化了有集合下载意愿用户的下载能力。

**效果：** 上线后整体分发系数（人均下载个数）提升**20%**（忽略曝光结构的情况下）。

### 8.4 模型结构与实现

**模型结构：**
- 尝试过WND结构、DIN结构、MLP结构，效果差异不大
- 最终采用带Attention的网络结构或简单MLP
- softmax层是softmax net，有参数更新
- label action是输出的动作维度

**特征：**
- User特征：年龄性别等属性特征，用户旧机安装列表，新机已安装app列表等行为特征

**π_θ和β_θ的区别：**
- 采用相同的训练结构和共享底层网络参数
- π_θ网络会反向传播回底层网络，β_θ不会
- π_θ网络的样本采用全样本和奖赏训练，β_θ仅采用有下载行为的样本做训练且无奖赏
- 原因：π_θ需要最大化长期回报，β_θ只需要学习实际样本的分布

### 8.5 强化学习调参实践

在强化学习召回的调参过程中，我积累了以下经验（来源：强化学习调参具体实现、RL+强化学习召回）：

**学习率调整：**
- RL训练对学习率非常敏感，太大容易震荡不收敛，太小收敛太慢
- 通常从1e-4开始尝试，根据训练曲线调整
- 可以采用学习率衰减策略

**奖赏缩放（Reward Scaling）：**
- 奖赏值的范围对训练稳定性影响很大
- 可以对奖赏做归一化或标准化（减去均值除以标准差）
- 也可以用clip限制奖赏的范围

**熵正则化（Entropy Regularization）：**
- 在损失函数中加入策略熵的惩罚项，鼓励探索，避免策略过早收敛到确定性动作
- 熵系数需要调参，太大会导致策略太随机，太小起不到探索作用

**批量大小：**
- RL训练的方差较大，需要较大的batch size来稳定梯度估计
- 但batch太大会降低样本效率
- 通常在512到4096之间尝试

**探索策略：**
- 线上用轮盘赌采样而不是贪心选择，保证探索
- 可以用ε-greedy策略，以概率ε随机探索
- 探索率需要随时间衰减

**未来展望（文档中提到）：**
- SMiRL：以最小化不确定性为奖赏进行学习
- 逆强化学习：从用户行为中自动学习奖赏函数，减少人工设计
- 加入Critic网络拟合长期奖赏（Actor-Critic架构），更好地刻画和服务用户

> **面试口述版：**
> "强化学习召回是我在微视后期重点探索的方向，最深入的实践是在应用宝必备弹窗场景复现Google的Top-K Off-Policy REINFORCE算法。这个场景一次推荐21个app，传统逐个pCVR排序的问题是top5可能都是功能相似的电商app，用户不会同时下载。我们用REINFORCE策略梯度直接优化集合奖赏，核心有几个技术点：一是Off-Policy重要性采样修正，因为线上行为策略和目标策略不一致；二是TopK策略梯度，定义item出现在集合中的概率α=1-(1-π)^K，推导出来的梯度修正项λ=K(1-π)^(K-1)，这个设计很巧妙——概率小的item梯度更激进去探索，概率大的item梯度趋近于0给其他item机会；三是Weight Capping防止重要性采样权重爆炸。最有业务洞察的是奖赏重定义——我们发现52.3%的用户只下载<=3个app，粗暴用单个奖赏之和会惩罚这类精选用户，于是给下载<=3个的用户同样赋予最高奖赏，上线后人均下载个数提升20%。模型上试过WND、DIN、MLP，效果差异不大，最后用带Attention的MLP。"

**Q：强化学习召回相比传统召回的优势和挑战是什么？**
A：优势：①直接优化集合级效果而不是单item，能处理item之间的相互影响（如多样性、互补性）；②可以优化长期回报而不只是即时反馈；③天然支持探索与利用。挑战：①训练不稳定，对超参数敏感，调参难度大；②Off-Policy场景下重要性采样权重可能过大导致梯度爆炸；③样本效率低，需要大量交互数据；④线上探索可能伤害用户体验；⑤奖赏函数设计困难，需要深刻的业务理解。在工业界，RL召回更多用于特定场景（如一次性展示多个item的弹窗、集合推荐），而不是全量替换传统召回。

**Q：TopK策略梯度中的λ项为什么能自动调节探索和利用？**
A：λ_K = K(1-π)^(K-1)是α对π的导数。当π很小时（模型认为这个item不太可能被选中），λ≈K，梯度被放大K倍，模型会更激进地更新这个item的参数，相当于鼓励探索；当π很大时（模型已经很确定这个item会被选中），λ≈0，梯度几乎不更新，相当于停止利用这个item，把梯度让给其他item。这样就自动实现了"不确定的多学，已确定的少学"，比固定学习率或固定探索率更智能。

## 九、item2vec与兴趣召回

### 9.1 item2vec原理

item2vec是Word2vec在推荐系统中的直接应用，我在微视的行为Embedding召回项目中核心就是用item2vec训练达人embedding。

**核心思想：**
- 将用户的行为序列（按时间排序的item列表）类比为自然语言中的"句子"
- 将每个item类比为"词"
- 用Word2vec的Skip-gram或CBOW模型训练item的分布式表示（embedding）
- 训练得到的item embedding可以捕捉item之间的共现关系，语义上相似的item在向量空间中距离更近

**Skip-gram模型：**
- 给定中心词（当前行为的item），预测其上下文窗口内的其他词（用户前后行为的item）
- 目标函数：最大化上下文词的预测概率
- 损失函数：
```
L = -Σ_{-c≤j≤c, j≠0} log P(w_{t+j} | w_t)
```

**负采样优化：**
- 全量softmax计算量太大，用负采样加速
- 对每个正样本（上下文词），从词频分布中采样若干负样本
- 损失变为二分类的logistic loss

**item2vec与Word2vec的区别：**
- Word2vec的句子是有语法结构的自然语言，词序很重要
- item2vec的"句子"是用户行为序列，item之间没有严格的语法关系，但时序关系仍然有意义（用户连续交互的item通常相关）
- item2vec通常对行为序列做一些预处理（如过滤低质量行为、按时间排序、加入时间衰减权重等）

### 9.2 微视item2vec实践

在微视行为Embedding召回项目中，item2vec的具体配置如下（来源：好友达人梳理（总））：

**训练数据：**
- 用户7天内有正向行为的达人list
- 行为类型：赞转评或完播
- 过滤：达人list长度>5且<5000

**模型参数：**
- 模型：Word2vec Skip-gram
- Embedding维度：**32维**
- 窗口大小：通常设为5
- 负采样数：默认5-10
- 训练迭代次数：通常5-10轮

**后处理：**
- 计算同一级类目下达人两两cos距离
- 每个达人保留top10相似达人
- 最大最小归一化相似度得分
- 存入HDFS，线上加载到Redis

### 9.3 一二级兴趣召回

一二级兴趣召回是基于用户兴趣标签的分层召回策略（来源：一二级兴趣召回）。

**核心思路：**
- 将用户兴趣分为一级兴趣（大类目，如游戏、美食、美妆）和二级兴趣（细分类目，如游戏下的MOBA、FPS、RPG）
- 基于用户的行为历史构建用户的一二级兴趣画像
- 按兴趣标签召回对应类目的优质达人/内容

**兴趣画像构建：**
- 统计用户在各一级/二级类目下的行为（播放、完播、点赞、评论、关注）
- 对不同行为类型加权（关注>评论>点赞>完播>播放）
- 加入时间衰减，近期行为权重更高
- 取topN兴趣标签作为用户的兴趣画像

**召回策略：**
- **一级兴趣召回**：基于用户top一级兴趣，召回该类目下的热门/优质达人。覆盖面广，保证基本的相关性
- **二级兴趣召回**：基于用户top二级兴趣，召回更细分的类目达人。更精准，覆盖率较低
- 一二级兴趣召回可以按比例混合，在准确性和覆盖率之间折中

**在微视的应用：**
- 用户画像cat1达人召回（ID 13003）：根据用户一级兴趣画像匹配所属类别的达人（来源：好友达人梳理（总））
- 外部画像召回（ID 14998）：基于外部画像一级类目召回热门达人
- 分人群热度召回（ID 14111）：基于用户性别、年龄、地域分组，结合类目满意度召回

### 9.4 兴趣探索boost与搜索承接优化

这是我在微视做的另一个重要优化方向（来源：关注作者兴趣&兴趣探索boost&搜索承接优化），核心是解决三个问题：

**问题一：搜索行为在推荐页没有承接**
- 现状：query到tag的全匹配映射，匹配过于粗暴，匹配程度低
- 优化方案：
  1. 接入query召回接口（包括query改写、分词等召回方式）
  2. query到tag的模型预测，结果写入session供匹配召回
  3. 将query全匹配改成模糊匹配召回（当前可直接优化）
  4. 基于query切词的tag全匹配召回（当前可直接优化）

**问题二：有关注作者行为但推荐页感知低**
- 原因：关注时间久远，当关注作者发文量低时，推荐页行为无法累积导致无法推出相关内容
- 优化方案：
  1. 建立基于用户关注作者的兴趣画像计算，并建立召回通路
  2. 对于关注作者发文量低或画像推荐太少的问题，建立关注作者画像的兴趣探索——关注作者垂类进行boost，对于太久之前关注导致之后没出的行为采用强插逻辑进行试探
  3. 基于喜欢作者画像召回相似作者发文视频（线上已有，可做boost逻辑提高关注率）

**问题三：兴趣探索频率过低**
- 现状：采用末尾强插逻辑，只插入一位导致其他可能的兴趣点无法得到有效曝光
- 优化方案：
  1. 将当前的低频兴趣探索、随机兴趣探索逻辑下沉至boost
  2. 保留搜索、外部画像、热点承接的强插逻辑
  3. 老用户低频兴趣boost（提权幅度依据汤姆森采样得分计算）
  4. 新用户随机探索boost

**作者账号垂直度计算：**
为了支持关注作者兴趣画像，需要计算作者账号的垂直度：
- **分类垂直度**：统计作者发文量、不同分类下发文量、发文类目个数；计算最多分类视频个数占比；计算发文类目的纯度（信息熵）
- **标签垂直度**：类似分类垂直度，计算topN标签，去除质量类标签和无关兴趣标签
- 数据格式：(personid, 是否达人, 发文数量, 最高类目发文数量, 作者发文类目个数, 最高类目, 纯度(信息熵), 最多类目视频个数占比)

**基于用户关注的兴趣画像计算：**
- 根据作者分类垂直度进行统计（限制发文数量、纯度、最高类目占比满足条件）
- 以用户为角度统计关注作者的垂直度画像
- 按照关注作者垂直度类别数量排序，计算相应类目的历史播放完整度作为参考指标

> **面试口述版：**
> "item2vec是我在微视行为Embedding召回项目的核心技术。简单说就是把用户7天内的正向行为序列当作句子，达人ID当作词，用Skip-gram训练32维embedding。这个方法简单有效，训练出来的达人embedding可以捕捉行为共现的语义关系。除了item2vec，我还做了一二级兴趣召回和兴趣探索优化。一二级兴趣召回是基于用户的兴趣画像分层召回——一级兴趣保证覆盖面，二级兴趣保证精准度。兴趣探索优化是我觉得比较有价值的工作，主要解决三个问题：一是搜索行为在推荐页没有承接，我们把query到tag的全匹配改成模糊匹配和切词匹配，还接入了query召回接口；二是用户有关注作者但推荐页感知低，因为关注时间久或作者发文少，我们建立了关注作者的兴趣画像召回通路，并对关注作者垂类做boost，太久没出的用强插试探；三是兴趣探索频率太低，原来只在末尾强插一个，我们把低频探索下沉到boost，提权幅度用汤姆森采样计算，新用户用随机探索boost。"

**Q：item2vec的窗口大小怎么选？太大太小有什么影响？**
A：窗口大小决定了item2vec在多大范围内捕捉item之间的共现关系。窗口太小（如1-2），只能捕捉紧邻行为的item关系，学到的是非常短期的兴趣切换；窗口太大（如20+），会把用户在较长时间内的所有行为都当作上下文，可能引入不相关的item（用户兴趣可能已经变化），同时计算量也会增大。在微视达人embedding训练中，我们用的窗口大小是5左右，因为用户连续关注/互动的5个达人通常有较强的兴趣关联。实际选择需要根据用户行为序列的平均长度和兴趣变化频率来调，通常在3-10之间。

- 识别对电影内容有兴趣的用户（基于播放、完播、互动行为）
- 构建影评人池（认证影评人、电影领域高活跃创作者）
- 基于CF或Embedding方法为电影兴趣用户推荐影评人
- 可以结合电影内容的语义匹配（用户喜欢的电影类型 vs 影评人擅长的影评类型）

**垂类召回的通用方法论：**
1. **垂类识别**：通过内容标签、人工审核、模型分类等方式识别item的垂类属性
2. **用户垂类兴趣建模**：统计用户在各垂类下的行为，构建垂类兴趣画像
3. **垂类达人池构建**：筛选各垂类下的优质创作者
4. **垂类内召回**：在垂类达人池内用CF/Embedding/热门等方法召回
5. **垂类间混合**：根据用户多兴趣权重，混合多个垂类的召回结果

> **面试口述版：**
> "达人召回和好友召回是我在微视账号推荐的两大核心方向。达人召回我维护了十几路召回，包括热门兜底、分人群热度、个性化CF、行为Embedding、互动行为召回、实时关注等，每一路有明确的召回ID和分层quota——关系链层占50%，行为层占30%，画像层占20%。其中行为Embedding召回是我从0到1做的，用Word2vec训练32维达人emb，基于用户最近10个关注达人召回100个相似达人。达人池从SA级切换到45级后，关注率提升了5.3%。好友召回则充分利用了腾讯的社交关系链优势，一度好友基于QQ/微信/通讯录/红包关系merge按共同好友数倒排，二度好友离线计算覆盖约5000万用户，还有实时一二度召回。排序侧老用户用LR模型，特征包括用户画像、行为统计、关系链交叉特征三大类。另外我还探索了影评人这类垂类召回，核心思路是先做垂类识别和用户垂类兴趣建模，然后在垂类达人池内做个性化召回。"

**Q：好友推荐和达人推荐在召回策略上有什么本质区别？**
A：好友推荐的核心是**社交关系链**，信号来源是用户的真实社交关系（QQ/微信/通讯录/红包），召回逻辑是基于共同好友数的关系链扩展，目标是帮用户找到现实中认识但还没在微视关注的人。达人推荐的核心是**内容兴趣**，信号来源是用户的内容消费行为（播放/完播/互动/关注），召回逻辑是基于兴趣相似度的内容匹配（CF/Embedding/兴趣画像），目标是帮用户发现可能感兴趣的内容创作者。在微视的混排策略中，我们会计算用户对达人还是好友更感兴趣，决定谁在前面，返回数量平分。两者的召回源、特征、排序模型都是分开的，最后在重排层混合。

## 十一、召回方向现状与优化方案

### 11.1 百亿量级SIMNET模型规划

SIMNET是我在搜索推荐召回方向规划的百亿量级语义匹配模型（来源：百亿量级SIMNET模型规划），目标是作为高级特征输出到下游模型，提升线上效果。

**模型目标：**
- 海量点击曝光的弱监督语义模型，在编码方式、表示方式和交互方式上做精进
- 对比tiny-bert（词表2w），SIMNET支持**500w大小词表**（basic/phrase/bigram）
- 可以替换线上较硬的统计特征（如bi-lstm），提升特征值覆盖率到100%
- 具备海量数据&稠密模型训练能力

**训练目标设定：**
- 样本量：**100亿**
- 词表：百万级
- 更新周期：每月
- 编码：basic/phrase/bigram/BPE
- 表示：CNN/BOW
- 匹配：COS/MLP
- 特征：增加匹配类特征（相关性中的非语义类特征）
- 多域：title/click-query/Content

**训练效率（GPU单卡V100）：**
- 标准BOW-DSSM：1亿训练数据**30分钟**内过一个epoch（1层FC hiddim=128，100w词表dim=128，cos交互，margin loss，Adam）
- 标准CNN-DSSM（100w词表）：1亿数据**90分钟**内过一个epoch（kernel [3,4,5]*64，cos交互，margin loss，Adam）
- 标准CNN-DSSM（500w词表）：1亿数据90分钟内过一个epoch（SGD optimizer）

**工程优化手段：**
- 混合精度训练
- 数据prefetch
- OP算子融合
- 超大batch收敛（LAMB优化器），待验证

**训练数据生成：**
- pair-wise点曝数据
- 训练集：打底资源，以最后一个点击title和这个点击index之上的所有title进行组pair
- 测试集：另一天数据（50W）
- 数据规模：一天数据量约5-6000万，落盘后tfrecord 50GB，100天数据约5TB

**模型结构（pair-wise CDSSM）：**
- basic侧：windows=[3,4,5]，kernel_size=64的CNN网络
- phrase侧：BOW网络（后改为CNN）
- loss：margin loss，basic和phrase分别计算后相加：loss = loss_phrase + loss_basic
- 另一种方案：多编码特征上层concat，q_emb=concat([b_q,p_q])，t_emb=concat([b_t,p_t])，交互层点乘/cos

**离线实验结果：**
- version-1：单模型在0601点爆测试数据上正逆率**1.57**
  - 在混排CTR模型中，绝对值正逆序提升千分之**8**，相对值千分之**3**
  - 特征重要度按分裂个数排第**7**，按增益排第**14**
- version-2：用w2v初始化词表（高频25W用中文词向量初始化，其余25W随机），正逆率提升到**1.60**
- version-3：调研WWW2020论文，持续优化

### 11.2 语义相关性模型具体打法

语义相关性模型是搜索推荐召回的核心能力之一，应用于相关性、语义召回、精准问答、query改写等多个环节（来源：语义相关性模型具体打法）。

**中台语义模型现状：**
- 应用于应用宝、腾讯视频、腾讯看点、腾讯新闻等PCG产品线

### 11.3 搜索承接优化

搜索承接是连接搜索行为和推荐召回的重要环节（来源：关注作者兴趣&兴趣探索boost&搜索承接优化、搜索推荐召回方向现状及优化方案）。

**核心问题：**
- 用户有搜索行为，但推荐页没有有效承接，搜索兴趣无法转化为推荐召回
- 现状是query到tag的全匹配映射，匹配过于粗暴，匹配程度低

**优化方案：**
1. **接入query召回接口**：包括query改写、分词等召回方式
2. **query到tag的模型预测**：用模型预测query对应的tag，结果写入session供匹配召回
3. **全匹配改模糊匹配**：将query的全匹配改成模糊匹配召回，提升覆盖率
4. **基于query切词的tag全匹配**：先对query切词，再用切词结果做tag全匹配，比直接全匹配更灵活

**语义召回在搜索中的应用：**
- 语义相关性模型用于搜索结果的相关性打分
- tinybert语义模型作用于排序的final_score（队列机制+相关性打分+ctr打分）
- tinybert2.0目标：点击曝光样本正逆序达到1.5，auc至少提升2个千分点
- 优化tinybert在相关性数据集上的效果，推动在相关性模型上线

**Q：SIMNET和DSSM是什么关系？SIMNET的创新点在哪里？**

### 12.2 高频Q&A

**Q：你做过哪些召回方法？分别解决什么问题？**

A：我在微视做过的召回方法可以分为几类：
1. **基于关系链的召回**：一度/二度好友召回，解决"找到用户现实中认识的人"的问题，基于共同好友数倒排，是好友推荐的主力
2. **基于协同过滤的召回**：达人CF召回，解决"和你关注了相似达人的人还关注了什么"的问题，用共现相似度，加入了类目加权和流行度惩罚
3. **基于Embedding的召回**：行为Embedding（item2vec）和graph Embedding，解决"基于用户行为序列学习兴趣表示"的问题，用Word2vec/DeepWalk训练达人embedding，ANN检索
4. **基于兴趣画像的召回**：一二级兴趣召回、分人群热度召回，解决"基于用户长期兴趣标签召回"的问题
5. **基于深度语义匹配的召回**：DSSM双塔/SIMNET，解决"user和item的深度语义匹配"问题，用pair-wise margin loss训练
6. **基于强化学习的召回**：TopK集合召回，解决"一次性推荐多个item时的集合整体优化"问题，用REINFORCE策略梯度
7. **垂类召回**：影评人召回等，解决特定垂类的专业创作者发现问题

每一路召回解决不同维度的问题，最后合并去重交给排序层，这就是多路召回的核心思想——用不同信号源互补，保证召回的"全"和"准"。

**Q：DSSM和TDM怎么选？**

A：选择取决于item库规模和工程资源：
- **DSSM双塔**适合百万到千万级item库，优势是结构简单、训练部署成熟、user塔和item塔独立可预计算、ANN检索延迟极低（毫秒级）。缺点是user和item的交互只有最后一层余弦，表达能力受限，超大规模（亿级）item的ANN索引维护成本高。
- **TDM**适合亿级以上超大规模item库，优势是检索复杂度O(logN)、每层都有深度非线性交互表达能力更强、树结构天然有层次化兴趣聚类。缺点是树结构构建维护复杂、beam search可能漏最优解、训练需要逐层监督工程复杂度高、树更新需要重新训练。

在微视百万级达人池的场景下，DSSM+ANN已经足够且工程更简单，TDM更多是作为达人池扩大后的技术储备。如果item库到了亿级（如全量视频库），且有足够工程资源维护树结构，TDM会更有优势。另外两者也可以结合——用DSSM的item embedding做层次聚类构建TDM的树结构。

**Q：召回怎么评估？离线和线上分别看什么指标？**

A：召回的评估分离线和线上两层：

**离线指标：**
- **召回率（Recall）**：最核心的指标，用户实际交互的item中有多少被召回命中。通常按召回topK（如Recall@500）计算
- **命中率（Hit Rate）**：有多少用户的召回结果包含了其后续交互的item
- **覆盖率（Coverage）**：召回结果覆盖的item占全库比例，衡量多样性
- **NDCG@K**：召回结果的排序质量
- **正逆率**：语义模型中，正样本得分高于负样本的比例（如SIMNET的1.57/1.60）

**线上指标：**
- **pCTR/uCTR**：人均点击率和用户点击率，召回候选集经过排序后的最终点击效果
- **关注率**：账号推荐场景的核心业务指标
- **VV占比**：各召回源贡献的播放量占比，评估每路召回的业务贡献
- **人均交互个数**：如应用宝场景的人均下载个数（TopK RL召回提升20%）

**评估时的注意点：**
- 离线召回率高不代表线上效果好，因为召回只是第一道漏斗，最终效果还取决于排序
- 要分场景评估，不同场景（关注页/发现页/消息页）的用户行为模式不同，同一召回源在不同场景效果可能差异很大
- 要做消融实验，逐路召回下线看效果下降，评估每路召回的边际贡献
- 关注召回的延迟和资源消耗，效果好但延迟超标的召回不能上线

**Q：负采样在召回训练中有什么作用？你是怎么做的？**

A：负采样是召回训练（尤其是DSSM、YouTube DNN这类匹配模型）中最关键的环节之一，决定了模型学习的决策边界。

**作用：**
- 全量softmax或全量负样本计算量太大，负采样大幅降低计算复杂度
- 负样本的质量直接决定模型能学到多精细的匹配边界——负样本太简单模型学不到东西，太难以致不收敛

**我在微视的做法：**
1. **曝光未点击负采样**：最主要的负样本来源，将曝光给用户但未点击/未关注的item作为负样本，最贴近真实分布
2. **随机负采样**：从全量item库中按流行度加权采样（热门item更容易被采为负样本），保证负样本的多样性
3. **Hard Negative**：从同类目下或当前模型的topK结果中采样难负样本，提升模型对相似item的区分度
4. **混合策略**：通常是曝光未点击+随机采样混合，正负比1:5到1:10

**在达人CF中**，负样本的概念不太一样——CF是基于共现矩阵的无监督方法，不需要显式负采样，但通过公式中的流行度惩罚（log(粉丝数)做分母）间接实现了"热门item更难获得高相似度"的效果。

**Q：多路召回怎么融合？每路召回的数量怎么定？**

A：多路召回的融合是召回系统的核心工程问题。在微视账号推荐中，我们采用**分层quota+统一排序**的方式：

**分层策略：**
- 将召回源按优先级分为多层：第1层（关系链召回，如一度/二度好友）、第2层（行为召回，如Embedding/CF/实时关注）、第3层（画像/热门召回）
- 每层分配固定的quota比例：0.5:0.3:0.2（第1层50%，第2层30%，第3层20%）
- 同层内的多路召回按配置顺序填充，先到先得
- 配置格式：layer_policy=1:13010@13008@13007@13001@13004;2:13804@14113@13996@13801;3:14998@13997@14111

**统一排序：**
- 所有召回源的候选合并去重后，交给统一的排序模型（LR/DNN）打分排序
- 排序模型不关心候选来自哪一路召回，只根据user-item特征打分
- 这样每路召回的"质量"最终体现在排序后的位置上

**quota确定的方法：**
- 初始时根据经验设定（关系链召回质量最高所以占比最大）
- 通过AB实验调整：增加某层quota看效果变化，找到最优比例
- 做消融实验：下线某路召回看效果下降，评估其边际贡献
- 分场景设定：不同场景（关注页/发现页/消息页）的最优quota可能不同

**重排层的额外处理：**
- 类目打散：同类目item间隔出现，限制同类目最大数量
- 曝光降权：高频曝光未点击的item降权
- 多样性保证：E&E策略（Thompson Sampling）探索新类目

**Q：新用户冷启动召回怎么做？**

A：新用户冷启动是召回的经典难题。在微视账号推荐中，我们的做法：

**好友方向：**
- 新用户实时一度/二度好友召回：依赖实时关系链获取接口，新用户授权后立即获取QQ/微信/通讯录关系，在线计算候选
- 新用户好友规则排序：score = 0.7×共同好友得分 + 0.3×活跃得分，不用模型排序因为新用户特征不足

**达人方向：**
- 热门达人兜底：人工筛选的200个优质达人，保证基本推荐质量
- 分人群热度召回：基于新用户注册时的性别、年龄、地域信息，召回对应人群的热门达人
- 外部画像召回：如果有外部数据（如应用安装列表），基于外部画像召回
- 新用户随机探索boost：在推荐中加入随机探索，快速收集行为数据

**快速兴趣建模：**
- 新用户前几次交互的权重很高，实时更新兴趣画像
- 实时关注召回：捕捉新用户的第一次关注行为，立即反馈到召回
- 一旦新用户积累了5个以上正向行为，就可以启用行为Embedding召回

**核心思路**：冷启动阶段用非个性化召回（热门/分人群热度）保证基本质量，用社交关系链（如果有授权）做个性化，同时通过探索策略快速收集行为数据，逐步过渡到个性化召回。

**Q：召回的延迟怎么优化？**

A：召回延迟是线上服务的核心指标，通常要求单次请求总延迟在10-20ms以内。优化手段：

**1. 离线预计算：**
- item embedding批量离线计算，存入向量数据库或Redis，线上只查不计算
- CF相似度矩阵离线计算，线上只做查表
- 热门榜单、分人群热度等离线预计算

**2. ANN检索优化：**
- 选择合适的索引结构：IVF（倒排聚类）适合高吞吐，HNSW（图索引）适合高精度低延迟
- 向量压缩：PQ（乘积量化）压缩向量存储，减少内存和计算
- 调整nprobe/efSearch参数：在精度和延迟间折中
- 批量查询：多个user embedding合并查询

**3. 多路召回并行：**
- 多路召回源并行调用，而不是串行
- 用线程池/协程实现并发，总延迟取决于最慢的一路
- 设置每路召回的超时时间，慢的路直接降级或跳过

**4. 缓存：**
- 用户embedding缓存：用户短时间内多次请求复用embedding
- 热门召回结果缓存：热门item的召回结果变化慢，可以缓存
- Redis集群：高频访问的召回结果存Redis

**5. 增量更新：**
- 不需要每次全量更新召回索引，只更新有变化的部分
- 新item先挂到最近的簇/叶子节点，定期全量重建

在微视的实践中，行为Embedding召回的item相似关系是离线计算好存在Redis中的，线上只需要查用户最近关注的10个达人各自的top10相似达人，纯查表操作，延迟在2ms以内。DSSM的ANN检索用FAISS IVF+PQ，百万级item单次检索5ms以内。

**Q：你觉得召回未来的发展方向是什么？**

A：基于我在微视的实践和对业界的观察，召回方向有几个发展趋势：

1. **从单塔匹配到多兴趣建模**：传统DSSM用一个user embedding表示用户的所有兴趣，但用户通常有多个兴趣。未来会用多兴趣embedding（如MIND模型的胶囊网络多兴趣提取），每个兴趣embedding分别召回，提升召回的多样性和覆盖率。语义相关性模型中也提到了用胶囊网络解决长标题多向量表示问题。

2. **从即时反馈到长期价值优化**：传统召回优化点击率/关注率等即时反馈，但忽略了用户长期留存和生态健康。强化学习召回（如我们做的TopK集合召回）可以优化长期回报，未来会在更多场景落地。Actor-Critic架构、逆强化学习（自动学习奖赏函数）是重要方向。

3. **从行为信号到多模态语义融合**：传统召回主要利用行为共现信号（CF/Embedding），未来会更多融合内容的多模态语义（文本/图像/音频），尤其是在冷启动和内容理解场景。SIMNET这类大规模语义模型就是这个方向的探索。

4. **从固定召回到端到端召回排序联合优化**：目前召回和排序是分开优化的，召回优化召回率、排序优化CTR，但两者的目标不完全一致。未来会有更多召回排序联合优化的工作，比如用排序模型的梯度指导召回，或者端到端训练。

5. **超大规模检索的工程创新**：随着item库增长到亿级甚至百亿级，ANN检索的工程挑战越来越大。TDM树匹配、向量数据库的分布式架构、GPU加速检索等是重要方向。

6. **可解释性和公平性**：召回的"为什么推荐这个"越来越重要，尤其是在账号推荐中，推荐理由（"因为你关注了A"）可以提升用户信任。同时要保证召回的公平性，避免头部item垄断曝光。

> **面试最后总结：**
> "召回是推荐系统的第一道漏斗，也是我在微视四年投入最多的方向。我的核心经验是：第一，多路召回是工业界的必然选择，没有任何单路召回能覆盖所有用户兴趣，关键是每路召回的信号源要清晰、互补；第二，Embedding召回是从传统统计召回（CF）到深度召回（DSSM）的桥梁，item2vec简单但极其有效，graph Embedding能捕捉结构信号；第三，召回的评估不能只看离线召回率，必须通过线上AB实验验证最终业务指标，而且要做消融实验评估每路召回的边际贡献；第四，工程能力和算法能力同等重要——延迟、缓存、增量更新这些工程细节直接决定了一个召回方法能不能上线。我从行为Embedding召回的0到1，到graph Embedding的效果提升，再到DSSM双塔和强化学习召回的技术探索，对召回的全链路有比较深入的理解和实践。"
