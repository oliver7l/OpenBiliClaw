# 一、推荐系统全景架构

## 1.1 链路总览：召回→粗排→精排→重排

我在腾讯做推荐系统时，完整的推荐链路是一个**漏斗式多级筛选**架构，每一层承担不同的计算复杂度和精度目标：

| 层级 | 输入规模 | 核心目标 | 计算特点 | 典型延迟预算 |
|------|---------|---------|---------|------------|
| **召回（Recall）** | 全库百万~亿级 | 从海量内容中快速捞回相关候选集，保证"不漏" | 多路并行、轻量模型/索引、近似搜索 | 几十ms级 |
| **粗排（Pre-rank）** | 召回候选千~万级 | 对候选集做初步排序，截断到百级，平衡精度与效率 | 轻量模型（如LightGBM、简单DNN）、特征精简 | 几十ms级 |
| **精排（Rank）** | 粗排截断百级 | 精准预估用户对每个item的多目标概率（CTR/CVR/时长/留存），输出最终排序分 | 复杂深度模型（DLRM/WDL等）、全量特征、多任务 | 百ms级 |
| **重排（Re-rank）** | 精排TopN | 结合业务规则、多样性、时效性、干预策略做最终调整，保证"体验好" | 规则+模型混合、队列PK、去重、位置干预 | 十几ms级 |

**核心方法论**：每一层的设计原则是**"上一层保证召回率，下一层保证准确率"**，用计算复杂度换精度，用漏斗结构控制整体延迟。召回层追求"全"，精排层追求"准"，重排层追求"体验"。

> **面试口述版**：我在腾讯微视和QQ看点做推荐时，系统是标准的召回-粗排-精排-重排四级漏斗。召回层从全库内容中通过多路并行召回（CB、CF、语义、热点等）捞回几千候选；粗排用轻量模型截断到几百；精排用DLRM等深度模型做CTR/CVR/时长/留存多目标预估；重排做队列PK、去重、多样性和业务干预。每一层的核心是用计算复杂度换精度，同时严格控制延迟预算。

## 1.2 各层职责与交互详解

### 召回层

召回层是推荐系统的"入口"，决定了后续所有排序的候选空间。我在实际工作中，召回策略分为三大类：

**CB类（Content-based，基于内容）**：
- 基于用户兴趣标签（tag）、主题（subject）、概念（concept）、事件（event）做内容匹配
- 热点召回（HOT-SUB、HOT-tag）：在兴趣个性化基础上叠加热度值
- 关注召回：用户关注账号的内容
- 本地召回：按省市区对内容建索引
- 群体召回：冷启动、女性、老年等特定人群
- SF短期兴趣跟随：从用户最近点击产生的兴趣中召回内容

**CF类（协同过滤）**：
- UCF（UserCF）：每天离线计算相似用户，推荐邻居喜欢的内容
- ICF（ItemCF）：准实时计算内容"邻居"，推荐行为相似的内容
- 好友在读（FRIEND）：社交关系链召回

**其他类**：
- 探索召回：基于知识图谱的兴趣泛化（A→关系→B）
- 语义索引：用户向量化+内容向量化，找最相似内容向量（本质上更偏排序）
- HighQuality打底：人审+少量FT内容，个性化弱但保证第一印象

**关键设计**：CB召回后会内部调用UM（用户模型）先做一次排序，再将Top结果返回给粗排，这个能力已封装为可复用模块，供其他各种召回复用（来源：QBfeeds推荐系统现状.txt）。

### 粗排层

粗排层在召回候选集上做初步排序，核心是**"快"**。在搜索推荐场景中，粗排通过队列机制实现：

- **QueueCalProcess**：计算每个资源在各维度队列的分值（整体后置、后置队列、品类优先队列、匹配队列、时效队列、tag队列、账号队列、资源质量队列、综合队列）
- **QueuePkTopKProcess**：按队列排序取TopK，资源内排序（核心词命中>相关性分档>时效性分档）+资源间PK混排（综合队列打分>粗排打分）（来源：整体梳理.txt）

### 精排层

精排层是整个推荐系统的"大脑"，核心是多目标模型预估：

- **ModelProcess**：获取全部模型打分——CTR（点击模型）、LTR（学习排序模型）、Rele（相关性模型）、CVR（视频转化模型）等，供综合排序使用（来源：整体梳理.txt）
- 模型类型包括：WDL（Wide & Deep）、DLRM（深度学习推荐模型）、LightGBM（冷启动点击预测）、DSSM（深度语义匹配）、Tiny-BERT（高级语义特征）等（来源：架构现状.txt）

### 重排层

重排层是"最后一公里"，核心是**业务体验**：

1. **过滤**：ReleFilterProcess（相关性过滤）、CvrFilterProcess（CVR过滤/跨队列后置）、CtrFilterProcess（CTR过滤/跨队列后置）、LowQuaResProcess（低质过滤：反黄、低质、视频封面低质）
2. **捞回**：ResComplementProcess——当过滤资源太多时，按相关性模型打分进行资源捞回，保证返回数量
3. **去重**：ResSourceDeduplication（来源去重，企鹅号资源优先）、DeduplicationProcess（内容理解id重复+标题完全重复）
4. **干预**：InterventionProcess（CTR打分干预：领域意图/资源意图/指定账号/指定aid/指定资源类型/评论数）、AladdinClickAdjustProcess（阿拉丁TopN保护）、RegexPosnProcess（正则位置干预）
5. **混排**：QueuePkProcess（打底资源内部排序后PK）、AladdinSortProcess（阿拉丁资源与打底资源根据点击模型混排，混排后打底恢复原本相对顺序）
6. **特殊重排**：SpecialReSortProcess（资讯短视频聚合卡特殊重排）

（来源：整体梳理.txt）

## 1.3 推荐系统衡量指标体系

一个推荐系统做得好不好，需要从**平台、用户、CP**三方利益相关方角度衡量：

| 维度 | 指标类别 | 具体指标 |
|------|---------|---------|
| **平台指标** | 规模指标 | PV、VV |
| | 推荐能力 | 曝光效率、CTR |
| | 生态健康 | 覆盖率（unique URL分发能力、被推荐商品占比、信息熵、基尼系数）、新物品推荐能力 |
| | 商业目标 | 信息流推荐AB实验不应对商业目标产生明显损害 |
| **用户指标** | 消费类 | UV转化率、人均曝光、人均消费、时长 |
| | 健康度 | 留存率 |
| | 时效性 | 全局热点/垂类热点/本地热点推荐能力 |
| | 技术指标 | 预测准确度（测试集AUC/GAUC） |
| | 多样性 | 分主题分刷数曝光分布、探索占比 |
| | 满意度 | 用户调研 |
| **CP指标** | 生产能力 | 垂类品类下总生产能力 |

**关键数据**：
- QB推荐系统每天能分发的内容约**20万**，明显高于看点的**6万左右**（来源：QBfeeds推荐系统现状.txt）
- QB多样性现状：探索图文占比**8%**，探索视频占比**4%**，探索整体占比**5%左右**（来源：QBfeeds推荐系统现状.txt）
- 新物品保护机制：图文在展控层对新item有保护；短小视频在粗排层有加权（发布的**12小时**时间窗&曝光阈值内）；小视频会拿出一部分流量用来预曝光（来源：QBfeeds推荐系统现状.txt）

> **面试口述版**：衡量推荐系统我会从三方视角看。平台侧看规模、CTR、覆盖率和生态健康，我们当时每天分发约20万内容，覆盖率用unique URL数衡量；用户侧看消费指标、留存、时效性和多样性，我们探索内容整体占比约5%；CP侧看生产能力。新物品保护是生态健康的关键，图文在展控层保护，短视频在粗排层做12小时时间窗加权，小视频还会专门拿流量预曝光。

# 二、精探架构详解

## 2.1 精探是什么

"精探"是我在腾讯参与的**精准搜索词推荐服务**，主要应用于QQ浏览器（QB）的搜索场景——当用户在搜索框输入或在正文底部、feeds流等场景时，系统推荐相关的搜索词（query），引导用户进一步搜索。

精探架构分为**在线服务**和**离线处理**两大部分（来源：精探架构.txt）。

## 2.2 在线服务架构

在线服务的处理流程为：

1. **预处理（Preprocess）**：接收请求，获取文章信息、用户画像等上下文
2. **召回（Recall）**：多路并行召回候选搜索词
3. **排序（Sort）**：对召回候选词进行CTR预估和排序
4. **后处理（Post-process）**：质量过滤、相关性过滤、去重等
5. **无量流程**：兜底/降级处理

### 召回渠道详解

精探的召回是**多路并行**架构，共8路召回，每路在日志样本中有独立代号：

| 召回渠道 | 日志代号 | 类型 | 说明 |
|---------|---------|------|------|
| 文章tag召回 | recallByE2q | 标签召回 | 基于文章标签匹配搜索词 |
| 文章分类召回高点击词 | recallByHot | 统计召回 | 从点击日志挖掘分类高点击词 |
| 文章分类召回补位词 | recallByReview | 补位召回 | 其他词填不满位置时用来补位，也参与常规排序 |
| 文章句子级语义召回 | recallByNlp | 语义召回 | NLP句子级语义匹配 |
| 文章篇章级语义召回 | recallByNlpSeman | 语义召回 | 篇章级语义匹配 |
| 文章-词相似性召回 | recallByDocSim | 语义召回 | 文档与词的相似性计算 |
| 知识图谱召回 | recallByAssoWord | 语义召回 | 基于知识图谱关联词 |
| 文章概念召回 | recallByConcept | 语义召回 | 基于文章概念匹配 |

（来源：精探架构.txt）

**方法论提炼**：多路召回的设计原则是**"不同召回路覆盖不同语义空间"**——tag召回保证精准匹配，高点击词保证热度，语义召回保证泛化能力，补位词保证返回数量。各路召回后合并去重，统一进入排序阶段。

## 2.3 离线处理

离线处理负责：
- 倒排索引构建（tag倒排、分类高点击词统计等）
- 语义模型训练（句子级/篇章级语义向量）
- 知识图谱构建与更新
- 样本生成与模型训练（CTR模型）

## 2.4 精探监控体系

精探服务的监控分为一级和二级指标：

**一级监控指标**（业务核心）：

| 指标 | 说明 |
|------|------|
| getRecommQuery.%.success | 有返回数（成功率） |
| getRecommQuery.%.impression | 平均返回词数 |
| getRecommQuery.%.ctr | 平均PCTR |
| getRecommQuery.%.RecallProcessor.recall | 平均召回词数 |

**二级监控指标**（模块级）：

| 指标 | 说明 |
|------|------|
| DocumentProcessor/DocumentProfileProcessor.success | 获取文章信息成功率（旧/新） |
| RelationMapping.success | 文章主题映射成功率 |
| tag.success | IR倒排召回成功率 |
| CtrProcessor/NumerousProcess.success | CTR预估成功率（旧/无量） |
| QualityProcessor.success | 质量服务成功率 |
| RelevanceProcessor.success | 相关性服务成功率 |
| tag.recall | IR平均召回词数 |
| QualityProcessor.pass | 质量过滤通过率 |
| RelevanceProcessor.pass | 相关性过滤通过率 |

（来源：系统稳定性监控梳理.txt）

> **面试口述版**：精探是我在QB做的精准搜索词推荐服务，架构分在线和离线。在线是预处理→多路召回→排序→后处理的pipeline，召回有8路并行，包括tag召回、高点击词、补位词、句子级/篇章级语义召回、文档相似性、知识图谱和概念召回。离线负责倒排索引、语义模型和CTR模型训练。监控上分一级业务指标（成功率、返回词数、PCTR、召回词数）和二级模块指标（各下游服务成功率、过滤通过率等）。

# 三、微视/QQ看点工程架构

## 3.1 服务拆分总览

我在腾讯参与的推荐/广告系统采用**微服务架构**，按功能职责拆分为独立服务，通过TAF（腾讯内部RPC框架）/HTTP进行通信。以UG（用户增长）广告推荐系统为例，主要功能模块如下：

| 服务 | 功能 | 代码服务名 |
|------|------|-----------|
| **广告接入服务** | TAF协议接入 | BUSIUgProxyServer |
| | HTTP协议接入 | BUSIUgAccessNodeServer |
| **中控服务** | 调用下游服务，实现画像获取、召回广告、广告过滤、广告排序及策略干预 | BUSIUgHubServer |
| **广告代理服务** | 构造广告请求、调用广告主接口、处理广告回包（组UI） | BUSIUgExProxyServer |
| **排序服务** | 对商业资源进行排序 | BUSIUgRankServer |
| **预估服务** | 对广告进行预估打分 | AdsPredictServer（旧，即将废弃）/ BUSIUgPredictInfoServer（新） |
| **相关性服务** | 对广告进行相关性打分 | UgCorrelationPredictServer（旧）/ albert_attention（新） |
| **商业统计服务** | 数据统计 | BUSIUgStatServer |
| **公共库** | 通用工具库 | UgComm |

（来源：工程架构.txt）

**设计方法论**：
1. **接入层与业务层分离**：TAF和HTTP两种接入协议独立服务，下游业务逻辑统一
2. **中控模式**：HubServer作为核心调度，串联画像→召回→过滤→排序全链路，策略干预集中管理
3. **新旧服务并行**：预估服务和相关性服务都有新旧版本并行，逐步迁移，保证线上稳定性
4. **公共库下沉**：通用能力（特征处理、工具函数）下沉到UgComm公共库，避免重复开发

## 3.3 特征存储与获取

特征获取采用**代理模式**：
- **特征代理服务（FeatureProxy）**作为统一入口，上游排序服务只调用特征代理，由代理负责路由到各具体特征服务
- 特征分为：公共特征、文本特征、CTR实时特征、CVR特征、相关性特征、Query侧特征、高级语义特征（DSSM/Tiny-BERT）
- 实时特征通过**FeatureReportServer**（实时上报）+**FeatureComputeServer**（实时累积）链路维护

**存在的优化点**（来源：架构现状.txt）：
1. 通过模型代理接用任意模型时，都会先调用全部特征并传给下游预测服务，下游预测服务按需筛选，**存在资源浪费**
2. 分片没有完全起到"请求条数增加、耗时几乎不变"的效果

> **面试口述版**：我们的工程架构是典型的微服务拆分。接入层分TAF和HTTP两种协议，中控服务HubServer串联画像获取→召回→过滤→排序全链路。排序服务下游通过模型代理和特征代理统一调用，模型服务包括CTR、LTR、WDL、相关性、CVR等，特征服务包括公共特征、文本特征、实时CTR/CVR特征、DSSM/Tiny-BERT高级语义特征。当时我们也发现模型代理存在"全量特征下发、下游按需筛选"的资源浪费问题，这是后续优化方向。

# 四、信息流搜索推荐服务重构

## 4.1 重构背景

我在腾讯参与了信息流搜索推荐服务的重构项目。重构前的痛点是：

- 信息流搜索推荐同时支持**QQ浏览器、手机QQ看点、看点快报**3个应用
- 每个应用又有多种场景：**正文底部、feeds流回退、搜索结果页、搜索结果页回退**
- 即使相同场景下，不同应用的**词库、处理流程、模型**也各不相同
- 导致日常支持维护、定位问题、升级优化的**成本很高**

（来源：信息流搜索推荐服务重构.txt）

## 4.2 重构目标

| 阶段 | 目标 | 具体内容 |
|------|------|---------|
| **短期目标** | 代码层面统一 | 所有场景共用一套代码，不同应用的相同场景主要流程相同，用分支/适配形式兼容线上现有的不同词库、业务逻辑、模型 |
| **长期目标** | 策略层面统一 | 相同场景使用同一套策略和模型，通过配置参数、模型特征适配不同应用的特殊性 |

**实施路径**：以快报的搜索词推荐代码为基础（当时快报正在实验阶段，代码由QB服务删减迁移而成，CTR模型也复用QB模型），先完成基础代码重构→替换快报服务→增加QB业务逻辑适配→切换QB流量→迁移看点流量。

## 4.3 服务架构设计

### 核心设计原则

1. **接口与业务逻辑分离**：以一套统一接口支持各应用和各场景，服务内部根据不同场景分开处理流程。好处是接入新场景时尽量少开新接口，服务迁移时可复用现有接口部署新服务，减少上游对改动的感知。

2. **业务逻辑与功能模块分离**：功能模块与业务逻辑解耦，语义召回、质量过滤等作为功能模块提供独立可重用的功能，针对特定场景的需求可以简单组合任意功能模块，再加上少量特定开发。

### 部署策略

- **代码统一，部署分离**：多个应用和场景在代码层面统一，共用同一套代码和同一个调用接口
- 仍然**分应用部署多个服务**，原因：
  1. 现状已经是分应用部署，重构代码不希望牵涉上游调用改动
  2. 分服务部署方便监控各服务流量
  3. 隔离异常流量风险
- QB和看点已有各自不同的历史接口在线上运行，需要额外的**适配代码**把对历史接口的调用转换到新通用接口

## 4.4 控制流模式（Processor架构）

这是重构中最核心的技术设计——**基于Processor的异步控制流架构**：

### 基本概念

- 一个基本功能模块实现成一个**Processor类**，所有模块继承一个基类，实现一个通用接口
- 接口读入一个结构体参数**ProcessorParam**，该参数**既是输入也是输出**
- 功能模块的工作：从上游接收数据→对数据进行特定加工→传给下游
- 一条控制流通过特定的顺序组合这些功能模块实现特定的业务逻辑

### 异步调用的处理

推荐服务调用其他服务时通常使用**异步调用**提高性能（执行调用的线程和处理返回结果的线程不是同一个），且可同时调用多个下游服务。异步调用破坏了控制流的线性关系，调用关系表现为**依赖图**。因此：

1. 封装异步调用的功能模块需要提供**2个钩子函数**：构造异步调用 + 处理异步返回
2. 并发调用时，多个模块同时处理同一个数据结构，需要**对数据作保护**，或从代码逻辑上避免同时操作数据的相同部分

### 生命周期管理

| 对象 | 生命周期 | 用途 |
|------|---------|------|
| **Processor对象** | 进程唯一或线程唯一（取决于内部状态是否可线程间共用），**跨请求** | 存储服务内部状态（加载的数据、配置等） |
| **ProcessorParam** | 等于**一次请求的周期** | 存储单次请求数据 |

### 服务运行流程

1. **初始化阶段**：初始化所有Processor，加载数据，设置参数；服务运行过程中也可定时重载数据和参数
2. **请求处理**：接收到请求时按控制流图组装Processor，然后发起一次异步调用

### 典型请求处理代码（伪代码）

```
getRecommQuery(req, rsp):
    pParam = new ProcessorParam()
    // 文档处理
    f1 = docProcessor.process(pParam)
    // 多路召回并行
    f2 = f1.then(tagRecallProcessor.process(pParam))
    f3 = f1.then(simRecallProcessor.process(pParam))
    // 更多召回...
    // 等待所有召回完成
    f4 = whenAll(f2, f3)
    // 质量过滤和特征计算并行
    f5 = f4.then(qualityProcessor.process(pParam))
    f6 = f4.then(featureProcessor.process(pParam))
    f7 = whenAll(f5, f6)
    // CTR/CVR预估等后续流程...
```

（来源：信息流搜索推荐服务重构.txt）

### 注意事项与限制

- 一些逻辑相同的功能因初期数据结构未抽象导致重复代码（如加载各倒排索引、正文底部和feeds流回退的相关性过滤），可合并成Processor，通过初始化参数区别
- 涉及上下游服务的差异无法完全消除，例如：
  - QB正文底部的文章主题和tag是推荐服务主动从DCache获取，而快报的主题和tag是上游使用参数传下来的
  - QB正文底部和快报正文底部使用的实时曝光上报的DCache数据结构不同
- **原则**：把外部差异封装在尽量小的单元内部，向外提供一致接口，减少流程其他部分的感知。后续更好的方案是和上下游约定使用统一接口

# 五、模型训练Pipeline与线上Serving

## 5.1 数据配置化

### 背景与问题

排序侧特征实验不断增加，大家各自生成训练和测试的tfrecord，带来几个问题：
1. **存储和计算成本高**：可能只是简单增加几个特征就重新生成一份新数据，集群计算压力大
2. **互相之间对比存在差异**：处理数据时的一些差异导致对比实验不可靠

### 解决方案：数据配置化

将原来的`VideoResysDataGenerator`拆分成两个部分（代码地址：video_resys_tfdata）：

| 组件 | 职责 |
|------|------|
| **VideoResysSampleTable** | 解析特征（如解析insightdnn特征），join引擎日志表和曝光点击表，生成样本中间表 |
| **VideoResysTFRecordData** | 提供抽样、重命名、过滤等逻辑，配置化生成训练和测试tfrecords |

（来源：模型pipeline流程.txt）

### 样本类型

| 样本类型 | 适用模型 | 中间表 |
|---------|---------|--------|
| **短期样本** | CTR、VV（播放次数）、VT（播放时长）模型 | omg_video_resys::t_rcmd_video_app_cid_tfdnn_sample_h |
| **长期样本** | LTVV（长期播放）模型 | omg_video_resys::t_rcmd_video_app_resys_cover_retention_sample_h |

### Spark任务优化

不同于之前对曝光数据进行**10%抽样**，VideoResysSampleTable直接采用**全量曝光数据**和引擎日志进行join，导致任务直接增大了将近**10倍**。采取的优化策略：

1. **engine表和曝光点击表切小**：repartition 5000
2. **shuffle partition调大**：`--conf spark.sql.shuffle.partitions=1024`（默认200，join时会导致executor OOM，这是优化后最明显的地方）
3. **资源配比**：core调到4，executor_memory按1:4调整（如16），保证CPU利用率；如果executor GC严重可调大memory
4. **错峰执行**：最好实验21-23点的任务，一般主要卡在这些时间点

（来源：模型pipeline流程.txt）

## 5.2 特征工程

### 特征体系

模型使用的特征分为以下几类：

**用户/上下文特征（单值，batch_size=1）**：
- 上下文：day_of_week、hour_of_day、src_key
- 设备：dev_type、dev_model
- 地理位置：lbs_province、lbs_city、province、city
- 用户画像：age、gender、prof（职业）、edu（学历）
- 业务：rec_scene、is_vip、plat_bucket、plat_strategy、rec_reason

**Item特征（单值，batch_size=-1）**：
- cid（内容ID）、idx_alg（召回算法ID）、idx_score（召回分）
- prev_watch_cnt（历史播放次数）、prev_imp_cnt（历史曝光次数）
- prev_watch_cnt_since_imp（曝光后播放次数）、prev_imp_cnt_since_watch（播放后曝光次数）

**用户行为序列特征（多值，batch_size=1，max_len=20）**：
- cid_playlist / cid_playlist_cnts / cid_playlist_secs：用户播放历史（内容ID列表+播放次数列表+播放时长列表）
- play_cates / play_cates_cnts / play_cates_secs：用户播放的一级类目（来自insightdnn[0]）
- play_gens / play_gens_cnts / play_gens_secs：用户播放的二级类目（来自insightdnn[1]）
- play_subgens / play_subgens_cnts / play_subgens_secs：用户播放的三级类目（来自insightdnn[2]）
- play_om_firsts / play_om_firsts_cnts / play_om_firsts_secs：用户播放的OM一级（来自insightdnn[3]）
- play_om_seconds / play_om_seconds_cnts / play_om_seconds_secs：用户播放的OM二级（来自insightdnn[4]）

**方法论**：序列特征采用"三元组"设计——ID列表+次数列表+时长列表，既保留了行为的内容信息，又保留了行为的强度和深度信息。多值特征通过`max_len`截断，不足时用默认值填充。

### 标签体系

| 标签 | 含义 | 类型 |
|------|------|------|
| is_watched | 是否播放（短期） | 短期label |
| watch_secs | 播放时长（短期） | 短期label |
| watch_cnt | 播放次数（短期） | 短期label |
| lt_is_watched | 是否播放（长期） | 长期label |
| lt_watch_cnt | 播放次数（长期） | 长期label |
| lt_watch_secs | 播放时长（长期） | 长期label |
| is_nextday_retention | 次日留存（1天） | 长期label |
| is_nextday_retention2 | 次日留存（2天） | 长期label |
| is_nextday_retention3 | 次日留存（3天） | 长期label |
| is_nextday_retention4 | 次日留存（4天） | 长期label |

### 新增特征流程

1. 后台（qixu）增加pb字段，提供pb协议并上报boss 5893，落盘`omg_tdbank::omgpb_t_boss_v1_5893`
2. 接入层（qunfengliu）同步增加pb字段，上报boss 8366，落盘`omg_tdbank::omgpb_t_boss_v2_8366`（后续新引擎上报统一走后台上报）
3. 解析`omgpb_t_boss_v2_8366`上报字段（解析程序已迁移到tfdata工程下）
4. 在长/短期中间表中增加新特征字段，在VideoResysSampleTable中增加新特征逻辑
5. 生成新的配置文件，增加对应新特征，生成新的tfrecord

### 新增Label流程

- **短期label**（如付费label）：在短期中间表上增加字段+join逻辑，或新建一张中间表在短期中间表基础上join
- **长期label**（需等待2天/7天等）：建议新建中间表，基于短/长期中间表进行join（不需要再直接join引擎日志表）

## 5.3 模型配置化与训练

### 模型架构

以长期LTVV模型为例，使用**DLRM2**网络架构：

| 配置项 | 值 | 说明 |
|--------|-----|------|
| network_type | dlrm2 | 深度学习推荐模型 |
| embed_size | 128 | Embedding维度 |
| default_num_oov_buckets | 100 | 默认OOV桶数 |
| hidden_layer_sizes | [512, 512, 512] | 隐藏层大小 |
| loss | clip_weighted_cross_entropy | 带截断的加权交叉熵 |
| label | lt_is_watched | 长期播放标签 |
| weight | lt_watch_cnt | 长期播放次数作为权重 |
| clip_min / clip_max | 1 / 100 | 权重截断范围 |
| optimizer | lazy_adam | 优化器 |
| learning_rate | 0.0001 | 学习率 |
| batch_size | 4096 | 批大小 |
| train_epochs | 1 | 训练轮数 |
| train_shuffle_buffer_size | 1000000 | 训练shuffle buffer |

**特殊配置**：
- `map_num_oov_buckets`：{cid: 300000, rec_reason: 100000, play_subgens: 2000, play_om_seconds: 2000}——高基数特征分配更多OOV桶
- `map_top_k_to_select`：{cid: 500000, rec_reason: 150000}——只保留TopK高频ID
- `map_shared_embedding`：{cid_playlist: cid}——用户播放历史中的cid与item cid共享embedding

### 评估指标

| 指标 | 类型 | 说明 |
|------|------|------|
| AUC | auc | 全局AUC，label=lt_is_watched |
| VV-AUC | weighted_auc | 按播放次数加权的AUC，weight=lt_watch_cnt |
| VT-AUC | weighted_auc | 按播放时长加权的AUC，weight=lt_watch_secs |
| RetainAUC1-4 | auc | 1-4天次日留存AUC |
| GAUC | group_auc | 按请求分组的AUC，group_key=seqnum |
| VV-GAUC | weighted_group_auc | 按播放次数加权的GAUC |
| VT-GAUC | weighted_group_auc | 按播放时长加权的GAUC |
| RetainGAUC2-4 | group_auc | 2-4天留存GAUC |

**方法论**：多指标评估体系的设计逻辑是——AUC衡量整体排序能力，GAUC消除用户间偏差（按请求分组），VV/VT加权AUC衡量高价值用户/内容的排序质量，留存AUC衡量长期价值。线上效果最终看留存和时长，因此VT-GAUC和RetainGAUC是核心关注指标。

## 5.4 模型上线与线上Serving

### 线上Serving方案概述

- **TensorFlow作为pCTR引擎的lib**，负责模型的载入和预测实例的inference
- 算法同学以**引擎插件（so）**的形式开发自己负责的排序/召回模型
- 算法插件负责：模型/配置载入、实例构造、实例inference、inference结果封装
- 引擎只提供输入输出接口
- 每位算法同学维护自己的**Sumeru集群**，每个集群上运行自己的pctr引擎，引擎上可加载一类或多类模型
- 配置实验时需要**引流到自己的Sumeru集群**

（来源：模型线上serving相关文档.txt）

### 模型导出流程

1. 在yaml文件中设置`save_model_mode: placeholder`，加载checkpoints模型，生成输入的placeholder，保存为savedmodel模型
2. 在自定义network中实现`_get_serve_inputs`方法，包含所有模型的输入tensor，用于生成signature
   - 常见错误：线上加载so时出现"You must feed a value for placeholder tensor 'example'"，大部分是因为`_get_serve_inputs`没有包含所有输入tensors
   - 排查方法：用`saved_model_cli show --dir saved_model/ --all`打印模型signature
3. 重载`_serve_fn_opt`，定义模型的inference图
   - 核心优化：用户+context特征只需计算一次，在和item特征交互时，先调用`_tile_tensors_with_batch_size`方法扩展batch_size份
   - 开发者需要清楚交互的边界，保证准确性
4. 完成模型导出后，打包一个**xml文件**，用于线上serving配置化so解析

### XML配置详解

XML配置中每个tensor的关键字段：

| 字段 | 含义 | 取值说明 |
|------|------|---------|
| name | tensor名称 | 与模型输入对应 |
| dtype | 数据类型 | string/float/int |
| batch_size | 批次大小 | **-1**=item特征（一个batch有多个item）；**1**=user/context特征（一个batch只有1个） |
| size | 特征维度 | 1=单值；-1=数组 |
| default_value | 默认值 | 特征缺失时的填充值 |
| from | 特征来源映射 | item.xxx / user.xxx / context.xxx |
| max_len | 数组截断长度 | 仅数组特征需要 |

**并行配置**：`<parallel intra_op_threads="24" inter_op_threads="12" />`

### 算法so开发

- 算法so的开发统一在`algorithm_plugins`中的`pctr_tf_dnn_dlrm_config`对应的so上开发
- 新建分支，提交MR时增加指定reviewer，避免影响线上其他模型
- 已有特征不需要特殊处理的直接配置化；需要特殊处理的需修改so
- 新增特征需要引擎传给pctr，不需要特殊处理的直接配置化

### 模型上线流程

1. 拉取代码（主project与submodule都要拉取）
2. 准备工具与环境（主要是blade构建工具）
3. 创建新的算法对应目录或修改已有算法代码
4. 对修改完的代码进行**单元测试与集成测试**
5. 将测试完毕的代码提issue与merge request，找指定reviewer进行code review并合并到master
6. 在Sumeru发布最新代码
7. 在实验系统（骡马）配置实验，引流到自己的Sumeru集群

### MIND召回模型Serving特殊说明

MIND（Multi-Interest Network with Dynamic routing）是我参与的多兴趣召回模型：

- **search_method**配置项：设为1时采用**暴力计算（brute force）**，设为0时采用**HNSW近似搜索**
- **merge_method**配置项：决定多interest时不同的融合方式
- **keep_num**配置项：决定多interest融合时每个interest保留的召回结果数

**mdl模型文件组成**：

| 文件 | 内容 | 说明 |
|------|------|------|
| item_vec.dat | 模型item的embedding | v1=近似计算，v2=bruteforce计算（索引加载逻辑不同，在算法插件初始化时加载，无法用实验配置切换，只能在模型文件中决定） |
| model_conf.conf | 模型conf文件 | |
| saved_model.pb + variables | 模型saved_model | |
| video_d1_mapping.dat | 视频及对应一级类目 | |
| video_id_mapping.dat | 视频及对应字典编码 | 用于inference时构造样本 |
| video_id_mapping_new.dat | 过滤后的视频及字典编码 | 用于bruteforce求最近邻（faiss索引只支持从0开始编码且不可跳码，需另外新建字典） |

**bias+brute force特殊配置**：
- item_vec.dat版本设为v2，embedding最后一项设为item的bias
- 额外生成召回池子过滤后的item字典表video_id_mapping_new.dat

## 6.2 数据问题与数仓建设

### 现存问题

**数据源本身的问题**：
- 灯塔上报只有lc，没有lcid；后台服务上报有lcid

**任务的问题**：
1. 与其他团队的任务相互依赖，难解难分——不需要的任务因为其他人有依赖不敢停，依赖的任务需要修改时无法随意改
2. 大部分数据源是十分钟级或小时级，但依赖的很多中间任务是天级，提高数据时效性的计划无法在现有依赖关系上实现
3. 存在无效任务——如ID为8130154的任务，仅仅是把字段从一个表复制到另一个表
4. 多层做ETL——如8139720任务，第一层解析event_value，第三层解析event_details，原始数据存在于多层浪费存储
5. 维度关系混乱——group by所选维度比较随意
6. 重复关联版本维表——几乎每一层都会关联版本维表
7. 全量读表浪费——如商业依赖的原始数据t_sh_ads_ug_data_log，某天有**127亿**数据，需要的只有**2.1亿**，占**1.6%**，而多次依赖都是直接依赖全量表
8. 阅读数计算逻辑极其复杂（"神逻辑"），经过4步过滤才能使用

**口径问题**：
1. 是否包含无效用户：DAU不包含无效用户id（搜索中心规范），QV由于历史原因包含了
2. 是否只包含'MTT'开头的版本：DAU只包含，QV包含全部版本
3. platform是否只包含android和iphone（急速版已下线）
4. 宽表DAU不加入精探点击，但中心OKR有加入精探点击用户去重；OKR中直达和摄像头跳结果页的部分算重了
5. 有些只记DAU不记QV（阅读、搜狗直出、小说垂搜结果页）

### 数仓分层设计

针对以上问题，设计了标准的数仓分层：

| 层级 | 全称 | 职责 |
|------|------|------|
| **ODS** | Operational Data Store（操作数据层） | 保持与原始上报一样的粒度，ETL规范化处理，解析需要的字段；不做过滤（为了问题追查）；对商业/精探数据只取搜索部分做分离 |
| **DWD** | Data Warehouse Detail（数据明细层） | 每种数据源输出两份（全量+过滤无效用户/版本）；计算阅读/直达305/直达404等特殊功能表；动态分区/多路输出划分原始数据；多源合并；关联维表获取lcid/lc/platform/is_system/version/sub_version |
| **DWM** | Data Warehouse Middle（数据中间层） | 按数据源各自计算QV；最细粒度：guid、jumpfrom、is_zy、query、source、lcid；宽表粒度：guid、jumpfrom、is_zy、lcid取max；关联最严表获取is_zy |
| **DWS** | Data Warehouse Summary（汇总数据层） | 按不同组合合成多个宽表，根据口径决定直达和摄像头是否剔除跳自建页 |
| **ADS** | Application Data Store（应用数据层） | 根据业务需要产出报表，如中心OKR报表 |

（来源：数据流梳理总结.txt）

### 项目二：模型训练Pipeline数据配置化改造

> **面试口述版**：我在微视做推荐时，负责模型训练Pipeline的优化。当时的痛点是排序侧特征实验越来越多，大家各自生成tfrecord，导致存储计算成本高（加几个特征就重跑全量数据），而且不同人处理数据的差异导致实验对比不可靠。

## 7.3 高频Q&A

### Q1：推荐系统为什么要分召回、粗排、精排、重排？能不能直接精排？

**A：** 核心原因是**性能与精度的权衡**。全库内容可能有百万到亿级，如果直接用精排的复杂深度模型对全库做预估，延迟和计算成本都不可接受。所以用漏斗结构：召回层用轻量的索引/近似方法从全库快速捞回几千候选（保证"不漏"），粗排用轻量模型截断到几百（平衡精度和效率），精排才用复杂模型对百级候选做精准多目标预估（保证"准"），最后重排做业务体验优化（多样性、去重、干预）。每一层用计算复杂度换精度，同时严格控制延迟预算。

### Q2：多路召回怎么设计？各路召回的区别是什么？

**A：** 多路召回的设计原则是**"不同召回路覆盖不同语义空间"**，保证候选集的多样性和覆盖率。以我做的精探为例，8路召回各有分工：tag召回（recallByE2q）基于文章标签做精准匹配；高点击词召回（recallByHot）从点击日志挖掘分类高点击词保证热度；补位词召回（recallByReview）在其他词填不满时补位保证返回数量；句子级/篇章级语义召回（recallByNlp/recallByNlpSeman）用NLP模型做语义泛化；文档-词相似性（recallByDocSim）计算内容与词的相似度；知识图谱（recallByAssoWord）基于图谱关联词扩展；概念召回（recallByConcept）基于文章概念匹配。各路召回后合并去重，统一进入排序。在QBfeeds场景中，召回分CB类（基于内容兴趣）、CF类（协同过滤）和其他类（探索、语义索引、打底），CB召回后还会内部调用UM先做一次排序再返回粗排，这个能力已封装可复用。

### Q3：你们的精排模型用什么架构？特征怎么设计？

**A：** 我们用DLRM2（深度学习推荐模型）架构，embed_size=128，三层512维隐藏层。特征分三类：第一类是用户/上下文单值特征（设备、地理位置、用户画像age/gender/prof/edu、业务场景等），这类特征batch_size=1，线上只算一次；第二类是item单值特征（cid、召回算法ID、召回分、历史播放/曝光统计等），batch_size=-1，每个item都要算；第三类是用户行为序列特征，采用"ID列表+次数列表+时长列表"三元组设计，比如cid_playlist（用户播放历史）和insightdnn多级类目序列（一级/二级/三级类目、OM一级/二级），max_len=20截断。序列特征中的cid_playlist与item cid共享embedding（map_shared_embedding），减少参数同时保证语义一致。高基数特征如cid分配30万OOV桶、只保留Top50万高频ID。

### Q4：模型从训练到上线的完整流程是什么？

**A：** 完整流程是：①数据配置化生成tfrecord（SampleTable解析特征join生成中间表→TFRecordData配置化抽样过滤生成tfrecord）；②模型训练（Tesla平台配置yaml，DLRM2训练，lazy_adam优化器，lr=0.0001，batch_size=4096，评估AUC/GAUC/VV-GAUC/VT-GAUC/留存AUC）；③模型导出（save_model_mode=placeholder，实现_get_serve_inputs包含所有输入tensor，重载_serve_fn_opt用tile优化user/context特征只算一次，打包XML配置文件描述每个tensor的batch_size/dtype/from映射）；④算法so开发（在algorithm_plugins的pctr_tf_dnn_dlrm_config上开发，单元测试+集成测试，提MR找reviewer合并）；⑤Sumeru集群发布；⑥实验系统（骡马）配置实验引流到自己的集群。线上Serving用TensorFlow作为pCTR引擎lib，算法以so插件形式开发，每人维护自己的Sumeru集群，引擎可加载一类或多类模型。

### Q5：线上Serving怎么做性能优化？

**A：** 几个关键优化：①user/context特征只计算一次——在_serve_fn_opt中，用户和上下文特征先算好，然后用_tile_tensors_with_batch_size扩展成batch_size份再和item特征交互，避免重复计算；②XML配置中batch_size区分item特征（-1，一个batch多个item）和user/context特征（1，一个batch一个），引擎据此优化计算；③TensorFlow并行配置intra_op_threads=24、inter_op_threads=12；④召回模型用近似搜索加速——MIND模型支持HNSW近似搜索（search_method=0）替代brute force（search_method=1），大幅降低召回延迟；⑤CB召回后内部调用UM先做一次轻量排序再返回Top结果给粗排，减少粗排计算量。

### Q6：推荐系统的监控体系怎么设计？

**A：** 我们采用**两级监控体系**。一级是业务核心指标，直接反映服务健康度和业务效果：请求数、成功率（有返回数/请求数）、平均返回词数、平均召回词数、平均pCTR、平均耗时、超时率。二级是模块级指标，用于快速定位问题：各下游服务的成功率和平均耗时（特征代理、模型代理、CTR/LTR/相关性/CVR预测服务、画像服务、语义去重服务等）、Dcache命中率（用户实时画像和行为）、各路召回的平均召回数（tag、语义、热点、人群等）、各过滤环节的通过率（质量过滤、相关性过滤）。出了问题先看一级指标判断影响面，再下钻二级指标定位具体模块。算法负责人还要为自己的Sumeru集群配置失败率告警。

### Q7：数据流有哪些常见问题？怎么治理？

**A：** 我在实际工作中遇到的主要问题和治理方案：①**跨团队任务依赖难解**——不需要的任务因为别人依赖不敢停，依赖的任务要改字段改不了。治理是推动数仓分层，明确各层职责，减少跨层直接依赖；②**时效性瓶颈**——数据源是10分钟/小时级但中间任务是天级，想提时效改不动。治理是DWD层做明细数据，DWM层支持不同时间粒度的聚合；③**全量读表浪费**——比如商业原始表127亿数据只需1.6%，但每次都全量读。治理是在ODS层就做数据分离，只取需要的部分；④**多层ETL和重复存储**——原始数据在多层都存在。治理是ODS层只做规范化解析，DWD层才做过滤和加工，避免原始数据冗余；⑤**口径不一致**——DAU和QV在无效用户、版本过滤上口径不同。治理是DWD层输出全量和过滤两份数据，供不同口径使用，后续处理不再做正则匹配。整体是标准的ODS→DWD→DWM→DWS→ADS五层架构。

### Q8：重排层做了哪些事情？为什么需要重排？

**A：** 重排是推荐链路的"最后一公里"，精排输出的是每个item的独立预估分，但最终展示需要考虑**列表级的体验和业务规则**，这是精排的point-wise预估做不到的。我们的重排做了这些事：①**多维度过滤**——相关性过滤（ReleFilter）、CVR过滤（CvrFilter）、CTR过滤（CtrFilter）、低质过滤（反黄、低质、视频封面低质）；②**资源捞回**——过滤太多导致返回数量不足时，按相关性打分捞回资源（ResComplement）；③**去重**——来源去重（不同来源标题相似，企鹅号优先）、内容去重（内容理解id重复+标题完全重复）；④**业务干预**——CTR打分干预（领域意图/资源意图/指定账号/指定资源类型/评论数加权）、阿拉丁TopN保护、正则位置干预（query命中正则时指定资源类型到固定位置）；⑤**混排**——阿拉丁资源与打底资源根据点击模型混排，混排后打底恢复原本相对顺序；⑥**特殊重排**——资讯短视频聚合卡特殊重排。核心方法论是：精排解决"每个item好不好"，重排解决"这一屏内容合不合适"。

### Q9：怎么衡量推荐系统的好坏？

**A：** 从三方利益相关方角度衡量。**平台侧**：规模指标（PV/VV）、推荐能力（曝光效率、CTR）、生态健康（覆盖率——我们当时每天unique URL分发约20万，高于看点的6万；新物品推荐能力——图文展控层保护新item，短视频粗排层12小时时间窗加权，小视频拿流量预曝光）、商业目标（AB实验不能明显损害商业收入）。**用户侧**：消费指标（UV转化率、人均曝光、人均消费、时长）、健康度（留存率）、时效性（全局热点我们是行业第一梯度，因为有主编导向；垂类和本地热点有提升空间）、预测准确度（AUC/GAUC）、多样性（我们探索内容整体占比约5%，图文8%、视频4%）、用户满意度（内容质量、时热内容不退避、负反馈有效性）。**CP侧**：垂类品类生产能力。核心是不能只看CTR，CTR优化到极致可能损害时长、留存和生态，需要多目标平衡。

### Q10：Processor异步控制流架构是怎么设计的？

**A：** 这是我在服务重构中设计的核心架构。基本思想是**"功能模块即Processor，控制流即依赖图"**。每个功能模块（语义召回、质量过滤、特征计算等）实现成一个Processor类，继承基类，通用接口读入ProcessorParam（既是输入也是输出），模块从上游接数据→加工→传下游。一条业务逻辑就是按特定顺序组合这些Processor。因为推荐服务大量使用异步调用并行调下游（执行线程和返回处理线程不同），线性控制流被打破成依赖图，所以我设计了2个钩子函数：构造异步调用和处理异步返回。并发时多个模块同时操作同一个ProcessorParam，需要做数据保护或从逻辑上避免同时操作相同部分。生命周期上，Processor对象跨请求（进程唯一或线程唯一，存服务内部状态如加载的索引和配置），ProcessorParam随一次请求（存单次请求数据）。服务初始化时加载所有Processor和数据，请求到来时按控制流图组装Processor发起异步调用。这个架构的好处是新场景接入只需组合现有Processor加少量适配，功能模块可复用，异步并行天然支持。
