# 一、多目标多任务学习全景

### 1.1 为什么需要多目标

我在腾讯微视做账号推荐和内容排序时，深刻体会到**单一目标无法真实反映用户体验和平台价值**。如果只优化点击率（CTR），模型会倾向于推荐标题党、封面党内容，用户点进来很快划走，时长和留存都会掉；如果只优化播放时长，又可能牺牲互动率（点赞、评论、关注），导致社区生态弱化。

微视的推荐场景需要同时关注多个业务目标：
- **点击（CTR）**：用户是否愿意点开这个视频，反映内容吸引力
- **时长（Watch Duration）**：用户看了多久，反映内容质量和匹配度
- **互动（点赞/评论/转发）**：用户是否产生深度参与，反映社区活跃度
- **关注（Follow）**：用户是否关注账号，反映长期关系建立
- **留存（Retention）**：用户是否次日/次周还回来，反映长期价值

这些目标之间**既相关又冲突**：高点击不一定高时长，高时长不一定高互动。多目标多任务学习的核心就是**在一个模型中同时建模多个目标，利用任务间的相关性提升整体效果，同时缓解任务间的冲突**。

### 1.2 推荐中的典型目标与信号

在微视的长视频和短视频场景中，我用到的隐式反馈信号远不止"是否点击"：

| 目标类型 | 具体信号 | 说明 |
|---|---|---|
| 点击类 | 是否点击、播放转化率（UTR） | 反映内容吸引力 |
| 时长类 | 播放时长、完播率、人均时长 | 反映内容质量与匹配度 |
| 互动类 | 点赞、评论、转发、收藏 | 反映深度参与度 |
| 关系类 | 关注账号、进入主页 | 反映长期关系建立 |
| 长期价值 | 长期VV（LTVV）、次留、周留 | 反映用户长期价值 |

> **面试口述版**："我在微视做推荐排序时，从最开始的单目标CTR模型，逐步演进到点击+时长+互动的多目标模型。核心原因是单一目标会导致策略短视——只优化点击会推标题党，只优化时长会牺牲互动。我们最终用多任务网络同时建模多个目标，再通过加权融合得到最终排序分。"

### 1.3 多任务模型范式

多任务学习的核心问题是**如何共享信息、如何隔离冲突**。我在实践中接触和使用过以下几种范式：

| 模型范式 | 共享方式 | 门控机制 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|---|---|
| **Shared-Bottom** | 底层共享一个网络，上层各任务独立塔 | 无 | 结构简单，训练高效，参数少 | 任务冲突时互相干扰，负迁移严重 | 任务相关性高、冲突小 |
| **MMoE** | 多个Expert网络共享，每个任务有独立Gate | 任务级Gate，对Expert加权 | 缓解任务冲突，比Shared-Bottom效果好 | Expert设计需调参，Gate可能坍缩 | 任务有一定相关性但存在冲突 |
| **DBMTL** | 贝叶斯网络建模任务间依赖关系 | 贝叶斯层 | 能建模任务间因果/依赖关系 | 结构复杂，深层目标受益但浅层目标可能负向 | 任务间有明确依赖关系（如点击→时长） |
| **DEN** | Engagement Network + Multi-Head Attention兴趣网络 | Target-Aware Attention | 精准捕捉用户短中长期兴趣和参与度 | 训练时耗较高，对长尾内容泛化不足 | 长视频/内容消费场景 |
| **Muti-gated DEN** | 在DEN基础上引入Side Information + Multi-Gated | 多门控网络 | 捕捉用户关注点差异，改善长尾泛化 | 结构更复杂，需设计Side Info和门控 | 内容属性丰富、用户关注点多元的场景 |

> **可背诵要点**：
> - **Shared-Bottom**是最基础的多任务结构，所有任务共享底层特征表示，任务差异大时容易负迁移。
> - **MMoE**通过多个Expert和任务级Gate实现"选择性共享"，是工业界最常用的多任务结构之一。
> - **DBMTL**用贝叶斯网络显式建模任务间依赖，适合有因果关系的任务链。
> - **DEN**是微视自研的深度参与度网络，核心是Engagement Network建模兴趣强度 + Multi-Head Attention捕捉多峰兴趣。
> - **Muti-gated DEN**在DEN基础上引入Side Information和多门控，解决用户关注点差异和长尾泛化问题。

# 二、DEN深度参与度网络（Deep Engagement Network）

### 2.1 问题背景与动机

我在微视做长视频推荐时，基线DNN模型存在三个核心缺陷，这也是DEN要解决的问题：

**缺陷一：无法捕捉中、长期兴趣。** 基线DNN只考虑用户最近播放的20多个cid（内容ID），但活跃用户的播放历史通常覆盖较长时间周期，历史播放内容较多。只看最近20条，中、长期兴趣完全丢失。（来源：DEN深度参与度网络）

**缺陷二：兴趣强度信号过于粗糙。** 基线模型只考虑用户对专辑的总播放次数、总播放时长等粗粒度隐式反馈，没有考虑：
- 用户对最新一集内容的播放时长
- 用户按退出时刻统计的总播放时长
- 被播放专辑本身的总视频时长、视频个数
- 最后一集被播放视频的时长属性
- 专辑的被播放时间戳、专辑更新时间

这些细粒度信号才能真实反映用户对内容的兴趣强度。（来源：DEN深度参与度网络）

**缺陷三：忽略时序性。** 基线模型没有考虑用户历史播放cid的时序性。用户兴趣不仅与"看过什么"有关，还与"以什么顺序看的"有关——先看喜剧再看悬疑，和先看悬疑再看喜剧，当前兴趣状态完全不同。（来源：DEN深度参与度网络）

### 2.2 研究路线图

针对上述问题，DEN的研究路线分为五步：
1. 增加播放序列长度，验证中、长期兴趣对兴趣捕捉是否更精准
2. 研究用户对item的播放反馈信息是否更准确反映兴趣强度
3. 研究历史播放序列中不同位置内容对当前兴趣的影响
4. 针对用户兴趣的多峰特点，设计能capture用户看到不同内容后兴趣表示的网络结构
5. 提高兴趣网络的预估效率

（来源：DEN深度参与度网络）

### 2.3 DEN网络结构详解

DEN的完整网络结构如下，我按数据流逐层拆解：

```
输入层
  ├── 用户历史播放专辑序列 ci (i=1,2,...,N)
  ├── 每个专辑的播放反馈信息 ci_play_feedback_info
  └── 当前预估专辑 target_id
      │
      ▼
Embedding Layer
  ├── 专辑ID → 低维稠密Embedding
  ├── target_id → 低维稠密Embedding
  └── Position Encoding → 对播放序列中专辑的位置ID编码
      │
      ▼
Engagement Network（参与度网络）
  ├── 输入：用户对每个专辑的播放反馈信号
  ├── 功能：归纳播放反馈信号，输出表达用户对专辑播放兴趣强度的向量
  └── 输出：兴趣强度表示
      │
      ▼
Target-Aware Multi-Head Attention（目标感知多头注意力）
  ├── Query：target_id的Embedding（当前候选内容）
  ├── Key/Value：历史播放专辑的Embedding + Engagement输出 + Position Encoding
  ├── 功能：基于用户兴趣多峰特性，mask与当前内容无关的兴趣，
  │         增强与候选target相关的兴趣
  └── 输出：低维稠密的用户兴趣Embedding
      │
      ▼
特征拼接层
  ├── 用户兴趣Embedding
  └── 其他特征信号（用户画像、上下文特征等）
      │
      ▼
全连接网络（FC Layers）
      │
      ▼
输出层（各任务目标预估）
```

**各层核心设计要点：**

**① Embedding + Position Encoding层**
- 将专辑ID和target_id映射到低维稠密向量
- 采用Position Encoding对播放序列中专辑的位置ID编码，将位置信息加入专辑表示中，**表达历史播放内容的时序性**——这解决了基线模型忽略时序的缺陷

**② Engagement Network（参与度网络）——DEN的核心创新之一**
- 输入是用户对每个历史专辑的播放反馈信息（最新一集播放时长、退出时刻总时长、专辑总视频时长、视频个数、最后一集时长、播放时间戳、更新时间等）
- 功能是**对这些细粒度播放反馈信号进行归纳，输出表达用户对该专辑播放兴趣强度的信号**
- 这解决了基线模型只用总播放次数/总时长的粗粒度问题，能更精准地衡量"用户到底有多喜欢这个内容"

**③ Target-Aware Multi-Head Attention（目标感知多头注意力）——DEN的另一核心创新**
- 基于用户兴趣具有**多峰特性**（一个用户可能同时喜欢喜剧、悬疑、纪录片等多种类型）设计
- Query是当前候选target的Embedding，Key/Value是历史播放序列的表示（含Embedding + Position + Engagement输出）
- **mask与当前内容无关的兴趣，增强与候选target相关的兴趣**——比如候选是悬疑剧，就从用户多峰兴趣中激活悬疑相关的那部分，抑制喜剧、纪录片等无关兴趣
- 多头设计允许模型在不同子空间捕捉不同维度的兴趣匹配

**④ 输出与后续计算**
- 最终输出低维稠密的用户兴趣Embedding
- 与其他特征信号一起加入后续全连接网络计算，得到各目标的预估值

（来源：DEN深度参与度网络）

### 2.4 DEN与传统多任务模型的对比

| 维度 | 传统Shared-Bottom/MMoE | DEN |
|---|---|---|
| 兴趣建模 | 依赖共享层自动学习，无显式兴趣网络 | 显式设计Engagement Network + Multi-Head Attention |
| 时序信息 | 通常不建模序列时序 | Position Encoding显式编码播放序列位置 |
| 兴趣强度 | 只用粗粒度反馈（点击/总时长） | Engagement Network归纳细粒度播放反馈信号 |
| 多峰兴趣 | 共享层可能混合不同兴趣，无法针对性激活 | Target-Aware Attention mask无关兴趣，增强相关兴趣 |
| 序列长度 | 通常只取最近少量行为 | 支持更长播放序列，捕捉中、长期兴趣 |
| 训练效率 | 相对高效 | 离线训练时耗较高（DEN遗留问题） |

> **面试口述版**："DEN是我在微视参与的深度参与度网络，核心解决三个问题：一是基线只看最近20条行为，DEN通过延长序列加Position Encoding捕捉中、长期兴趣和时序性；二是基线只用总播放次数和总时长，DEN设计了Engagement Network，把最新一集播放时长、退出时刻时长、专辑总时长、视频个数、播放时间戳这些细粒度反馈归纳成兴趣强度信号；三是用户兴趣是多峰的，DEN用Target-Aware Multi-Head Attention，以候选内容为Query，从历史行为中mask掉无关兴趣、增强相关兴趣。线上在精选猜你喜欢样式上，曝光人均时长提升2.33%，播放转化率提升1.71%，曝光人均vv提升2.34%。"

### 2.5 实验效果与遗留问题

**实验设置：**
- DEN模型和DNN基线均采用**小时增量训练**，实现小时级模型更新
- 线上配置随机分配的等流量实验桶和对照桶，唯一变量是实验桶有DEN网络结构
- 实验观察期：2020.2.6 - 2020.2.20

**核心实验结果（ltvv-DEN，长期vv收益目标）：**
- 精选猜你喜欢样式上，对比基线DNN策略：
  - **曝光人均时长提升2.33%**（来源：DEN深度参与度网络）
  - **播放转化率（UTR）提升1.71%**（来源：DEN深度参与度网络）
  - **曝光人均vv提升2.34%**（来源：DEN深度参与度网络）

**对比实验还包括：**
- 时长-DEN（rank-1039）vs 时长DNN基线（rank-1012）
- vv-DEN（rank-1040）vs vv-DNN基线（rank-1020）

**遗留问题：**
- 离线训练时耗较高，是后续需要优化的方向

（来源：DEN深度参与度网络）

# 三、Muti-gated DEN

### 3.1 DEN的局限性与Muti-gated DEN的动机

DEN上线后效果显著，但在实践中我们发现两个核心局限，这直接催生了Muti-gated DEN：

**局限一：无法准确判断用户观看视频的关注点。** 一部电视剧涉及多个著名演员、导演、剧情、内容类型、口碑（豆瓣评分）等信息，观看该剧的众多用户关注的点各不相同——有人是冲某个演员来的，有人是冲剧情来的，有人是冲口碑来的。DEN模型在专辑粒度建模兴趣，**无法捕捉用户在更细粒度属性上的关注点差异**。（来源：Muti-gated DEN）

**局限二：对长尾内容泛化不够。** 长视频存在头部内容贡献多数播放量的特点，DEN强调基于用户播放行为捕捉兴趣，对于播放量少的长尾内容，行为信号稀疏，**存在挖掘不充分、泛化不够的问题**。（来源：Muti-gated DEN）

### 3.2 Muti-gated DEN的研究路线

针对上述局限，Muti-gated DEN的研究路线分为三步：

1. **引入视频专辑的Side Information**：将演员、导演、剧情、内容类型、豆瓣评分等内容属性作为Side Information引入，使模型能在属性粒度理解内容和用户兴趣
2. **设计基于Multi-Head Attention的网络结构**：capture候选内容与历史播放兴趣在Side Information粒度的匹配程度——比如候选剧的主演是否与用户历史偏好的演员匹配
3. **设计Multi-Gated网络结构**：表达用户对不同内容的兴趣度，通过门控机制选择性地激活不同Side Information维度的兴趣

（来源：Muti-gated DEN）

### 3.3 Muti-gated DEN网络结构推演

虽然原文未给出完整结构图，但基于研究路线和DEN的基础结构，Muti-gated DEN的网络结构可以推演为：

```
输入层
  ├── 用户历史播放专辑序列 ci
  ├── 每个专辑的播放反馈信息（Engagement输入）
  ├── 每个专辑的Side Information（演员/导演/类型/豆瓣评分等）
  ├── 当前候选专辑 target_id
  └── target的Side Information
      │
      ▼
Embedding Layer
  ├── 专辑ID Embedding
  ├── Side Information各属性Embedding（演员/导演/类型/评分等）
  ├── Position Encoding
  └── target Embedding + target Side Info Embedding
      │
      ▼
Engagement Network（延续DEN设计）
  └── 输出兴趣强度信号
      │
      ▼
Side-Info粒度 Multi-Head Attention
  ├── Query：target的Side Information表示
  ├── Key/Value：历史专辑的Side Information表示 + Engagement输出
  └── 功能：在属性粒度计算候选与历史兴趣的匹配度
      │
      ▼
Multi-Gated Network（多门控网络——Muti-gated DEN核心创新）
  ├── 多个Gate，每个Gate对应一类Side Information维度或兴趣模式
  ├── 每个Gate以用户状态+target信息为输入，输出该维度的权重
  ├── 对不同Side Information维度的兴趣表示进行加权融合
  └── 功能：表达用户对不同内容属性的兴趣度，选择性激活关注点
      │
      ▼
兴趣表示输出 → 拼接其他特征 → FC网络 → 多任务输出
```

**Multi-Gated机制的核心思想：**
- 不同用户关注的内容属性不同，门控网络根据用户和候选内容的信息，**动态决定哪些Side Information维度应该被重视**
- 比如对于"演员粉"用户，对应演员维度的Gate输出高权重；对于"剧情党"用户，对应剧情/类型维度的Gate输出高权重
- 这与MMoE的Gate思想类似，但**门控作用在Side Information维度而非Expert维度**，更贴合内容属性丰富的长视频场景

### 3.4 Muti-gated DEN与MMoE的关系

| 维度 | MMoE | Muti-gated DEN |
|---|---|---|
| 门控对象 | 多个Expert网络（通常是MLP） | Side Information维度/兴趣模式 |
| 门控输入 | 共享特征 | 用户状态 + target信息 + Side Info |
| 门控输出 | 对Expert的加权权重 | 对不同内容属性兴趣的加权权重 |
| 核心目标 | 缓解任务间冲突，实现选择性共享 | 捕捉用户关注点差异，改善长尾泛化 |
| 兴趣建模 | 无显式兴趣网络 | 继承DEN的Engagement + Attention兴趣网络 |
| 内容理解 | 不区分内容属性 | 引入Side Information，在属性粒度理解内容 |

> **可背诵要点**：
> - MMoE的Gate是**任务级**的，决定每个任务用哪些Expert；Muti-gated DEN的Gate是**内容属性级**的，决定用户关注哪些内容维度。
> - 两者都用门控实现"选择性激活"，但作用层次不同：MMoE在模型结构层面，Muti-gated DEN在语义理解层面。
> - Muti-gated DEN可以看作是**DEN（兴趣网络）+ Side Information（内容属性）+ Multi-Gated（关注点选择）**的组合，而非简单的MMoE变体。

> **面试口述版**："DEN上线后我们发现两个问题：一是用户看同一部剧关注点不同，有人看演员有人看剧情，DEN在专辑粒度建模捕捉不到这种差异；二是长视频头部效应强，DEN依赖播放行为，对长尾内容泛化不够。所以我们做了Muti-gated DEN，核心是三步：引入演员、导演、类型、豆瓣评分这些Side Information；用Multi-Head Attention在属性粒度计算候选和历史兴趣的匹配；再设计Multi-Gated网络，根据用户和候选内容动态决定哪些属性维度该被重视。它和MMoE的区别是，MMoE的门控作用在Expert层面解决任务冲突，我们的门控作用在内容属性层面解决用户关注点差异和长尾泛化。"

# 四、多目标融合自动调参

### 4.1 多目标加权融合的基本思路

多任务模型会输出多个目标的预估值（如点击概率pCTR、时长预估pDuration、互动概率pLike等），最终排序需要将这些目标融合成一个综合分。最常用的方式是**加权线性融合**：

```
final_score = alpha * pCTR + beta * pDuration + gamma * pLike + delta * pFollow
```

其中alpha、beta、gamma、delta是各目标的权重。**权重的设定直接决定排序策略的偏向**——权重大的目标会被优先优化。

在微视的实践中，这四个参数（alpha、beta、gamma、delta）是多目标融合的核心调参对象。（来源：多目标融合自动调参）

### 4.2 离线网格搜参

**搜参方式：** 采用网格搜索（Grid Search），对alpha、beta、gamma、delta四个参数在指定范围内按步长穷举组合。

**搜参命令示例：**
```bash
python para_search_grid_v2.py \
  --input=data/20200622 \
  --output=result.csv \
  --n_worker=30 \
  --range='6,6.1,0.1_1,2,0.2_1,2,0.2_0.1,0.2,0.1' \
  --n_sample=100000
```

**搜索范围配置规则：**
- 用`_`分割四个参数的范围，依次为alpha、beta、gamma、delta
- 每个参数的格式为`start,end,step`
- 示例`'6,6.1,0.1_1,2,0.2_1,2,0.2_0.1,0.2,0.1'`表示：
  - alpha: 6.0, 6.1（步长0.1）
  - beta: 1.0, 1.2, 1.4, 1.6, 1.8, 2.0（步长0.2）
  - gamma: 1.0, 1.2, ..., 2.0（步长0.2）
  - delta: 0.1, 0.2（步长0.1）
- 若不配置range参数，则从字典服务拉取base参数进行调整

**运行环境：** 可在开发机上运行，或在venus上利用tf模块开CPU容器运行。每个worker几乎会100%占用一个核心，需注意控制worker数量。（来源：多目标融合自动调参）

### 4.3 在线实时搜参（v3版本）

在线搜参通过Flink实时消费数据，实现参数的在线动态搜索：

**数据流：**
- Kafka消费组实时消费三路数据：
  - 曝光：`cg_yoorecappgroup_multitask_integrate_streaming_exposure`
  - 点击：`cg_yoorecappgroup_multitask_integrate_streaming_click`
  - 点赞：`cg_yoorecappgroup_multitask_integrate_streaming_like`

**参数存储：**

（来源：多目标融合自动调参）

### 4.4 参数选择策略（Select Best）

搜参得到大量参数组合后，需要一套策略选择最优参数。选择策略的核心逻辑如下：

```python
# 读搜参结果
res_df = pd.read_csv(res_path)
epsilon = 1e-5

# 定位base参数对应的记录
base_record = res_df.loc[
    (abs(res_df['alpha'] - alpha_base) <= epsilon) &
    (abs(res_df['beta'] - beta_base) <= epsilon) &
    (abs(res_df['gamma'] - gamma_base) <= epsilon) &
    (abs(res_df['delta'] - delta_base) <= epsilon)
].iloc[0]

# 筛选条件1：AUC优于base 且 观看时长优于base
candi_df = res_df.loc[res_df['auc'] > base_record['auc']].loc[
    res_df['mean_watch_duration'] > base_record['mean_watch_duration']
]

# 筛选条件2：点击量提升 >= 0.05% (0.0005)
candi_df['click_increase'] = (
    candi_df['click_proportion'] - base_record['click_proportion']
) / base_record['click_proportion']
candi_df = candi_df.loc[candi_df['click_increase'] >= 0.0005]

# 计算点赞提升
candi_df['like_increase'] = (
    candi_df['like_proportion'] - base_record['like_proportion']
) / base_record['like_proportion']

# 筛选条件3：观看时长与视频时长差值 >= 6秒
# （视频时长太长会导致vv大幅下降，因此需要控制）
candi_df['time_gap'] = candi_df['mean_watch_duration'] - candi_df['mean_duration']
candi_df = candi_df.loc[candi_df['time_gap'] >= 6]

# 最终选择：按时长降序、点赞提升降序排序，取第一
if len(candi_df) > 0:
    best_record = candi_df.sort_values(
        by=['mean_watch_duration', 'like_increase'],
        ascending=[False, False]
    ).iloc[0]
else:
    best_record = base_record  # 无更优参数，回退base
```

**搜参结果CSV字段说明：**
- alpha, beta, gamma, delta：四组融合权重
- auc：该组参数下的AUC
- mean_watch_duration：top1/3样本的平均观看时长
- mean_duration：top1/3样本的平均视频时长
- click_proportion：top1/3样本的点击占比
- like_proportion：top1/3样本的点赞占比

**选择策略的核心思想——帕累托最优思路：**
1. **硬约束过滤**：AUC必须优于base、观看时长必须优于base、点击提升不低于0.05%、time_gap不低于6秒——这些是不可妥协的底线
2. **多目标排序**：在满足硬约束的候选集中，按时长和点赞提升排序选最优
3. **安全回退**：如果没有候选满足所有约束，回退到base参数，避免线上效果劣化

这本质上是一种**带约束的多目标优化**：在保证点击、AUC不劣化的前提下，最大化时长和互动。（来源：多目标融合自动调参）

### 4.5 实验效果与问题

**实验结果：**
- **Select Best v1**（主要优化点赞）：整体指标都有所提升
- **第二次实验**（优化时长）：单vv时长上升，但vv下降，总时长没有显著增长——这说明**过度优化时长会损害播放量，需要在时长和vv之间做平衡**

**存在的问题：**
1. **数据延迟与join率的权衡**：实时数据join需要等待窗口，延迟大则join率高但时效性差，延迟小则join率低
2. **3流join延迟大**：曝光点击join之后要再等一个窗口再和点赞join，有2个时间窗口的延迟
3. **Flink任务不稳定**：组内flink任务增加后，每天会有几个小时跑不出来

**未来展望：**
- 数据先存到HDFS，再当离线数据join（用离线稳定性换实时性）
- 当前时段的参数，使用上周或昨天同期的数据进行网格搜索
- 以用户粒度进行调参（不同用户群体用不同的融合权重）

（来源：多目标融合自动调参）

> **面试口述版**："多目标融合我们用的是加权线性融合，四个参数alpha/beta/gamma/delta分别控制点击、时长、点赞、关注的权重。调参分离线和在线两套：离线用网格搜索，多进程并行，每个参数指定start/end/step；在线用Flink实时消费曝光、点击、点赞三路数据做动态搜参。选参策略是带约束的多目标优化——先硬过滤：AUC和观看时长必须优于base、点击提升不低于万分之五、观看时长和视频时长的差不低于6秒；然后在候选集里按时长和点赞提升排序选最优。实验中我们发现优化点赞时整体指标都涨，但纯优化时长会导致vv掉、总时长不涨，所以约束条件里特意加了time_gap来控制视频时长。"

# 五、多任务模型调优

### 5.1 MMoE模型调优实践

我在微视调优MMoE模型时，总结了以下关键经验：

**① 基础结构选择：单个MLP + LR最优**
- 使用**单个MLP加LR**的模式可以比较好地实现训练时间和模型性能的均衡
- 引入FM（Factorization Machine）或CIN（Compressed Interaction Network）模块**均没有产生正向效果**
- 结论：在微视的推荐场景下，简单的MLP+LR比复杂的特征交叉模块更有效

**② Expert和Tower的深度控制**
- 单纯增加Expert layers的深度和宽度**并不能带来性能提升**
- Expert layers和Tower的层数之和**控制在3层以内**会有比较好的效果
- **Tower超过一层会带来负向效果**——任务塔不宜过深，否则容易过拟合或导致任务间干扰

**③ Expert多样性的重要性**
- 如果使用多个MLP作为Expert，**结构差异较大时效果较好**
- 这说明Expert之间需要有差异性，才能捕捉不同的特征模式；如果所有Expert结构相同，容易学到相似的表示，退化为共享底层

（来源：多任务模型调优-xingdawang）

### 5.2 DBMTL模型调优实践

**① 全贝叶斯网络的双面效应**
- 使用全贝叶斯网络对于**深层目标有一定帮助**——深层目标（如时长、互动）依赖浅层目标（如点击）的信息，贝叶斯网络能更好地传递这种依赖
- 但对于**浅层目标会有一些负向效果**——浅层目标被深层目标的梯度反向影响，反而损害了自身的学习

**② 层数控制**
- Specific layers和Bayesian layers**最好都只用一层**
- Bayesian layers的输出**不应该是logits的形式**——应该输出特征表示或概率分布，而非直接的logits

**③ 梯度截断技巧**
- 可以尝试：前向计算时将浅层目标的Bayesian layers输出作为深层目标的Bayesian layers输入
- 但在**回传梯度时进行截断**（Stop Gradient），或者不对浅层目标的网络使用深层目标的损失
- 这样既能让深层目标利用浅层信息，又能避免深层目标的梯度干扰浅层目标的学习

（来源：多任务模型调优-xingdawang）

### 5.3 多任务调优的核心问题与解法

| 核心问题 | 表现 | 解法（来自实践） |
|---|---|---|
| **任务不平衡** | 某些任务样本多/梯度大，主导共享层学习，其他任务学不好 | 控制Expert+Tower总层数≤3，Tower≤1层避免过拟合；调整各任务loss权重 |
| **负迁移** | 任务差异大时，共享表示反而损害各任务性能 | MMoE用多个结构差异大的Expert增加多样性；DBMTL用梯度截断隔离深层对浅层的干扰 |
| **梯度冲突** | 不同任务梯度方向相反，共享层参数更新互相抵消 | MMoE的Gate实现选择性共享；DBMTL的Bayesian层显式建模任务依赖；Tower不超过1层减少冲突传导 |
| **过拟合** | 模型复杂度高，小样本任务过拟合 | Expert+Tower总层数≤3；不引入FM/CIN等复杂模块 |

> **可背诵要点**：
> - MMoE调优三原则：**单个MLP+LR就够了**，FM/CIN没用；**Expert+Tower总层数≤3**，Tower>1层负向；**Expert结构要有差异**，相同结构退化为共享层。
> - DBMTL调优三原则：**全贝叶斯帮深层害浅层**；**Specific和Bayesian层都只用1层**，Bayesian输出不用logits；**前向传信息、反向截梯度**，隔离深层对浅层的干扰。
> - 多任务调优的本质是**在共享和隔离之间找平衡**：共享太少学不到任务间相关性，共享太多负迁移和梯度冲突。

> **面试口述版**："多任务模型调优我踩过不少坑。MMoE方面，最开始尝试加FM和CIN模块做特征交叉，发现完全没正向效果，后来回到单个MLP加LR反而效果和效率最均衡。深度方面，一开始把Expert和Tower都堆很深，发现单纯加深度宽度没用，后来把Expert加Tower总层数控制在3层以内，而且Tower超过1层就负向。还有一个关键点是多个Expert的结构要有差异，结构一样就退化成共享底层了。DBMTL方面，全贝叶斯网络对深层目标有帮助但对浅层有负向，所以我们用了梯度截断——前向计算时浅层Bayesian输出传给深层，反向传播时截断，不让深层梯度干扰浅层。"

# 六、贝叶斯优化搜参

### 6.1 为什么用贝叶斯优化

网格搜索虽然简单，但存在两个核心问题：一是**搜索效率低**，参数空间稍大就需要海量组合；二是**无法利用历史实验信息**，每次搜索都是独立的，不会从之前的实验结果中学习。

贝叶斯优化（Bayesian Optimization）是一种**基于概率模型的黑盒函数优化方法**，核心思想是：用高斯过程（GPR）建模参数与 reward 之间的未知函数关系，通过采集函数（Acquisition Function）平衡探索（Exploration）和利用（Exploitation），**用尽可能少的实验次数找到最优参数**。

在多目标融合调参场景中，目标函数 `f(alpha, beta, gamma, delta) = reward` 是一个黑盒函数——给定一组参数，需要上线实验、收集数据、计算reward，每次调用成本很高（至少1天），因此贝叶斯优化比网格搜索更适合。（来源：贝叶斯优化搜参）

### 6.2 贝叶斯优化整体流程

```
步骤1：参数冷启动
  └── 通过离线搜参的方式先得到一些冷启动参数
      │
      ▼
步骤2：参数下发
  ├── 方式A：一个桶里存多组参数，通过名字服务随机下发
  │   （上线容易，但难保证同一用户一直映射到同一组参数）
  └── 方式B：设置多个1%的小桶，每个桶对应一个名字服务下发不同参数
      │
      ▼
步骤3：收集数据
  └── 得到每组参数的线上指标（人均时长、人均vv、互动率等）
      │
      ▼
步骤4：计算Reward
  └── reward结合人均时长、人均vv、视频时长、互动率等
  └── reward需要和base参数的reward对比（归一化，消除时间段差异）
      │
      ▼
步骤5：GPR建模 + 采集函数选参
  ├── 用历史（参数, reward）样本训练高斯过程回归模型
  ├── 用采集函数（EI/MPI/LCB等）选择下一组要上线的参数
  └── 可以有多个reward和acquisition，偏向不同指标/探索/利用
      │
      ▼
步骤6：新参数上线 → 回到步骤3，循环迭代
```

（来源：贝叶斯优化搜参）

### 6.3 高斯过程（GPR）建模

高斯过程回归是贝叶斯优化的核心，它对未知函数 `f(x) = reward` 建立后验分布：
- 给定历史观测样本 `{(x_i, y_i)}`，GPR可以预测任意新参数x处的reward均值μ(x)和方差σ(x)
- **均值μ(x)** 表示该参数点的预期reward（利用）
- **方差σ(x)** 表示该参数点的不确定性（探索潜力）

在微视的实现中，有两种技术路线：
1. **基于GPyOpt**：使用封装好的贝叶斯优化库GPyOpt
2. **基于sklearn GPR + scipy**：自己用sklearn的GaussianProcessRegressor建模，用scipy优化采集函数

（来源：贝叶斯优化搜参）

### 6.4 采集函数（Acquisition Function）

采集函数决定下一组参数选哪里，核心是平衡探索和利用：

| 采集函数 | 全称 | 思想 | 偏向 |
|---|---|---|---|
| **EI** | Expected Improvement | 选择期望提升最大的点，兼顾均值和方差 | 平衡探索与利用 |
| **MPI** | Maximum Probability of Improvement | 选择比当前最优更优概率最大的点 | 偏利用 |
| **LCB** | Lower Confidence Bound | 选择置信下界最小的点（最小化问题） | 偏探索 |

GPyOpt提供EI、MPI、LCB三种采集函数。在实践中，可以设置多个reward和acquisition组合：
- 偏向不同指标的（偏时长、偏互动）
- 偏向exploration的（多探索未知参数空间）
- 偏向exploitation的（多在已知高reward区域精细搜索）
- 然后得到不同的参数同时上线实验

（来源：贝叶斯优化搜参）

### 6.5 Reward函数设计

Reward函数是贝叶斯优化的"指挥棒"，直接决定优化方向。微视的reward设计如下：

```python
def cal_score(base_record, exp_record):
    # 计算各指标相对base的变化率
    click_inc = (exp_record['click'] - base_record['click']) / base_record['click']
    duration_inc = (exp_record['duration'] - base_record['duration']) / base_record['duration']
    watch_duration_inc = (exp_record['watch_duration'] - base_record['watch_duration']) / base_record['watch_duration']
    like_inc = (exp_record['like'] - base_record['like']) / base_record['like']

    # 硬约束：点击跌幅超过阈值 → 直接返回点击变化率（负反馈）
    if click_inc < CLICK_THR:
        return click_inc
    # 硬约束：点赞跌幅超过阈值 → 直接返回点赞变化率（负反馈）
    elif like_inc < LIKE_THR:
        return like_inc
    # 点击和点赞都达标 → 返回观看时长涨幅（优化目标）
    else:
        return watch_duration_inc
```

**Reward设计的核心原则：**
1. **与base对比做归一化**：reward需要和base参数的reward对比得到，相当于归一化。否则不同时间段收集的数据因为流量、内容池差异，对比没有意义
2. **硬约束优先**：点击和点赞是不可妥协的底线，跌幅超阈值直接给负反馈
3. **主目标优化**：在满足约束的前提下，优化观看时长涨幅

（来源：贝叶斯优化搜参）

```python
    return reward

# GPyOpt每次优化有batch_size参数，设置为10
# 多进程调用10个f，每个f通过队列获取自己要上线的桶
```
- 目标：优化 `f(alpha, beta, gamma, delta) = reward`
- 调用这个函数时，参数上线，1天后收集样本得到函数值
- batch_size=10，多进程并行调用10个目标函数

**基于sklearn GPR + scipy的实现流程：**
- 样本收集 → 过去样本训练GPR → 采样参数，计算EI → 从EI排名靠前的随机选择一组上线

（来源：贝叶斯优化搜参）

### 6.7 存在的问题与挑战

**V1版本的问题：**
- 目标函数的调用设置成并行的，但**实际没并行**——一组参数上线后等待结果，会阻塞别的组的参数上线
- 目前不可用，有问题没解决

**核心挑战：**
1. **冷启动问题**：需要下发多少组参数？按什么规则选？参数太少GPR建模不准，太多实验成本高
2. **数据置信度问题**：一组参数需要收集多少数据才比较置信？少了reward波动大，多了实验周期长
3. **Reward和Acquisition设置**：如何设计reward权重和采集函数，平衡多个业务目标和探索利用

（来源：贝叶斯优化搜参）

> **面试口述版**："网格搜索效率太低，我们后来引入了贝叶斯优化做自动调参。整体流程是：先用离线搜参做冷启动，然后通过名字服务把参数下发到10个实验桶，收集线上数据算reward，用GPR建模参数和reward的关系，再通过采集函数选下一组参数上线，循环迭代。Reward设计是带硬约束的——点击和点赞跌幅超阈值直接负反馈，否则返回观看时长涨幅，而且所有reward都和base做对比归一化。采集函数用GPyOpt提供的EI、MPI、LCB，可以同时跑多个偏向不同的优化器。工程上用GPyOpt的batch_size=10实现10个桶并行。不过V1版本有个问题，目标函数名义上并行但实际串行，一组参数等结果会阻塞其他组，这个还没完全解决。"

# 七、优化用户长期价值

> **说明**：《优化用户长期价值策略（一）.txt》原文仅65字节，内容为标题+"网络请求失败！"，原文内容缺失。以下长期价值相关内容从DEN文档（ltvv-DEN模型）、多目标融合自动调参、贝叶斯优化等文档中提取和归纳。

### 7.1 长期价值vs短期目标

推荐系统中，短期目标（点击、即时时长）和长期价值（留存、LTV、长期VV）之间存在天然的张力：

- **短期目标**：点击、单次播放时长、即时互动——容易观测、反馈快，但优化短期目标可能导致"标题党""擦边内容"等短视行为
- **长期价值**：用户次日留存、周留存、长期播放量（LTVV）、用户生命周期价值（LTV）——反馈延迟大、建模困难，但真正决定平台的健康度和商业价值

我在微视的实践中，**ltvv-DEN（长期vv收益目标）模型**就是直接以长期VV为优化目标的尝试。（来源：DEN深度参与度网络）

### 7.2 LTVV建模实践

**ltvv-DEN模型**是在DEN网络结构基础上，以长期VV收益为目标训练的模型：

- **模型结构**：沿用DEN的完整网络（Embedding + Position Encoding + Engagement Network + Target-Aware Multi-Head Attention + FC）
- **优化目标**：长期VV（LTVV），而非即时点击或单次时长
- **训练方式**：基于tf-dnn新框架上线，小时增量训练

**线上效果（精选猜你喜欢样式，对比基线DNN策略）：**
- **曝光人均时长提升2.33%**（来源：DEN深度参与度网络）
- **播放转化率（UTR）提升1.71%**（来源：DEN深度参与度网络）
- **曝光人均vv提升2.34%**（来源：DEN深度参与度网络）

这说明**以长期VV为目标的模型，不仅提升了长期指标，也带动了短期指标（时长、转化率）的提升**——长期价值和短期目标并非完全对立，好的长期目标建模可以实现双赢。

### 7.3 延迟反馈问题

长期价值建模的核心挑战是**延迟反馈**：
- 点击反馈几乎实时（用户点不点立刻知道）
- 时长反馈在播放结束后知道
- 而长期价值（次留、LTVV）需要等待数天甚至数周才能观测到完整标签

在多目标融合自动调参的在线搜参中，我们就遇到了延迟反馈的工程问题：
- **3流join延迟**：曝光点击join之后要再等一个窗口再和点赞join，有2个时间窗口的延迟
- **数据延迟与join率的权衡**：等的时间越长join率越高，但参数更新的时效性越差

贝叶斯优化中也明确提到：**一组参数上线后需要等1天收集反馈**，才能得到reward值。这就是长期/延迟反馈在调参中的直接体现。

（来源：多目标融合自动调参、贝叶斯优化搜参）

### 7.4 从多目标调参看长期价值优化

多目标融合的参数选择策略本身就体现了长期价值的思路：

1. **time_gap约束**：`time_gap = mean_watch_duration - mean_duration >= 6`，控制推荐的视频时长不要过长——因为视频时长太长会导致vv大幅下降，虽然单条时长长但总时长和长期消费会受损
2. **多指标平衡**：不单纯优化时长，而是同时约束点击、点赞、AUC——避免为了单一指标牺牲用户体验和长期留存
3. **用户粒度调参展望**：未来计划以用户粒度进行调参，不同用户群体用不同的融合权重——这本质上是针对不同用户的长期价值差异化优化

（来源：多目标融合自动调参）

> **面试口述版**："长期价值是推荐系统的终极目标，但建模难度大，主要是反馈延迟——点击实时就有，次留和LTV要等几天甚至几周。我们在微视做了ltvv-DEN模型，直接以长期VV为目标训练，线上在精选猜你喜欢上曝光人均时长提升2.33%、UTR提升1.71%、人均vv提升2.34%，说明优化长期目标也能带动短期指标。延迟反馈在工程上也带来很多问题，比如在线调参时曝光点击点赞三流join有两个窗口的延迟，贝叶斯优化每组参数要等一天才能拿到reward。我们的应对是在多目标融合里加约束，比如time_gap >= 6秒来控制视频时长，避免为了单条时长牺牲vv和长期消费。"

# 八、面试话术

### 8.1 口述版：多目标多任务学习整体介绍

> "我在腾讯微视做账号推荐和内容排序时，核心工作就是多目标建模。最开始是单目标CTR模型，后来发现只优化点击会推标题党，用户点进来很快划走，时长和留存都掉。所以我们演进到多目标模型，同时建模点击、时长、点赞、关注多个目标。
>
> 模型结构上，我们从Shared-Bottom到MMoE，再到自研的DEN和Muti-gated DEN。DEN的核心是Engagement Network加Target-Aware Multi-Head Attention，能捕捉用户的短中长期兴趣和多峰兴趣，线上人均时长提升2.33%。Muti-gated DEN在DEN基础上引入Side Information和多门控，解决用户关注点差异和长尾泛化问题。
>
> 多目标融合用加权线性融合，四个参数alpha/beta/gamma/delta，调参从网格搜索演进到贝叶斯优化。调优实践上，MMoE的Expert加Tower总层数控制在3层以内，Tower超过1层就负向；DBMTL用梯度截断隔离深层对浅层的干扰。"

### 8.2 高频Q&A

**Q：多任务学习怎么做？为什么需要多任务？**

A：多任务学习的核心是在一个模型中同时建模多个目标，利用任务间的相关性提升整体效果。需要多任务的原因是推荐场景有多个业务目标（点击、时长、互动、关注、留存），这些目标既相关又冲突——单一目标优化会导致策略短视，比如只优化CTR会推标题党。多任务的做法是：底层共享特征表示，上层各任务有独立的塔；进阶做法是用MMoE的多Expert加Gate实现选择性共享，或者用DEN这样的显式兴趣网络加多任务输出。我在微视的实践是从Shared-Bottom演进到MMoE，再到自研的DEN/Muti-gated DEN。

**Q：DEN和MMoE有什么区别？**

A：DEN和MMoE解决的是不同层面的问题。MMoE是多任务学习的通用结构，核心是多个Expert加任务级Gate，解决任务间的冲突和负迁移问题，它不关心具体的兴趣建模。DEN是微视自研的深度参与度网络，核心是Engagement Network建模用户兴趣强度（细粒度播放反馈归纳）加Target-Aware Multi-Head Attention捕捉用户多峰兴趣，它解决的是用户兴趣精准建模的问题。DEN的输出可以作为多任务模型的特征输入，两者不是互斥的，可以组合使用。简单说：MMoE管"任务间怎么共享"，DEN管"用户兴趣怎么建模"。

**Q：多目标融合的权重怎么定？**

A：我们用加权线性融合，final_score = alpha*pCTR + beta*pDuration + gamma*pLike + delta*pFollow。权重确定经历了两个阶段：第一阶段是离线网格搜索，对四个参数指定start/end/step穷举组合，多进程并行，然后用带约束的策略选最优——AUC和观看时长必须优于base、点击提升不低于万分之五、观看时长和视频时长差不低于6秒，最后按时长和点赞提升排序。第二阶段是贝叶斯优化，用GPR建模参数和reward的关系，通过采集函数（EI/MPI/LCB）选下一组参数上线，10个实验桶并行，比网格搜索效率高很多。实验中发现纯优化时长会导致vv下降、总时长不涨，所以约束条件里特意加了time_gap来控制。

**Q：多任务中任务冲突怎么解决？负迁移怎么办？**

A：任务冲突和负迁移是多任务学习的核心挑战。我在实践中有几个解法：第一，用MMoE的Gate机制实现选择性共享，每个任务有独立的Gate对多个Expert加权，任务可以选择对自己有用的Expert，避免完全共享导致的冲突。第二，控制模型复杂度，MMoE的Expert加Tower总层数控制在3层以内，Tower超过1层就负向——塔太深会放大任务间的梯度冲突。第三，Expert之间要有结构差异，相同结构的Expert容易学到相似表示退化为共享层，结构差异大时效果更好。第四，对于DBMTL这类有任务依赖的模型，用梯度截断——前向计算时浅层Bayesian输出传给深层，反向传播时截断，不让深层梯度干扰浅层。第五，调整各任务的loss权重，对样本少或重要的任务加大权重。

**Q：DEN的Engagement Network具体做什么？为什么需要它？**

A：Engagement Network是DEN的核心创新之一。基线模型只用总播放次数和总时长这种粗粒度反馈来衡量用户兴趣，但这些信号太粗糙了——一个用户看了10集和看了1集，总时长可能一样，但兴趣强度完全不同。Engagement Network的输入是细粒度的播放反馈信息：用户对最新一集的播放时长、按退出时刻统计的总播放时长、专辑本身的总视频时长和视频个数、最后一集被播放视频的时长、专辑的被播放时间戳和更新时间等。它对这些信号进行归纳，输出一个表达用户对该专辑播放兴趣强度的向量。这样模型就能区分"随便看看"和"深度追更"两种完全不同的兴趣强度，这是基线模型做不到的。

**Q：贝叶斯优化和网格搜索比有什么优势？Reward怎么设计？**

A：贝叶斯优化比网格搜索的核心优势是样本效率高——网格搜索对参数空间穷举，参数多的时候组合爆炸，而且每次搜索独立不利用历史信息；贝叶斯优化用GPR建模参数和reward的关系，通过采集函数平衡探索和利用，每次都选信息增益最大的参数点，用更少的实验次数找到最优。在我们的场景里，每组参数上线要等1天才能拿到reward，实验成本很高，贝叶斯优化的效率优势就特别明显。Reward设计是带硬约束的：点击和点赞跌幅超过阈值直接给负反馈，否则返回观看时长涨幅；所有reward都和base做对比归一化，消除不同时间段的流量和内容池差异。采集函数用EI、MPI、LCB，可以同时跑偏向不同指标、偏探索、偏利用的多个优化器。

**Q：Muti-gated DEN为什么要引入Side Information？多门控和MMoE的Gate有什么不同？**

A：引入Side Information是因为DEN有两个局限：一是用户看同一部剧关注点不同，有人看演员有人看剧情，DEN在专辑粒度建模捕捉不到这种差异；二是长视频头部效应强，DEN依赖播放行为，对长尾内容泛化不够。引入演员、导演、类型、豆瓣评分这些Side Information后，模型可以在属性粒度理解内容，对于行为稀疏的长尾内容也能通过属性匹配做推荐。多门控和MMoE的Gate作用层次不同：MMoE的Gate是任务级的，决定每个任务用哪些Expert，解决任务冲突；Muti-gated DEN的Gate是内容属性级的，根据用户和候选内容动态决定哪些属性维度该被重视，解决用户关注点差异。简单说，MMoE的Gate在模型结构层面，我们的Gate在语义理解层面。

**Q：多任务模型调优有什么经验？踩过什么坑？**

A：踩过不少坑。MMoE方面，最开始尝试加FM和CIN做特征交叉，发现完全没正向，回到单个MLP加LR反而效果和效率最均衡。深度方面，一开始把Expert和Tower都堆很深，发现单纯加深度宽度没用，后来把Expert加Tower总层数控制在3层以内，而且Tower超过1层就负向。还有Expert结构要有差异，相同结构退化为共享底层。DBMTL方面，全贝叶斯网络对深层目标有帮助但对浅层负向，所以用了梯度截断——前向传信息、反向截梯度。Specific和Bayesian层都只用1层，Bayesian输出不用logits。这些经验都是在微视的真实数据上反复实验得到的，数据来源是组内的调优实验文档。
