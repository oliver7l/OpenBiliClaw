# 信息流搜索推荐服务重构

## 产品定位（一句话）
将支持QQ浏览器、手机QQ看点、看点快报三个应用、多种场景的搜索词推荐服务，从多套独立代码重构为统一接口+模块化Processor的架构，降低维护成本，支撑后续策略统一。

## 背景与业务问题
- 信息流搜索推荐当前支持QQ浏览器、手机QQ看点、看点快报3个应用
- 视应用不同又有正文底部、feeds流回退、搜索结果页、搜索结果页回退等多种场景
- 即使相同场景下，不同应用的词库、处理流程、模型也各不相同
- 导致日常支持维护、定位问题、升级优化的成本很高
- 计划重构一个统一的搜索词推荐服务，兼容多个应用的多个场景

## 目标与核心指标
- **短期目标**：代码层面的统一。所有场景共用一套代码，不同应用的相同场景主要流程相同，用分支/适配形式兼容线上现有的不同词库、业务逻辑、模型
- **长期目标**：策略层面的统一。相同场景使用同一套策略和模型，通过配置参数、模型特征适配不同应用的特殊性
- **核心指标**：
  - 代码复用率（统一代码占比）
  - 新场景接入成本（开发人日）
  - 问题定位效率（平均故障定位时间）
  - 重构后效果与线上等效（CTR/收入不降）

## 方案设计（含技术栈/模型/表，可用ASCII图）

### 服务架构
```
上游调用（QB/看点/快报，各应用历史接口）
        │
        ▼
  适配层（历史接口→通用接口转换）
        │
        ▼
  通用接口（QueryRecomm.jce，一套接口支持所有应用/场景）
        │
        ▼
  分应用部署的服务实例（QB服务/看点服务/快报服务）
        │
        ├── 监控各服务流量
        └── 隔离异常流量风险
```

- 多个应用和场景在代码层面统一，共用同一套代码，提供同一个调用接口
- 仍然分应用部署多个服务：现状已是分应用部署，重构不牵涉上游调用改动；分服务部署方便监控各服务流量，隔离异常流量风险
- QB和看点已有各自不同的历史接口在线上运行，需要额外的适配代码把历史接口调用转换到新通用接口

### 代码设计原则
1. **接口与业务逻辑分离**：一套统一接口支持各应用和场景，服务内部根据不同场景分开处理流程。好处：接入新场景时少开新接口，服务迁移时复用现有接口，减少上游对改动的感知
2. **业务逻辑与功能模块分离**：功能模块与业务逻辑解耦，语义召回、质量过滤等作为功能模块提供独立可重用的功能，针对特定场景需求简单组合任意功能模块+少量特定开发

### 控制流模式（Processor架构）

```
Processor基类
  ├── 通用接口：process(ProcessorParam) → 输入输出同一结构体
  ├── 异步调用模块：2个钩子函数
  │     ├── 构造异步调用
  │     └── 处理异步返回
  └── 生命周期：进程唯一/线程唯一（取决于内部状态是否可线程间共用）
                跨请求，内部数据存储服务状态
                ProcessorParam存储单次请求数据，生命周期=请求周期
```

- 一个基本功能模块实现成一个类，所有模块继承基类，实现通用接口
- 接口读入ProcessorParam（既是输入也是输出），功能模块从上游接收数据，加工后传给下游
- 一条控制流通过特定顺序组合这些功能模块实现特定业务逻辑

### 异步调用与依赖图
- 推荐服务调用其他服务通常用异步调用提高性能（执行调用线程和处理返回线程不是同一个）
- 可同时调用多个下游服务，异步调用破坏控制流线性关系，调用关系表现为依赖图
- 封装异步调用的功能模块提供2个钩子函数：构造异步调用、处理异步返回
- 并发调用时多个模块同时处理同一数据结构，需要对数据作保护，或从代码逻辑上避免同时操作数据相同部分

### 典型请求处理流程（代码示例）
```cpp
taf::Int32 QueryRecommImp::getRecommQuery(
    const RecommQueryReq& req, RecommQueryRsp& rsp, taf::JceCurrentPtr current) {
  taf::TC_Common::AutoPtr pParam(new ProcessorParam());
  // 初始化 ProcessorParam

  auto f1 = m_docProcessor.process(pParam);
  auto f2 = f1.then(bind(&TagRecallProcessor.process, m_tagRecallProcessor, pParam));
  auto f3 = f1.then(bind(&SimRecallProcessor.process, m_simRecallProcessor, pParam));
  // 更多召回...

  auto f4 = whenAll(f2, f3);          // 等待所有召回完成
  auto f5 = f4.then(bind(&QualityProcessor.process, m_qualityProcessor, pParam));
  auto f6 = f4.then(bind(&FeatureProcessor.process, m_featureProcessor, pParam));
  auto f7 = whenAll(f5, f6);          // 等待质量过滤和特征提取完成
  // CTR/CVR预估等后续流程...

  return SERVERSUCCESS;
}
```

- 初始化阶段：初始化所有Processor，加载数据，设置参数；运行过程中可定时重载数据和参数
- 接收请求时：按控制流图组装Processor，发起一次异步调用
- 用promise/future模式管理异步依赖，whenAll等待多个并行任务完成

### 功能模块抽象与合并
- 当前有一些逻辑相同的功能，因开始设计数据结构时没有抽象，造成重复代码
- 如加载各个倒排索引、正文底部和feeds流回退的相关性过滤等，可分别合并成Processor，通过初始化参数区别
- 限制涉及上下游服务的差异：
  - QB正文底部的文章主题和tag是推荐服务主动从DCache获取，快报的主题和tag是上游用参数传下来的
  - QB正文底部和快报正文底部使用的实时曝光上报DCache数据结构不同
  - 这些差异只能通过代码层面编写不同的适配Processor兼容，原则是把外部差异封装在尽量小的单元内部，向外提供一致接口

## 技术实现要点
1. **统一接口+分应用部署的架构权衡**：代码层面统一（一套代码、一个接口），部署层面分离（分应用部署多个服务实例），既降低了维护成本，又避免了上游调用改动，同时保留了流量监控和故障隔离的能力。这是大型分布式服务重构的经典架构权衡。
2. **Processor模块化设计**：每个功能模块（语义召回、质量过滤、特征提取、CTR预估等）实现为一个Processor类，继承基类，实现统一接口，通过ProcessorParam传递数据。这种设计使功能模块可独立开发、测试、复用，新场景只需组合现有Processor+少量适配。
3. **异步依赖图的控制流管理**：用promise/future模式管理异步调用依赖，whenAll等待多个并行任务，then串联依赖任务，将复杂的异步依赖图转化为清晰的代码表达。这是高并发推荐服务的核心工程能力。
4. **历史接口适配层**：QB和看点已有不同的历史接口在线上运行，通过适配层将历史接口调用转换为新通用接口，实现平滑迁移，不牵涉上游调用改动。
5. **外部差异的最小封装原则**：不同应用的数据获取方式（DCache vs 上游参数）、数据结构不同，通过编写不同的适配Processor将外部差异封装在最小单元内部，向外提供一致接口，减少流程其他部分的感知。
6. **分阶段迁移策略**：先写基础架构→迁移快报功能→替换快报线上→适配QB切流量→最后适配看点，分阶段降低迁移风险，每阶段有明确的验证标准。

## 亮点与难点
- **亮点1：统一接口+分应用部署的架构设计**。不是简单地把三套代码合并，而是在代码统一和部署独立之间取得平衡，既降低维护成本又保留故障隔离能力，这是大型服务重构的架构智慧。
- **亮点2：Processor模块化+异步依赖图的工程设计**。将复杂的推荐流程拆解为可复用的Processor模块，用promise/future管理异步依赖，代码清晰、可维护、可扩展，展示了扎实的服务端工程能力。
- **亮点3：接口与业务逻辑分离、业务逻辑与功能模块分离的双分离原则**。两层分离使新场景接入成本极低（组合现有Processor），服务迁移时上游无感知，这是面向扩展性的架构设计。
- **亮点4：分阶段迁移的风险控制**。基础架构→快报→QB→看点的分阶段迁移，每阶段有明确的验证标准（服务可测试→接近线上效果→全量→diff可接受），降低了大型重构的风险。
- **亮点5：外部差异最小封装的工程原则**。把不同应用的数据获取差异封装在适配Processor内部，向外提供一致接口，这是处理多端差异的经典工程方法。
- **难点1：多应用多场景的差异抽象**。3个应用、4+种场景，词库、流程、模型各不相同，如何在统一架构中优雅地处理这些差异而不导致代码膨胀，是核心设计难点。
- **难点2：异步并发的数据保护**。多个Processor并发处理同一ProcessorParam时，需要避免同时操作数据的相同部分，这需要精细的代码设计或数据保护机制。
- **难点3：重构期间的线上稳定性**。重构期间需要保证线上服务不受影响，新老服务并行运行，流量逐步切换，任何一步出问题都可能影响线上收入。
- **难点4：看点服务的迁移复杂度**。看点代码和策略与QB/快报差异较大，迁移不能保证完全等效，需要评估保证效果近似且不变差，这是最后阶段的最大挑战。

## 可迁移点
1. **"统一接口+分应用部署"的架构权衡**：代码统一降低维护成本，部署独立保留故障隔离能力，这一架构权衡可迁移到任何多端/多场景的服务重构项目。
2. **Processor模块化+异步依赖图的工程设计**：将复杂流程拆解为可复用模块，用promise/future管理异步依赖，这是高并发推荐/广告/搜索服务的通用工程范式。
3. **双分离原则（接口与逻辑分离、逻辑与模块分离）**：两层分离使系统可扩展性极强，新场景接入只需组合现有模块，这是面向扩展性架构设计的通用原则。
4. **外部差异最小封装原则**：将多端差异封装在适配层内部，向外提供一致接口，这是处理多端/多渠道差异的经典工程方法。
5. **分阶段迁移的风险控制方法**：基础架构→最小场景→逐步扩展的分阶段迁移，每阶段有明确验证标准，这是任何大型系统重构/迁移的通用风险控制方法。
6. **历史接口适配层的平滑迁移设计**：通过适配层将历史接口转换为新接口，实现上游无感知的平滑迁移，这是任何系统升级换代的通用设计。
