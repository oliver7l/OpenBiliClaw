# 知识图谱构建与实时干预系统

## 产品定位（一句话）
在腾讯看点构建知识图谱（实体-关系-属性三元组），并设计实时干预系统支持实体数据的即时修改生效，从离线构建到在线干预形成完整的数据治理闭环。

> 注：本项目落地于QQ看点知识图谱，技术方法论可迁移至微视社交图谱与内容图谱。

## 背景与业务问题
- QQ看点需要知识图谱支撑内容理解、实体链接、推荐召回等下游应用
- 图谱日常运营中经常有实体数据需要实时干预生效的情况：
  - 某明星突发离婚消息，需要立即修改图谱中该明星的婚姻状态及配偶信息
  - 使用者反馈图谱中某热门综艺参演嘉宾有错，需要立即删改修正
- 通过重新构建图谱生效数据太慢（天级），无法满足时效性要求
- 亟需一种对图谱数据的实时干预生效能力，能够立即将线上数据修改至理想状态，并将修改记录保存，在之后的构建流程中保持正确的人工修改状态

## 目标与核心指标
- **图谱构建目标**：构建覆盖人物、作品、机构等实体的知识图谱，支持实体抽取、关系抽取、实体融合、属性补全
- **实时干预目标**：实体属性修改即时生效（秒级/分钟级），修改记录持久化，每日构建同步保持人工修改状态
- **核心指标**：
  - 图谱实体覆盖率、关系准确率
  - 实时干预生效延迟
  - 人工修改与构建结果的一致性
  - 干预操作的成功率

## 方案设计（含技术栈/模型/表，可用ASCII图）

### 整体架构
```
数据源（爬取/模型抽取/人工标注/算法抽取）
        │
        ▼
  图谱构建流程（离线，日级）
  实体抽取→关系抽取→实体融合→属性补全→质量评估
        │
        ├──→ 离线DB（t_kg_entity_data_compress）
        ├──→ 图引擎（在线查询）
        └──→ ES（搜索检索）
              │
              ▼
        实时干预系统（kgop平台）
        人工修改→DB回写→修改记录→图引擎实时生效
              │
              ▼
        每日构建同步修改记录→保持人工修改状态
```

### 一、图谱构建流程

#### 1. 实体抽取
- 从文本内容中抽取命名实体（人物、作品、机构、地点等）
- 基于NLP模型（NER）+ 规则 + 词典
- 实体类型：人物（明星/导演/演员）、作品（电影/电视剧/综艺/动漫）、机构（公司/平台）等

#### 2. 关系抽取
- 抽取实体间的关系（主演-作品、导演-作品、夫妻-人物、所属-机构等）
- 基于关系抽取模型 + 远程监督 + 人工校验

#### 3. 实体融合（Entity Resolution）
- 同一现实实体可能有多个ID（rid-eid聚簇），需要融合
- 基于实体属性相似度（姓名、别名、作品、关系）的聚类
- 融合后选择主ID（eid），其他ID作为别名

#### 4. 属性补全
- 基于模型预测、跨源数据对齐、推理规则补全缺失属性
- 多路接入数据：模型补充数据、人工修改数据、算法抽取数据

#### 5. 质量评估
- 实体准确率、关系准确率、属性覆盖率
- 人工抽检 + 自动评估

### 二、实时干预系统（现有方案）

#### kgop平台操作流程
```
运维同学在界面上修改实体属性 → 点击保存
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
  1. DB回写      2. 修改记录    3. 图引擎
  实体全部数据    保存到manual   实时修改
  覆盖原数据      表(Json格式)   线上SPO
        │           │           │
        └───────────┼───────────┘
                    ▼
            修改即时生效
            （平台查询/算子访问都得到最新数据）
                    │
                    ▼
            每日构建流程读取修改记录
            → 应用到构建中
            → 构建数据更新覆写线上
            → 保持人工修改状态
```

#### 数据存储
1. **t_kg_entity_data_compress**：实体全量数据，修改后回写覆盖
2. **t_kg_entity_info_manual**：人工修改记录，每个EID一行，所有属性Json格式存储，人工修改的属性加"manual_*"标记
3. **图引擎**：实时修改SPO（Subject-Predicate-Object）记录

#### 构建流程应用逻辑
- 筛选Json中有"manual_*"标记的所有属性
- 直接用这些属性值替代构建生成的对应属性数据
- 其他属性值保留正常构建结果

### 三、现有方案缺陷
- **被修改过的属性值永远不会再更新**：只会保留人工修改时的数据状态，直到下次人工继续修改
- 这种逻辑明显不适用于需要持续更新的属性（如明星的作品列表、年龄、粉丝数等）

### 四、优化方案

#### 4.1 修改记录存储格式重构
重新设计存储格式，以EID按行聚合，根据人工修改标记区别应用策略：

| 修改状态 | 标记 | 含义 | 应用逻辑 |
|---|---|---|---|
| 删除 | manual_delete | 若构建结果匹配到该属性值，则删除 | 属性值黑名单 |
| 新增 | manual_add | 若构建结果没有该属性值，则添加 | 属性值白名单 |
| 更新 | manual_update | 删去更新操作，改为删除+新增代替 | 组合操作 |

- 兼容现有修改记录格式，减少前端变更量
- 以EID按行聚合，减少DB行数
- SPO粒度的人工干预操作，灵活控制

#### 4.2 实体数据锁定策略
对于人工确认过不应该变化的属性或实体，新增加锁策略：

| 加锁状态 | 标记 | 作用 |
|---|---|---|
| 属性加锁 | property_lock | 该属性值不再变更，以修改记录为准 |
| 实体加锁 | entity_data_lock | 该实体所有属性值不再变更 |
| eid加锁 | entity_id_lock | 该实体ID不再变更，融合后优先选用该EID |
| 融合状态加锁 | mix_lock | rid-eid聚簇不再发生变化 |

#### 4.3 构建流程应用决策
- 先应用加锁策略（锁定的属性/实体/ID/融合状态不更新）
- 再应用manual_delete（删除黑名单属性值）
- 再应用manual_add（新增白名单属性值）
- 未锁定且未人工干预的属性，正常使用构建结果

### 五、展望
1. **ES实时干预**：图谱数据同时存储在DB、图引擎、ES中，需要增加实时干预修改记录生效到ES的能力
2. **统一SPO接入模块**：图谱存在多路接入数据（模型补充/人工修改/算法抽取），开发统一SPO接入模块，将接入数据协议统一成标准SPO格式，减少构建流程对不同接入数据的异化操作
3. **修改触发爬取**：每次人工修改实体数据后，触发一次对该实体的爬取任务，避免因数据未及时更新爬取导致错误修改
4. **构建覆盖人工标注通知**：当构建流程结果更新覆盖人工标注结果时，导出通知，人工标注者可确认或回滚

## 技术实现要点
1. **三层存储的实时一致性**：DB（离线全量）、图引擎（在线查询）、ES（搜索检索）三层存储需要保持实时一致性，人工修改后需要同步更新三层，每日构建后也需要同步覆写。
2. **修改记录的持久化与回放**：人工修改记录保存在manual表中，每日构建流程读取并回放修改，保证构建后的数据仍保持人工修改状态。这是"人工干预+自动构建"混合数据治理的核心机制。
3. **SPO粒度的精细干预**：优化方案将人工干预从"属性级覆盖"细化为"SPO级操作"（删除/新增/更新），并配合加锁策略，使人工干预更灵活、更精准，同时不影响未干预属性的正常更新。
4. **实体融合的ID管理**：rid-eid聚簇的实体融合机制，eid加锁保证融合后ID稳定，mix_lock保证聚簇不再变化，这是知识图谱中实体管理的核心工程问题。
5. **兜底与异常处理**：数据延迟、构建失败、修改冲突等异常场景需要兜底机制，保证系统在异常情况下仍能提供基本服务。
6. **人机协同的数据治理**：人工修改与自动构建的协同——人工负责高价值/高时效/错误修正，自动负责大规模/常规更新，两者通过修改记录和加锁机制协同，是知识图谱数据治理的最佳实践。

## 亮点与难点
- **亮点1：实时干预与离线构建的协同设计**。人工修改即时生效（图引擎实时更新），同时修改记录持久化到manual表，每日构建流程回放修改，保证构建后数据一致性。这是"在线干预+离线构建"混合架构的经典设计。
- **亮点2：从属性覆盖到SPO精细操作的优化**。现有方案的"被修改属性永远不更新"缺陷，通过manual_delete/manual_add/manual_update三种SPO级操作+加锁策略解决，既保证人工干预生效，又允许未干预属性正常更新，设计精巧。
- **亮点3：四级加锁策略的粒度控制**。属性加锁/实体加锁/eid加锁/融合状态加锁，四级粒度从细到粗，灵活控制哪些数据不应该被自动构建覆盖，体现了对数据治理粒度的深度思考。
- **亮点4：人机协同的数据治理理念**。人工负责高价值修正和实时干预，自动构建负责大规模常规更新，两者通过修改记录和加锁机制协同，不是"人工vs自动"的对立，而是"人工+自动"的协同。
- **亮点5：知识图谱全链路的工程能力**。从实体抽取、关系抽取、实体融合、属性补全到实时干预、质量评估，覆盖知识图谱构建和治理的全链路，展示了系统工程能力。
- **难点1：三层存储的实时一致性**。DB、图引擎、ES三层存储的实时同步是工程难点，任何一层的延迟或失败都会导致数据不一致，需要完善的同步机制和异常处理。
- **难点2：实体融合的准确性**。同一实体的多个ID融合需要高准确率，融合错误会导致数据混乱，eid加锁和mix_lock是事后补救，更需要提升融合模型的准确率。
- **难点3：人工修改与自动构建的冲突处理**。当自动构建结果与人工修改冲突时，如何决策（人工优先/构建优先/人工确认），需要完善的冲突处理机制。
- **难点4：修改记录的版本管理**。多次人工修改同一属性，需要版本管理和回滚能力，材料中未记录具体的版本管理方案。

## 可迁移点
1. **"在线干预+离线构建"混合数据治理架构**：人工修改即时生效（在线层），修改记录持久化后由离线构建流程回放，保证数据一致性。这一架构可迁移到任何需要人工干预+自动更新的数据系统（推荐系统特征库、用户画像系统、商品库、风控规则库等）。
2. **SPO级精细操作+加锁策略**：将人工干预从粗粒度覆盖细化为SPO级删除/新增/更新操作，配合多级加锁策略，既保证干预生效又允许未干预数据正常更新。这一思路可迁移到任何需要人工审核+自动处理的数据治理场景。
3. **人机协同的数据治理理念**：人工负责高价值/高时效/错误修正，自动负责大规模/常规更新，两者通过修改记录和加锁机制协同。这一理念适用于任何数据密集型系统的治理。
4. **知识图谱全链路工程方法**：实体抽取→关系抽取→实体融合→属性补全→质量评估→实时干预的全链路方法，可迁移到任何需要构建知识图谱的场景（医疗、金融、电商、教育等）。
5. **实体融合的ID管理方案**：rid-eid聚簇、eid加锁、融合状态加锁的ID管理方案，可迁移到任何需要实体对齐和ID管理的数据系统。
6. **多层存储的一致性设计**：DB（离线全量）+图引擎（在线查询）+ES（搜索检索）三层存储的一致性同步设计，可迁移到任何需要多层存储的系统架构。
