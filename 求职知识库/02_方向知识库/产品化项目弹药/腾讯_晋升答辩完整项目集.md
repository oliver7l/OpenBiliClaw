## 子项目一：烟火推荐项目（从0到1新业务）

### 产品定位（一句话）
QQ看点新业务"烟火"的推荐系统从0到1搭建，覆盖内容池建设、多路召回、排序模型全链路，为新业务冷启动提供推荐能力。

### 背景与业务问题
- 烟火是QQ看点的新业务方向，初期没有任何推荐系统，需要从0到1搭建。
- 新业务内容池小、用户行为少，传统推荐方法难以直接应用。
- 需要快速验证业务可行性，同时保证推荐质量。

### 目标与核心指标
- 北极星：烟火Tab用户消费时长、点击率
- 过程：内容池规模、召回覆盖率、新用户首屏点击率

### 方案设计
```
内容池建设 → 多路召回 → 排序 → 场景下发
  ├─ 内容池：PGC多版本过滤 + UGC内容池
  ├─ 召回：画像召回(FIREWORK_RECALL) + Embedding召回(Q_FIREWORK_EMBEDDING_RECALL)
  │       + 冷启动召回(Q_FIREWORK_UGC_COLD_START) + 兜底(Q_FIREWORK_DOUDI)
  ├─ Embedding：封面/标题/视频帧/烟火点击/主Feeds点击/DSSM(新老用户分开)
  └─ 排序：接入看点统一排序框架
```

### 技术实现要点
- 内容池多版本过滤策略迭代（v1→v2→v3），逐步加入质量分、时长、作者等级过滤
- 7种Embedding召回并行，覆盖多模态和行为信号
- 冷启动三档探索（explore_state 10/20/30）+ account_merged_score>0.88账号质量过滤
- 新用户7470组精细分群，简化画像+热门兜底
- 召回命名规范化：Q_业务_名称 + POOL-METHOD

### 亮点与难点
- 从0到1完整搭建新业务推荐系统，涵盖内容池到排序全链路
- 新业务冷启动阶段，用多模态Embedding+热门兜底解决行为稀疏问题
- 配置化召回框架支持后续快速迭代

### 量化结果（真实数字+来源）
- 大盘池版本1内容数量：7554条（来源：05_UGC推荐/UGC内容推荐召回.md）
- 新用户分群：7470组（来源：05_UGC推荐/冷启动.md）
- 冷启动账号质量阈值：account_merged_score>0.88（来源：05_UGC推荐/UGC内容推荐召回.md）
- 具体业务效果数据：材料中未记录

### 复盘与局限
- 新业务初期内容池规模小，召回多样性受限
- 排序模型初期复用看点统一模型，未针对烟火场景单独优化

### 可迁移点
- 新业务推荐系统从0到1的搭建方法论
- 内容池多版本过滤+冷启动三档的渐进式方案

### 面试话术
我在腾讯还负责了烟火新业务推荐系统的从0到1搭建。新业务没有任何推荐基础，我从内容池建设开始，做了多版本过滤策略，然后搭了画像、Embedding、冷启动、兜底四路召回，Embedding里做了封面标题视频帧多模态加DSSM双塔，新老用户分开建模。冷启动用三档渐进式曝光加账号质量分过滤，把探索流量给优质账号。新用户做了7470组精细分群用简化画像加热门兜底。整个系统用配置化框架搭建，支持后续快速迭代。

## 子项目二：QQ看点品类推荐中台（多品类统一推荐）

### 产品定位（一句话）
将图集推荐技术方案抽象为可复用的品类推荐中台，统一支撑图集、小说、短内容等多个品类的推荐需求，避免重复建设，提升算法迭代效率。

### 背景与业务问题
- 看点有图集、小说、短内容等多个内容品类，各品类各自搭建推荐系统，重复建设严重。
- 不同品类的召回、排序、特征体系有大量共通之处，可以抽象复用。
- 新品类接入推荐系统周期长，需要标准化的pipeline。

### 目标与核心指标
- 北极星：新品类接入推荐系统的周期、各品类核心指标
- 过程：pipeline复用率、特征复用率、模型复用率

### 方案设计
```
品类推荐中台
  ├─ 统一召回框架（多路召回+配置化）
  ├─ 统一训练pipeline（kandian_categroy_rank_model）
  ├─ 统一特征体系（用户特征+品类内容特征+交叉特征）
  ├─ 统一模型组件库（LR/DCN/ESMM/MMoE可配置切换）
  └─ 统一线上服务（atta上报+织云监控+统一路由）
```

### 技术实现要点
- 提供品类推荐训练pipeline（kandian_categroy_rank_model），方便特征添加、模型实验、模型上线
- 模型统一实现方案，将模块组件化，支持LR/DNN/DCN/DeepFM/DIN/xDeepFM等多种模型配置切换
- 图集推荐技术方案推广至小说、短内容等新品类
- 成为品类研发中心推荐的小业务中台

### 亮点与难点
- 从单品类推荐到多品类中台的技术抽象能力
- 训练pipeline标准化，大幅降低新品类接入成本
- 模型组件化开源，被腾讯网、波动星球、全民K歌、微信支付等多个BG内外业务咨询借鉴

### 量化结果（真实数字+来源）
- 推广至新品类：小说、短内容（来源：08_晋升答辩/专业影响.md）
- 成为品类研发中心推荐的小业务中台（来源：08_晋升答辩/专业影响.md）
- 开源repo：60+ stars（来源：08_晋升答辩/专业影响.md）
- 借鉴业务：腾讯网、波动星球、全民K歌、微信支付（来源：08_晋升答辩/专业影响.md）
- 具体接入周期缩短数据：材料中未记录

### 复盘与局限
- 中台化程度仍有提升空间，部分品类仍有定制化逻辑
- 模型组件库覆盖了常见模型，但对新模型（如Transformer系列）支持不足

### 可迁移点
- 推荐系统中台化的技术抽象和pipeline建设经验
- 模型组件化、可配置化的工程实践
- 技术方案跨业务推广的方法论

### 面试话术
我在腾讯把图集推荐的技术方案抽象成了品类推荐中台，统一支撑图集、小说、短内容多个品类。核心做了三件事：一是统一训练pipeline，叫kandian_categroy_rank_model，新品类加特征、做实验、上线模型都走标准化流程；二是模型统一实现，把LR、DCN、ESMM、MMoE这些都组件化，配置切换就行；三是统一召回和特征体系。这个中台成了品类研发中心推荐的小业务中台，我还把模型实现开源了，拿到60多star，腾讯网、全民K歌、微信支付这些业务都来咨询借鉴。

## 子项目三：短内容浮层多目标推荐

### 产品定位（一句话）
QQ看点短内容（短视频）浮层场景的多目标推荐系统，同时优化停留时长和用户互动，通过精排多目标和召回多目标全链路升级，带动大盘时长和互动增长。

### 背景与业务问题
- 短内容浮层是看点核心消费场景，但单目标模型只优化点击，时长和互动被忽视。
- 用户刷短视频时，停留时长和互动（点赞/评论/分享）是比点击更重要的深度消费指标。
- 召回侧只按相关度召回，候选集本身缺乏多目标质量信号。

### 目标与核心指标
- 北极星：短内容浮层时长、短内容总时长、大盘累积使用时长
- 过程：互动行为、进评论率/进评论数、篇均时长、广义DAU、DAU留存

### 方案设计
```
2020.04 短内容浮层多目标精排
  └─ MMoE多目标模型，同时优化停留时长+用户互动
  └─ 无量3.0平台部署，BG第一个全量多目标业务

2020.06 短内容浮层多目标召回
  └─ 多目标信号从精排下沉到召回
  └─ 实验桶56/67 vs 对照桶90/91
```

### 技术实现要点
- MMoE（多专家多门控）模型结构，多个专家网络共享底座，门控网络为每个目标分配专家权重
- 时长目标建模：实验了连续值/分档/顺序等多种方式
- 无量3.0平台快速对接，从模型训练到线上服务全链路打通
- 多目标召回：将多目标质量信号融入召回候选集生成

### 亮点与难点
- BG第一个在无量3.0全量上线多目标的业务，为后续业务踩坑铺路
- 多目标从精排到召回的全链路下沉，不仅排序优化，候选集质量也按多目标筛选
- 时长和互动两个目标存在天然冲突，MMoE结构有效平衡

### 量化结果（真实数字+来源）
**多目标精排**（4格置信度）：
- 大盘累积使用时长 +0.42%
- 大盘广义DAU +0.10%
- 广义DAU留存 +0.07%
- 短内容互动行为 +35%
- 短内容浮层时长 +6.8%
- 短内容总时长 +2.85%
（来源：08_晋升答辩/童力材料.md、能力举证材料-整体.md）

**多目标召回**（实验桶56/67 vs 对照桶90/91）：
- 进评论率 +80%
- 进评论数 +70%+
- 篇均时长 +8%
- 总时长 +4%
（来源：08_晋升答辩/童力材料.md、能力举证材料-整体.md）

### 复盘与局限
- 时长建模方式的最优方案未在材料中记录最终结论
- 多目标loss权重的调参过程未详细记录
- 互动目标中各子目标（点赞/评论/分享）的权重分配可进一步优化

### 可迁移点
- MMoE多目标在短视频场景的落地经验
- 多目标从精排下沉到召回的全链路方法论
- 新算法平台（无量3.0）快速接入的实践

### 面试话术
短内容浮层是看点核心场景，我负责它的多目标推荐升级。之前单目标只优化点击，用户点得多但不爱看、不互动。我先在精排上了MMoE多目标模型，同时优化停留时长和互动，并且牵头对接无量3.0平台，成了BG第一个在无量3.0全量上线多目标的业务。然后我把多目标信号下沉到召回，让候选集也按多目标质量来筛选。精排上线后大盘时长涨0.42%、互动涨35%、浮层时长涨6.8%，召回上线后进评论率直接涨了80%，篇均时长涨8%。

## 子项目四：特征体系建设与数据应用

### 产品定位（一句话）
为看点图集、短内容、UGC等多个业务搭建统一的特征体系，涵盖用户特征、内容特征、交叉特征、序列特征和亲密度特征，为排序模型提供高质量特征输入。

### 背景与业务问题
- 各业务特征分散建设，口径不统一，复用困难。
- 特征质量直接影响模型效果，缺乏系统化的特征挖掘和管理。
- 序列特征、亲密度特征等高级特征缺乏标准化实现。

### 目标与核心指标
- 北极星：模型AUC提升、线上CTR提升
- 过程：特征覆盖率、特征复用率、特征上线周期

### 方案设计
```
特征体系分层
  ├─ 基础数据层：关注/粉丝列表、用户画像、内容元数据
  ├─ 账号特征层：分类、等级、创作能力、粉丝数、多时间窗口统计
  ├─ 用户特征层：年龄、性别、省市、画像（一/二/三级分类+标签）、实时画像
  ├─ 内容特征层：
  │    ├─ 数值特征：PicCount、ReadNum、ClickNum、ExpNum、ClickRate、QualityScore等
  │    ├─ 类别特征：ChannelId、Author、分类、标签
  │    └─ 序列特征（16维）：exp_cnt、read_cnt、read_end_cnt、to_next_cnt、read_pic_cnt等
  ├─ 交叉特征层：用户画像×内容分类、性别×内容类目等
  └─ 亲密度特征层：guid维度聚合 + guid-文章 + guid-puin
```

### 技术实现要点
- **图集特征**：数值特征（PicCount/ReadNum/ClickNum/ExpNum/ClickRate/QualityScore等）+ 类别特征（ChannelId/Author/分类/标签）+ 16维序列特征（用户-图集交互序列）
- **账号特征**：关注率/互动率多时间窗口（1h/1day/3day/1week/全时段），创作能力等级
- **亲密度特征**：guid维度互动汇总/真实曝光点击/时长，guid-文章和guid-puin聚合，输出用户-账号亲密度分
- **实时画像**：基于用户最近点击序列实时生成，用于实时召回和排序
- **特征上报**：seq_id、recall_reason后台透传，recall_score特征上报，用户最近点击序列上报

### 亮点与难点
- 16维序列特征的设计和工程实现，捕捉用户-内容交互的时序模式
- 亲密度特征从guid到guid-文章到guid-puin的多层聚合，精细化刻画用户-账号关系
- 多时间窗口统计特征（1h到全时段），兼顾短期兴趣和长期偏好
- 特征上报全链路打通，支持归因分析和模型迭代

### 量化结果（真实数字+来源）
- 图集模型AUC从0.546提升至0.639（特征+模型迭代共同贡献）（来源：06_看点图集/03主Feeds工作笔记.md）
- LR加入valid_ctr特征后线上CTR从0.1179提升至0.1219（来源：06_看点图集/05主Feeds优化进展.md）
- 图集序列特征维度：16维（来源：06_看点图集/02主Feeds模型信息.md）
- 账号关注率/互动率时间窗口：1h/1day/3day/1week/全时段（来源：05_UGC推荐/UGC推荐-特征体系.md）
- 具体单个特征的贡献度：材料中未记录

### 复盘与局限
- 特征重要性分析不足，未系统评估各特征的贡献度
- 序列特征仅16维，可扩展为更丰富的行为序列（如DIN/DIEN中的注意力序列）
- 特征管理平台化程度不够，特征上线仍需人工开发

### 可迁移点
- 推荐系统特征体系分层设计方法论
- 序列特征和亲密度特征的工程实现
- 多时间窗口统计特征的设计

### 面试话术
我在腾讯负责多个业务的特征体系建设。我把特征分成六层：基础数据、账号特征、用户特征、内容特征、交叉特征和亲密度特征。内容特征里我设计了16维序列特征，捕捉用户和图集的交互时序模式，包括曝光、阅读、读完、翻页、读图片数等。亲密度特征做了guid、guid-文章、guid-puin三层聚合，精细化刻画用户和账号的关系。账号特征用了1小时到全时段的多时间窗口统计，兼顾短期和长期。这些特征支撑了图集模型AUC从0.546涨到0.639，LR加valid_ctr特征后线上CTR从11.79%涨到12.19%。

## 子项目五：召回体系与负样本优化

### 产品定位（一句话）
为看点多业务搭建多路召回体系，并系统化优化召回负样本采样策略，提升召回模型的训练效果和线上召回质量。

### 背景与业务问题
- 早期召回只有画像和协同单路，覆盖率低、多样性差。
- 召回模型训练中负样本选择直接影响模型效果，随机负样本导致模型学不到"相关但不喜欢"的区分能力。
- 召回问题排查缺乏系统化方法论。

### 目标与核心指标
- 北极星：召回内容的点击率、转化率
- 过程：召回覆盖率、各召回源贡献占比、召回模型AUC

### 方案设计
```
多路召回体系
  ├─ 画像召回：现网画像 + 实时画像 + 标签扩展
  ├─ 协同召回：现网w2c + new_w2c + UserCF + 达人CF
  ├─ 深度召回：DNN召回 + YouTube DNN + deeprecall
  ├─ 向量召回：word2vec/fasttext + node2vec + Graph Embedding系列
  ├─ 热门召回：全局热门 + 分类热门 + 标签热门 + 分群热度
  └─ 兜底召回：威尔逊热门 + 协同兜底 + 随机兜底

负样本优化
  └─ 从"相关度不好"的样本中选负样本，而非随机采样
```

### 技术实现要点
- **召回实验框架**：50-61号桶系统实验各召回源（画像/协同/new_w2c/deeprecall/usercf/全局热门/标签/分类），配套粗排策略（7天点击率/威尔逊分数/综合打分）和兜底策略（82-88号桶）
- **标签扩展实验**：72-74号桶验证原tag+扩展tag召回 vs 只用原tag召回
- **负样本优化**：从"相关度不好"的样本里选负样本，让模型学习区分"相关但用户不喜欢"和"不相关"，提升召回精准度
- **召回问题排查**：建立召回为空、召回量少、召回不准等场景的系统化定位流程

### 亮点与难点
- 从1路召回扩展到8+路召回的完整建设，配套粗排、兜底、标签扩展全链路实验
- 负样本优化方法论：从随机负样本到"相关度不好"负样本的进阶，提升召回模型区分能力
- Graph Embedding系列（w2v→DeepWalk→LINE→Node2Vec）在召回中的完整实验和全量落地

### 量化结果（真实数字+来源）

## 子项目八：性能优化

### 产品定位（一句话）
针对推荐系统线上服务的性能瓶颈进行优化，包括模型推理效率、召回服务延迟、特征计算开销等，保证高并发下的服务稳定性和低延迟。

### 背景与业务问题
- 推荐系统线上服务高并发（QQ看点亿级用户），延迟要求高。
- 多路召回并行+模型推理+重排，计算链路长，容易出现性能瓶颈。
- 模型越来越复杂（从LR到DCN到MMoE），推理开销增大。

### 目标与核心指标
- 北极星：推荐请求P99延迟、服务可用性
- 过程：模型推理耗时、召回耗时、特征计算耗时

### 方案设计
```
性能优化方向
  ├─ 模型推理优化
  │    ├─ LR：共享内存在线预测，避免服务化开销
  │    ├─ DNN/MMoE：taf服务化，批量预测
  │    └─ 模型量化/裁剪（规划中）
  ├─ 召回服务优化
  │    ├─ 多路召回并行化
  │    ├─ Embedding ANN索引（FAISS等）
  │    └─ 召回结果缓存
  ├─ 特征计算优化
  │    ├─ 离线预计算 + 在线KV读取
  │    └─ 实时特征增量计算
  └─ 重排优化
       ├─ 分层quota减少候选集规模
       └─ 规则打散算法优化
```

### 技术实现要点
- **LR模型共享内存预测**：模型权重上传共享内存，在线直接读取预测，避免RPC开销，适用于低延迟场景。
- **多路召回并行**：各召回源独立并行执行，通过配置化框架管理，总耗时取max而非sum。
- **Embedding ANN检索**：向量召回使用ANN索引（如FAISS），毫秒级检索topN。
- **离线预计算**：用户画像、账号特征、内容特征等离线天级/小时级预计算，在线KV读取，避免实时计算开销。
- **分层quota**：重排阶段按层分配quota（0.5:0.3:0.2），减少后续排序的候选集规模。

### 亮点与难点
- 在模型从LR升级到MMoE的过程中，通过共享内存→taf服务化的部署策略，平衡了模型复杂度和延迟要求。
- 多路召回并行化设计，8+路召回总延迟控制在单路级别。
- 高并发场景下的服务稳定性保障。

### 量化结果（真实数字+来源）
- 具体延迟数据（P99/P95）：材料中未记录
- 并发量：QQ看点亿级用户规模（来源：业务背景）
- 多路召回数量：8+路并行（来源：06_看点图集/05主Feeds优化进展.md）
- 分层quota比例：0.5:0.3:0.2（来源：工作资料_腾讯/好友达人梳理（总）.md）
- 性能优化的具体提升幅度：材料中未记录

### 复盘与局限
- 性能优化的量化数据记录不足，难以评估优化效果
- 模型推理优化主要靠部署策略，未深入到模型层面的量化/蒸馏/裁剪
- 召回结果缓存策略未充分利用

### 可迁移点
- 高并发推荐系统的性能优化方法论
- 模型部署策略选择（共享内存vs服务化vs中台）的经验
- 多路召回并行化工程实践

### 面试话术
性能优化方面，我在腾讯面对QQ看点亿级用户的高并发场景，主要做了几件事：一是LR模型用共享内存在线预测，避免RPC开销；二是8路以上召回全部并行化，总延迟取最大值而不是累加；三是Embedding召回用ANN索引做毫秒级检索；四是特征大部分离线预计算，在线直接KV读取。模型从LR升级到MMoE时，我通过共享内存到taf服务化的部署策略，平衡了模型复杂度和延迟。重排阶段用分层quota把候选集规模降下来，减少排序开销。
