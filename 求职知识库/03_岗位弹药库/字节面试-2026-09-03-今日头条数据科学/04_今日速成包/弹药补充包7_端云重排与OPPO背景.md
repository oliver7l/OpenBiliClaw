## 💣 弹药22 · 端云重排项目全景（架构前沿 · 今日强主菜候选）

### 项目背景（一页讲清）
```
场景：腾讯小世界/信息流（mqqrecommend 链路）主端策略下发后的"最后一公里"重排
问题：分页请求导致主端策略调整不及时 → 用户实时行为没法立即反映到待播放列表
方案：把重排拆成"云上重排 + 端上重排"两条通路，互为补充，用端云实时链路快速响应刷次内反馈
分工：
  云上重排 = 覆盖绝大多数用户，端-云实时链路快速落地收益，横向支持新用户/兴趣探索/商业化
  端上重排 = 高端机型+高消人群，利用客户端更实时、更细粒度的特征建模即时兴趣，探索新推荐范式
架构：主端混排（正常召回排序返回一刷列表）→ 云上重排（触发式，独立服务，含融合/多样性/槽位机制）
      → 端上重排（端上 buffer 候选做重排，异步拉取部分 feed 详情曝光）
```

### 完整话术（可直接背，讲前先确认归属）
> "我讲一个我在腾讯做的**端云重排**项目。背景：主端策略按分页请求下发结果，但**分页导致策略调整不及时**——用户刷到一半兴趣变了，待播放列表却没跟上。我参与设计了**端云两条重排通路**来解这个问题：
>
> **云上重排**：覆盖绝大多数用户，通过端-云实时链路，根据用户刷次内的实时消费行为触发云端重排——独立部署一套服务、和主端混排解耦，自带融合、多样性、槽位机制，召回内容区别于主端（含未曝光 feed 和多种定向召回）。它的价值是**快速落地收益**，还能横向承接新用户优化、兴趣探索、商业化等业务。
>
> **端上重排**：在高端机型和高消费人群上生效，利用**客户端上更实时、更细粒度的特征**（实时曝光、滚动速度、停留时长等）建模用户的即时兴趣，在端上 buffer 的候选里做实时重排，不重新请求主端。它的意义是探索一种**新的推荐范式**——把端侧算力变成推荐系统的算力扩展。
>
> 两个方向定位互补：云上重排求快、覆盖广，端上重排求深、个性化强，整体服务于提升大盘消费指标和产品体验。"

### ⚡ 追问链
- **"为什么需要端云重排，直接减少分页 size 不行吗？"** → 减少分页 size 能缓解，但用户×推荐系统交互指数级增长，QPS 还是扛不住；而且受带宽和隐私限制，客户端实时特征利用不充分。端上重排能把部分计算下沉到端侧。
- **"端上重排和云上重排怎么分工？"** → 云上覆盖全量、快速落地；端上在高消人群/高端机型上做更细粒度的即时兴趣建模，是新的范式探索；两者通过端云实时链路配合。
- **"端上 buffer 怎么填？"** → 策略层按多样性或特定规则生成固定数量候选队列，把 feedid 下发到客户端，客户端异步拉取部分 feed 详情用于曝光。
- **"端云重排和主端重排什么关系？"** → 都是对主端策略下发的列表做优化，端云重排解决的是**分页导致的主端调整不及时**问题，是对待播放列表的实时微调。

## 💣 弹药23 · 云上重排：Pointer Network 建模重排序列生成（模型亮点）

### 项目要点
```
问题：云上重排 = 从候选 list 里选出一个"最优顺序"的序列生成问题（重排本质是 Listwise）
方案：Pointer Network（Ptr）建模序列生成
  一期 = single-task 模型
  Encoder：GRU dynamic_rnn 对 item embedding 编码
  Decoder：对 list 里每个 item 逐一用 GRU 解码，每次解码获得"多样性得分 + mask 分数"
    - 多样性得分：判断 list 内 item 相似度，越高则多样性得分越低（鼓励多样性）
    - mask 分数：由 attention 得到（encoder 输出作 reference，decoder 初解作 query），调整排序概率
    - 特征通过多个全连接层预测每个 item 的排序概率/位置索引/分数
损失：MSE / hinge loss / CE loss（训练对 list 逐元素解码，标签复制成列表长度，label_mask 处理选中与补零）
训练技巧：先预测再训练，引入上一训练状态信息
```

### 完整话术（可直接背）
> "云上重排我核心做的，是把重排建模成**序列生成问题**，用 **Pointer Network** 来做。为什么用 Pointer Network？因为重排的挑战是：候选集合大小不固定，输出是一个'重新排序后的序列'，而传统 seq2seq 固定了输出集合范围，无法灵活改变输出长度。Pointer Network 的核心是**把 attention 当指针**——每次解码从输入序列里选一个元素作为输出，天然适合'从候选 list 里选出一个最优顺序'。
>
> 我的具体设计：encoder 用 GRU 对候选 item 编码；decoder 对每个位置逐一解码，关键在两个创新点——**①多样性得分**：实时判断 list 内 item 的相似度，相似度越高得分越低，在解码时抑制连续推相似内容；**②mask 分数**：通过 attention（encoder 输出作 reference、decoder 初解作 query）调整每个 item 被选中的概率，避免重复选择。损失我对比了 MSE / hinge / CE，用 label_mask 同时处理'是否被选中'和'是否补零'。
>
> 这个方案的优点是：解码阶段能利用编码特征避免信息丢失、先预测再训练能引入上一步状态、多样性打分让重排不只看单一分数。缺点我也很清楚：一期是单塔结构较单一、多样性策略偏简单、依赖高质量标签监督。所以后续规划是加召回塔做双塔、用相关性更强的特征细化多样性判别、以及对比 transformer 结构。"

### ⚡ 追问链
- **"为什么重排是序列生成问题？"** → 重排要输出一个完整顺序，不是逐 item 独立打分；item 之间的相对顺序、多样性约束都依赖序列上下文。
- **"Pointer Network 和 seq2seq 区别？"** → seq2seq 输出来自固定词表、长度固定；Ptr 的输出是指向输入序列位置的指针，长度灵活、可处理变长候选集合。
- **"多样性得分和 mask 分别解决什么？"** → 多样性得分解决"连续推相似内容"的体验问题；mask 解决解码时"重复选同一个 item"和"注意力偏移"的问题。
- **"为什么用 GRU 不用 transformer？"** → 一期用 GRU 简单高效；后续规划对比 transformer（如 self-attention 建模 item 间长距离依赖），这是优化方向之一。
- **"怎么评估重排效果？"** → 序列排序指标（NDCG/MAP/Precision@5）+ 业务指标（完播率、时长、退出率），配合消融和线上 AB。

## 💣 弹药24 · 端上重排：EdgeRec 式实时重排 + 模型消融实验（数据详实）

### 项目要点
```
背景：服务器端无法及时响应 → 端上实时重排（EdgeRec CIKM2020 思路）
方法：
 1) 端上实时用户感知：商品曝光行为序列（关注负反馈：曝光未点击）+ 商品详情页行为序列（关注交互程度）
    - item 与 action 是异构输入 → 分别 encode（item 用 GRU、action 用 Identity）再 Concat 融合
 2) 端上实时重排：context-aware ranking（RNN/Transformer 或全局特征+DNN）
    - 两种上下文：待排序商品间上下文（GRU 编码）+ 用户实时行为上下文（Attention：待排序商品为 Query、行为序列商品为 Key/Value）
模型消融实验（真实数据）：target attention 有效；dynamic/cross 特征多数有效；static（用户画像等）多数效果不明显；
   静态特征消融训练更稳定 → 说明动态行为特征对模型帮助大；loss 稳定在 0.14
深消 PRM 模型（重排 Transformer）：
   - 用 2D 卷积融合 multi-head 特征（原本多头直接 concat 降维，信息交互不充分）
   - 实验：n_head=4 + 4 层卷积最优：val_precision_5 0.57408 / val_map_5 0.7440 / val_ndcg_5 0.7545（vs baseline 0.57042/0.7421/0.7522）
   - 其他探索：局部注意力、胶囊网络多兴趣、动态 mask 稀疏化 attention
```

### 完整话术（可直接背）
> "端上重排我参考了 **EdgeRec（淘宝 CIKM 2020）** 的思路，核心是**端上实时用户感知 + 端上实时重排**。
>
> 实时用户感知我做了两块：**商品曝光行为序列**——不只关注点击这类正反馈，更关注**负反馈**（曝光未点击），因为某类目实时多次曝光不点击，说明用户当下兴趣变了；**商品详情页行为序列**——关注交互程度（停留时长、加购、收藏），区分'真点击'和'伪点击'。关键设计是：item 和 action 是**异构输入**，先分别 encode（item 用 GRU、action 用 Identity）再 Concat 融合，避免曝光行为主导序列。
>
> 实时重排用的是 **context-aware ranking**：同时利用两种上下文——待排序商品之间的上下文（GRU 编码）+ 用户实时行为的上下文（Attention：待排序商品做 Query，行为序列商品做 Key/Value），相当于'看看用户刚交互过的东西长啥样，再决定当前候选怎么排'。
>
> 我还做了**系统的消融实验**（真实线上数据）：验证 **target attention 最有效**；dynamic（行为）和 cross 特征大多数情况有效；而 static（画像、性别）多数效果不明显——静态特征消融后训练更稳定，反证动态行为特征对模型帮助最大。在重排模型 PRM 上，我用**2D 卷积融合 multi-head 特征**（原来多头直接 concat 降维，信息交互不充分），实验下来 **n_head=4 + 4 层卷积最优**，Precision@5 从 0.5704 提到 0.5741、NDCG@5 从 0.7522 提到 0.7545。"

### ⚡ 追问链
- **"端上重排最关键的输入是什么？"** → 客户端实时行为特征：实时曝光（含负反馈）、滚动速度/方向、详情页停留、加购收藏——这些是云端拿不到或拿不全的。
- **"为什么 item 和 action 要分开 encode？"** → 异构输入；点击稀疏、曝光密集，合成一条序列会被曝光主导；同构输入做 attention 才有意义。
- **"消融实验结论怎么指导建模？"** → 资源有限时优先保 target attention 和动态特征，static 可以砍，减小模型不损失效果。
- **"PRM 卷积融合多头为什么有效？"** → 多头 attention 各自算完直接 concat 丢失了头间交互，卷积在 seq_len×n_head 特征图上做局部感受野，让多头信息交互更充分。
- **"端上模型怎么上线？"** → 端侧模型要小（大模型端上跑不动），倾向轻量模型+云侧蒸馏下发（呼应弹药25 的 DCCL/COLLA）。

## 💣 弹药25 · 端云协作学习 + 论文综述（学术深度加分）

### 项目要点（论文综述归档-琳洁）
```
端上推荐：EdgeRec（端上实时感知+重排）、COLLA（云端双向蒸馏协作学习）、DCCL（端云协作训练）
  - COLLA：云训练初始模型→压缩下发→端用本地数据微调（云作教师、端作学生蒸馏）→端模型回传（端作教师、云作学生）→分组聚类云模型（K组）
  - DCCL：云端 pre-train → 端上 personalization（MetaPatch：插入 adapter + 超网络减少参数）→ 收集端模型做 Model-over-Models 蒸馏（MoMoDistill）
用户行为建模：DFN（显式/隐式正负反馈）、DIN/DIEN/DSIN/DMR/SeqFM/MIND（兴趣/多兴趣）
多目标：MMoE、PLE、ESMM
Listwise：PRM、DLCM、SetRank
```

### 完整话术（可直接背）
> "端云重排里我系统性调研了**端云协作学习**的论文，最有启发的是三篇：**EdgeRec** 给端上实时感知+重排打了样；**COLLA** 讲了云和端怎么**双向蒸馏**——云模型压缩下发给端、端用本地数据微调、端模型再回传蒸馏给云，而且把设备聚类成 K 组做分组云模型，兼顾算力和行为多样性；**DCCL** 更进一步，用 **MetaPatch**（在模型中间插 adapter + 超网络把个性化参数大幅压缩）在端上做个性化，再用 **MoMoDistill**（Model-over-Models）蒸馏回云。
>
> 这些给我端的端云架构提供了理论支撑：**云侧给通用能力，端侧做个性化微调，双向知识蒸馏保证不脱节**——这也是端云重排区别于单纯'端上跑个模型'的关键。"

### ⚡ 追问链
- **"端云协作最大的难点？"** → 模型压缩（云端大模型端上跑不动）+ 个性化与全局能力平衡 + 双向蒸馏的通信/隐私成本。
- **"MetaPatch 为什么能减参数？"** → 在层间插 adapter，用超网络生成 adapter 参数（只学小矩阵 Θ̂），避免端上全量训练或只训最后几层受限于预训练。
- **"端云数据隐私怎么处理？"** → 端上特征不出设备做个性化，云端只收模型更新/蒸馏信号，天然符合隐私要求。

## 💣 弹药26 · OPPO 背景：全场景统一建模 + 智能算力降本（平台侧弹药）

> ⚠️ 这是 **DataFun 公开访谈**（OPPO 推搜算法部总经理赖洪科，2023-12），不是用户本人作品。用法：作为"我在 OPPO 期间熟悉的方向/团队实践"谈平台侧与降本增效，**不要冒充是自己做的**。

### 项目要点
```
全场景统一建模（软件商店+游戏中心打通）：
  - 问题：应用分发近 20 个场景数据割裂、小场景特征稀疏估不准
  - 方案：全局特征共享 + 全局样本融合的数据底座（软件商店 85%+ 下载、数据最丰富）
  - 效果：KV 存储 2T→30T、特征 1 亿→100 多亿；游戏中心推荐从"怎么调都不达预期"到成倍提升
  - 架构：全局网络（共性）+ 个性化局部网络（个性），类似大模型+小模型
  - MMOE 建模：oCPX 场景 4 模块×5 转化指标 = 20 种 CVR 模型 → 浅层/深层目标共享 embedding，极大减少模型数、保证转化
智能算力（降本增值）：
  - V1.0：动态限流阈值 + 用户分层（低价值限流保高价值）→ 同资源下流量支撑 +15%、营收 +15%
  - V2.0：个性化价值预估"打假"（找准 VIP、低价值降级服务）→ 同资源流量支撑 +20%、营收再增长
  - V3.0：20% 流量承载 80% 价值 → 高质量用户增配算力
oCPX：广告主选优化目标（观看/下载/注册/付费），系统预估转化率+期望成本自动出价，成本效果稳定
```

### 完整话术（可直接背，OPPO 口径）
> "我在 OPPO 时对**推荐系统的降本增效和全场景统一建模**有比较深的理解。核心问题是：应用分发有接近 20 个场景，数据割裂、小场景特征稀疏'怎么估都估不准'。我们的方案是**全场景统一建模**——把软件商店和游戏中心的数据打通，因为 85% 以上的下载都发生在软件商店，它数据最丰富，用来增强稀疏的游戏中心场景，效果成倍提升；KV 存储从 2T 扩到 30T、特征从 1 亿扩到 100 多亿。架构上走**全局网络+个性化局部网络**的组合（共性+个性）。
>
> 多目标上用 **MMOE**：oCPX 有 4 个模块×5 个转化指标 = 20 种 CVR 模型，数量多难维护、深转化样本稀疏；MMOE 让浅层和深层目标**共享 embedding**，极大减少模型数量，还保证甚至提高了转化率，目标越深越需要更强的个性化网络。
>
> 算力侧做了**智能算力降本**三阶段：V1.0 动态限流+用户分层，同资源流量支撑+15%、营收+15%；V2.0 做个性化价值预估、给低价值流量降级，同资源流量支撑再+20%；V3.0 洞察到 20% 流量承载 80% 价值，给高质量用户增配算力。"

### ⚡ 追问链
- **"全场景统一建模怎么避免负迁移？"** → 全局共享底座负责共性，个性化局部网络负责场景差异（类似 MMoE 门控/大模型+小模型），任务相关性用模型结构隔离。
- **"为什么 MMOE 能减模型数？"** → 共享 embedding + 多塔，浅层目标帮深层目标学稀疏样本，不用每个转化目标各训一个模型。
- **"智能算力降本会不会伤用户体验？"** → V1 用用户分层保高价值；V2 改降级服务而非直接限流；V3 增配 VIP——从'无感优化'到'质量提升'递进。

## 💣 弹药27 · 行业前沿趋势（大厂 576 篇索引提炼）

> 来源：大厂实践文章精选（576 篇，2024-2025）。面试被问"你怎么看推荐/广告最新趋势"时用，展示你一直在跟踪前沿。

### 六大趋势（背下来）
1. **端到端生成式推荐**：快手 OneRec/OneSearch、美团 MTGR 生成式推荐 Scaling Law、阿里 RecIS——从"召回-排序分模块"走向"一个模型端到端生成候选"
2. **生成式排序/召回**：百度 GRAB/生成式广告召回、腾讯混元生成式召回——把召回/排序变成条件生成
3. **大模型+推荐**：腾讯 LFM4Ads（全平台 GMV +2.45%）、阿里妈妈 URM 召回大模型、相关性大模型蒸馏——LLM 做多粒度知识迁移/召回
4. **多目标/多任务持续深化**：快手 EMER 端到端多目标排序、多归因学习 CVR（MAL）、级联排序一体化（LCRON）
5. **重排在线学习**：淘宝 LAST——重排从离线到在线学习范式
6. **因果/数据科学**：多目标&因果标签贯穿；用户增长/用增精细化

### 话术（可直接背）
> "我平时持续跟踪大厂实践。看到几个明显趋势：**一是端到端生成式推荐**，像快手 OneRec、美团 MTGR、阿里 RecIS，用一个大模型端到端生成候选，替代分模块召回-排序；**二是生成式排序和生成式召回**，百度 GRAB、腾讯混元生成式召回，把排序变成条件生成；**三是大模型做多粒度知识迁移**，腾讯 LFM4Ads 用全表征基础大模型把 GMV 提升 2.45%；**四是多目标继续深化**，像快手 EMER 端到端多目标排序、阿里妈妈多归因 CVR。这些和我做的方向是呼应的——我做过 MMoE/ESMM 多目标、做过 Pointer Network 做序列重排，本质上都在往'序列级、端到端、多目标'演进。"
