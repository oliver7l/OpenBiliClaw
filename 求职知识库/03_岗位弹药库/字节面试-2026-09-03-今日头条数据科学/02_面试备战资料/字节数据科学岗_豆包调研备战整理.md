## 第一部分：SQL 连续登录 N 天算法（岛屿缺口 gap-and-islands）

### 核心思想
同一连续片段内，`dt - 行号rn` 得到的分组标记 grp 是同一个值，中断后 grp 变化。

### 完整分层
1. 内层 t：`distinct uid, dt` 去重（每用户每天只留1条，**漏写直接扣分**）
2. 内层 t2：`row_number() over(partition by uid order by dt)` 生成 rn
3. 内层 t3：`date_sub(dt, interval rn day)` 生成 grp 分组键
4. 外层：`group by uid, grp`，`count(*)` = 连续天数，`having >=7`，最后 `distinct uid`

### 高频追问
- 为什么 distinct uid,dt？→ 不去重会生成多个 rn，破坏 dt-rn 逻辑
- Hive 写法：`date_sub(dt, rn)` 直接写数字，不用 interval
- 只能用 row_number（rank跳号、dense_rank不适合）
- 与 lag 对比：lag 适合找断点，gap-islands 适合求最长连续/任意一段连续N天

### 6 种连续行为统计算法对比（背这个表）

| 算法 | 核心思想 | Hive原生 | 求最大连续 | 适用场景 |
|---|---|---|---|---|
| Gap-Islands 岛屿 | `dt-row_number()`生成分组ID | ✅ | ✅ | 批处理天粒度，通用 |
| LAG+断点累计 | 标记断点，sum得group_id | ✅ | ✅ | 可读性高，可自定义间隔阈值 |
| LAG固定偏移 LAG(dt,k) | 向前偏移k行做日期差 | ✅ | ❌ | 固定N，只判断是否存在连续N |
| 递归CTE | 迭代向后扩展片段 | ❌ | ✅ | 小数据集MySQL，大数据性能差 |
| 多表自连接JOIN | N-1次JOIN匹配 | ✅ | ❌ | N很小，无窗口函数老版本 |
| Session会话窗口 | 超时gap分割会话 | ❌(Spark支持) | ✅ | Spark/Flink流批一体，非严格连续 |
| 日历笛卡尔积 | 补全时间轴再分割 | ✅ | ✅ | 需补全缺失日期 |

### 岛屿缺口优缺点
**优点：** 代码简洁一步生成分组ID；通用性强支持任意N、能求最长连续、能拿起止时间；一次扫描性能好；模板可复用到签到/复购/打卡。
**缺点：** 必须先 uid+dt 去重否则全错；只支持天粒度（小时/分钟级要用lag）；grp是date类型略占存储；理解门槛高不直观。

### 完整可运行 SQL（Hive，来自第二份对话，代码最全）

**① 岛屿缺口 gap-and-islands（标准写法）**
```sql
SELECT DISTINCT uid FROM (
    SELECT uid, date_sub(dt, rn) AS grp FROM (
        SELECT uid, dt,
               ROW_NUMBER() OVER(PARTITION BY uid ORDER BY dt) AS rn
        FROM (SELECT DISTINCT uid, dt FROM login_log) t1
    ) t2
) t3
GROUP BY uid, grp
HAVING COUNT(*) >= 7;
```

**② LAG + 断点累计法（可读性强，可输出起止时间）**
```sql
WITH t_distinct AS (SELECT DISTINCT uid, dt FROM login_log),
t_lag AS (
    SELECT uid, dt, LAG(dt,1) OVER(PARTITION BY uid ORDER BY dt) AS prev_dt
    FROM t_distinct),
t_flag AS (
    SELECT uid, dt,
           CASE WHEN DATEDIFF(dt, prev_dt)=1 THEN 0 ELSE 1 END AS is_break
    FROM t_lag),
t_group AS (
    SELECT uid, dt, SUM(is_break) OVER(PARTITION BY uid ORDER BY dt) AS group_id
    FROM t_flag)
SELECT DISTINCT uid FROM t_group
GROUP BY uid, group_id HAVING COUNT(*)>=7;
```

**③ LAG(dt, N-1) 固定偏移（固定N，不能求最长连续）**
```sql
WITH t_distinct AS (SELECT DISTINCT uid, dt FROM login_log),
t_offset AS (
    SELECT uid, dt, LAG(dt,6) OVER(PARTITION BY uid ORDER BY dt) AS dt_6before
    FROM t_distinct)
SELECT DISTINCT uid FROM t_offset WHERE DATEDIFF(dt, dt_6before)=6;
```

**④ 递归 CTE（MySQL8/Spark支持，Hive不支持，大数据禁用）**
```sql
WITH RECURSIVE t_rec AS (
    SELECT DISTINCT uid, dt, 1 AS continue_cnt FROM login_log
    UNION ALL
    SELECT r.uid, l.dt, r.continue_cnt+1
    FROM t_rec r JOIN login_log l
      ON r.uid=l.uid AND DATEDIFF(l.dt, r.dt)=1)
SELECT DISTINCT uid FROM t_rec WHERE continue_cnt>=7;
```

**⑤ 多表自连接（N-1次JOIN，N大爆炸，仅了解）**
```sql
SELECT DISTINCT t1.uid FROM login_log t1
JOIN login_log t2 ON t1.uid=t2.uid AND DATEDIFF(t2.dt,t1.dt)=1
JOIN login_log t3 ON t1.uid=t3.uid AND DATEDIFF(t3.dt,t1.dt)=2
-- ...连续7天需JOIN 6次，t7 DATEDIFF=6
;
```

**⑥ 次日留存率（left join，不能inner join）**
```sql
WITH user_first AS (SELECT uid, min(dt) AS first_dt FROM login_log GROUP BY uid)
SELECT first_dt AS stat_dt,
       count(DISTINCT d.uid) AS new_user_cnt,
       count(DISTINCT l.uid) AS retain_cnt,
       round(count(DISTINCT l.uid)/count(DISTINCT d.uid),4) AS next_day_retention
FROM user_first d
LEFT JOIN login_log l ON d.uid=l.uid AND datediff(l.dt,d.first_dt)=1
GROUP BY first_dt;
```

**⑦ 行为漏斗（首页→列表→详情→下单，按用户打标后聚合）**
```sql
WITH user_step AS (
    SELECT uid,
      max(CASE WHEN event_name='home'   THEN 1 ELSE 0 END) step1,
      max(CASE WHEN event_name='list'   THEN 1 ELSE 0 END) step2,
      max(CASE WHEN event_name='detail' THEN 1 ELSE 0 END) step3,
      max(CASE WHEN event_name='order'  THEN 1 ELSE 0 END) step4
    FROM event_log GROUP BY uid)
SELECT sum(step1) home_cnt, sum(step2) list_cnt,
       round(sum(step2)/sum(step1),4) home2list_rate,
       sum(step3) detail_cnt,
       round(sum(step3)/sum(step2),4) list2detail_rate,
       sum(step4) order_cnt,
       round(sum(step4)/sum(step3),4) detail2order_rate
FROM user_step;
```

## 第四部分：面试真题 + 参考答案

### SQL
- **连续登录7天（2种实现+对比）**：岛屿 vs LAG断点
- **次日留存**：left join 不能 inner join（否则丢失未留存用户）
- **数据倾斜场景与解决**：
  - join倾斜：skewjoin、热点key随机加盐打散后聚合
  - count distinct：先 group by 再 count
  - group by倾斜：groupby.skewindata
  - null倾斜：null随机赋值打散
- **漏斗转化**：首页→列表→详情→下单每步转化率

### 统计 & AB实验
- **一二类错误**：α假阳性(没效当有效,取0.05)、β假阴性(有效当没效)、1-β=power(≥0.8)；调高α则一类升二类降；加大样本量可同时降低
- **样本量影响因素**：基线值、MDE最小可检测效应、α、power、渗透率/日活/周期；预留10-20%余量
- **SRM样本比例不匹配**：期望1:1实际显著偏离，结果不可信。排查：分流算法/seed/hash→实验过滤逻辑→人群分布→埋点丢失→上游数据过滤
- **核心涨护栏跌要不要全量**：不直接全量。确认统计可靠(SRM/p值/污染)→拆解是全局还是子集→分析因果→权衡价值(收益远大于损失可灰度,护栏若是留存/时长长期负向则不全量)→迭代新版本
- **辛普森悖论**：整体A优但每个子集B优，因人群结构差异。规避：分维度下钻、保证分流人群结构均衡
- **p>0.05不显著**：增样本拉周期、CUPED方差缩减、评估MDE、分人群挖掘、排查污染/SRM、确实无效及时停

### 业务Case
- **DAU下跌5%排查框架**：确认数据真实性(埋点/口径/多源交叉)→时间维度(断崖/渐变/同期对比)→维度下钻(新老/渠道/设备/版本/地域 + 各模块)→内外事件(版本策略/活动/节假日竞品舆情)→定位根因复现验证
- **投稿量下降**：投稿量=活跃作者数×人均篇数(先判断人少还是发的少)→头中尾部/新老/垂类下钻→投稿漏斗(打开创作页→编辑→提交)→排查改版/审核/激励/竞争
- **作者激励策略评估**：定目标→核心指标(投稿UV/篇数/优质占比)+护栏(留存/低质/投诉)→AB均衡分流→分层看头腰尾尾→看长期留存→成本收益→复盘迭代

### 项目深挖灵魂问题
- 真实贡献/哪些独立完成/最大困难
- 产品不接受你的结论：对齐假设分歧点→统一口径多源验证→补分维度+小流量实验→理解顾虑做折中灰度→争取试点用结果说话
- 主动发起项目STAR模板
- AB不及预期：排查可靠性→分维度(正负抵消)→回看假设→护栏副作用→定性反馈→迭代或停止
