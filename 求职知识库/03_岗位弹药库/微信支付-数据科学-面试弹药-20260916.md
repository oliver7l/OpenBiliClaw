## 1. NL2SQL：用「用户侧证人」身份讲

**定位选择**：不冒充「我研发过 NL2SQL 平台」（没做过，一追问就穿），而是讲「我是 NL2SQL 最典型的重度目标用户 + 口径治理参与者，我清楚它难在哪、该怎么做」。这在面试里是加分的清醒。

**痛点故事（真实，可放心讲）**：
> 行内取数：写 SQL→对口径→核数→出报告，一个客群分析周报的取数和口径核对占掉大量时间；六大渠道口径不统一时，同一个「转化率」能算出好几个数。所以我对「自然语言→SQL」的真实难点有体感。

**如果让我建 NL2SQL，我会怎么做（展现工程判断力）**：
1. **口径层优先于模型层**：先建指标口径词典/语义层（指标名→口径 SQL 模板→维度），很多「text-to-SQL」失败不是模型不行，是口径没定义清楚——我在行内做过口径统一，这是我最想先解决的问题。
2. **Schema linking**：表/字段元数据 + 业务注释 + 高频问答对做检索增强，不是把几百张表全塞 prompt。
3. **模板与生成混合**：高频固定报表走模板（准确率近 100%），长尾探索查询走生成。
4. **执行前校验与兜底**：生成 SQL 白名单校验（只读、行数限制）、结果合理性检查（环比突异告警）、置信度低时反问用户澄清。
5. **评测体系**：建业务问题→标准 SQL 的评测集，按执行准确率/口径命中率分层汇报，这也是 JD 里「评测体系搭建」的答法。

**常见追问**：
- 「NL2SQL 准确率上不去怎么办？」→ 分层：口径类问题用语义层消灭；长尾靠 few-shot 检索 + 人工反馈回流；关键决策场景保留「生成 SQL + 人工确认执行」的半自动模式（金融场景合规也要求这样）。
- 「Text-to-SQL 和 Agent 版有什么区别？」→ Agent 版 = NL2SQL 只是工具之一，外面套规划（拆解问题→查表→生成→执行→可视化→归因解读）+ 评测 + 记忆（用户偏好/口径纠错沉淀）。

## 2. DataAgent / RAG：行内试点怎么讲

**可讲的框架（基于你确认过的真实试点，具体细节按实际替换）**：

- **知识库问答试点**：讲清楚 ①知识从哪来（制度文档/产品手册/历史报告？〔待核对〕）②检索方案（向量检索+关键词混合？切片粒度？〔待核对〕）③效果与问题（幻觉怎么发现和抑制：引用原文出处、限定知识范围、置信度兜底）。
- **报告自动生成试点**：①输入是结构化数据还是文本（〔待核对〕）②「模板+数据填充」还是「LLM 自由生成」（金融场景几乎必然是模板骨架+LLM 润色解读，这个答法最稳）③人工审核环节怎么设计。

**加分答法——评测体系视角（JD 原文「评测体系搭建」）**：
> 我做策略建模出身，习惯「没有度量就不要上线」：问答试点要建评测集（问题-标准答案对），按事实准确率/引用正确率/拒答正确率打分；金融场景里「该拒答时拒答」和答对同样重要。

**知识图谱**（JD 提到但我们没做过）：诚实说没在生产里用过 KG，但能讲清适用边界——支付场景里实体关系（商户-法人-设备）用 KG 强，开放域问答用 RAG 够；如果建 DataAgent，会把「指标口径关系图」当轻量 KG 用（指标→口径→上游表→负责人），这个我有真实语料感。

## 3. SFT 微调：守原句，细节先核对

简历措辞（已定稿）：**「完成领域数据的SFT微调，探索LLM在金融场景的应用」**——就讲到这个粒度。

**⚠️ 追问应对原则：以下框架可讲，〔待核对〕项必须先换成你的真实情况，否则宁可答「这块我不方便展开细节」**：
- 基座是什么（行内采购的开源模型？哪个版本？〔待核对〕）
- 数据从哪来多少量（客服记录/产品文档构造指令对？〔待核对〕）
- 微调方式（全参还是 LoRA，工具链？〔待核对〕）
- 效果怎么评（人工评估 vs 自动指标？〔待核对〕）

**安全的通用答法**（不依赖未核对细节）：
> 试点的目标不是刷指标，是验证「领域微调能不能让模型理解我们的业务术语和口径」；我的角色在数据侧——构造/清洗领域指令数据、设计评估用例。结论是通用底座+检索增强已能覆盖大部分场景，微调的价值在风格对齐和术语一致性。这段经历让我对「什么时候该微调、什么时候 RAG 就够」有实操判断。

**个人 LLM 项目**（不进简历，面试聊）：被问「平时关注/动手过什么」时，用你真实的个人项目佐证工程热情，可自然衔接到「所以看到这个 DataAgent 岗位特别对口」。
