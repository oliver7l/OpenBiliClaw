## 一、音乐推荐 vs 通用推荐：五个本质差异（开场就能讲）

1. **反馈信号不同**：电商看"买/不买"，音乐看"**听多久/什么时候切**"。一首歌播放≠喜欢，**切歌时机才是核心信号**（3 秒切 vs 3 分钟切含义完全不同）。行为粒度更细、反馈更快（一首歌 3-4 分钟就完成一次"转化/流失"判定）。
2. **负反馈权重极高**：Spotify 把「前 30 秒切歌」作为最重的负信号；完播权重约为部分收听的 3 倍；收藏（save）是最强正信号，加歌单其次（表示"这首歌属于我生活某场景"），分享是主动背书。
3. **消费是"流"不是"点"**：音乐是 session 制连续消费（电台/歌单连续听 30 分钟+），前一首决定后一首的状态 → **序列建模（session-based）是主场**，点式 CTR 排序不够。
4. **强内容属性**：音频本身可建模（节奏/BPM/能量/valence/音色），是新歌冷启动唯一可靠信号——行为数据为零时，**音频嵌入是救命稻草**。
5. **约束特殊**：版权（部分歌不可推/限地区）、艺人疲劳（同一歌手不能连续推 N 首）、歌单/电台是"产品形态"而不只是"结果形态"。

## 二、信号体系与切歌建模（QQ 音乐：最值得背的细节）

### 2.1 行为分两档（QQ音乐口径）
- **重度实时行为**（态度鲜明，简单规则即可）：收藏、下载、删除（不再播放）→ 直接正/负反馈进推荐。
- **暧昧行为**（需模型判别）：**切歌**。切歌受环境/心情影响大，且切歌时机有深意。QQ音乐用 Logistic 类模型综合 **歌手、流派、切歌时机** 等因素输出 0-1 的真实态度分——只凭一次切歌就拉黑歌手会"南辕北辙"。

### 2.2 冷启动试探顺序（QQ音乐实证，面试可背）
**语言 > 歌手 > 流派**。90% 用户听中英文歌，最不能忍的是不喜欢的语言（外文歌），其次是歌手，再次才是流派。冷启动策略：先中英文混合 → 根据收藏/切歌锁语言 → 试探歌手锁区间 → 转常规推荐。

### 2.3 画像体系
- **用户画像 6 维**：内容偏好（歌手/语言/年代/流派）、社交属性（腾讯生态年龄性别职业）、场景偏好、人群属性、听歌时间段、**黑名单（厌恶建模）**。
- **音乐画像 6 维**：歌手、音频特征（MFCC/pitch）、热度统计、流派、情感标签（伤感/安静/思念）、乐器。
- **"音乐肖像"**：行为序列模型 + 语义分析结合，动态刻画用户音乐个性。

## 三、Spotify 体系：BaRT 与产品矩阵（全球标杆，必讲）

### 3.1 BaRT（Bandits for Recommendations as Treatments）
- 本质：**上下文多臂老虎机 + 因果推断**。把每次推荐当"治疗"（treatment），度量相对备选的增量（uplift 思维！与你已备的因果推断弹药直接连通）。
- **30 秒规则**：播放超 30 秒 = 成功，30 秒内切 = 失败。这是 BaRT 自评的目标函数。
- **Explore/Exploit**：epsilon-greedy 平衡；新用户偏 explore，老用户偏 exploit。论文《Explore, Exploit, Explain: Personalizing Explainable Recommendations with Bandits》（RecSys 2018）。
- 上下文特征：设备（手机=短session、智能音箱=背景音、车载=蓝牙场景）、时段（早=chill 晚=energetic）、耳机 vs 外放。

### 3.2 三大数据支柱
1. **协同过滤**（矩阵分解起步 → 后续嵌入化）
2. **音频分析**：tempo/key/energy/timbre/valence（源自 EchoNest），驱动 Radio 与相似歌曲
3. **NLP 文化向量**：爬博客/乐评/播放列表标题，理解"这首歌在网上怎么被谈论"，捕捉流派/情绪/文化语境

嵌入规模：歌曲/用户 128-256 维向量，**FAISS ANN（HNSW）** 毫秒级检索亿级曲库。

### 3.3 产品矩阵 = 场景化推荐（每个入口一套逻辑）
| 产品 | 机制 | 更新 |
|---|---|---|
| Discover Weekly | CF 为主 + 音频 + 社交信号 | 每周一，30 首，人均独立生成（每周 7500 万个独立歌单），累计 23 亿小时收听 |
| Release Radar | 关注关系 + 听歌邻近（没关注但听同类也给） | 每周五，新歌 |
| Radio / Autoplay | 音频相似 + session 延续信号 | 实时 |
| Daily Mix | 流派聚类（探索+熟悉混合） | 每日 |
| daylist | 按时段学"你周二上午 vs 周五深夜听什么" | 一天多次 |

**惊喜感设计**：Discover Weekly 刻意掺 ~30% 计划外推荐平衡熟悉与新颖（对抗 filter bubble）；学术研究证实高个性化平台用户流派探索反而更窄——**"惊喜感/探索"是音乐推荐特有的优化目标**（网易云用深度时序网络快速更新兴趣点，官方口径就是冲着"惊喜感"去的）。

## 四、QQ 音乐精细化调控（DataFunTalk，工程深度最高，二面重点）

### 4.1 内容价值评估（长尾/新歌扶持的底层）
- 比率型指标（完播率/搜播率/收藏分享率）小样本不可信 → **贝叶斯平滑**（I 和 C 都小时评分趋近大盘均值）。
- 绝对热度指标头尾差异巨大 → **牛顿冷却定律**做指数衰减。
- 多指标归一化后线性加权 = 综合互动质量分。
- **实时方案**：多源数据流先分别聚合再 union（不 join），异步 IO+缓存，滚动窗口（短期）+ 滑动窗口（中期/长期）二次聚合刻画"实时飙升趋势"，双写 ES（线上）+ tdw（离线）。

### 4.2 潜力爆款挖掘（黑马斯歌）
- **PDM 模型**：把歌"拆解"成 演唱/歌词/旋律/节奏 四维度分别建模再综合；多用户群 × 多指标组合训练系列模型，多角度挖"好歌"。
- **种子用户投票**：圈定"眼光独到、先知先觉"的种子用户，用其搜索/播放/收藏行为经 **PageRank** 给歌曲潜力打分（无监督，避免正负样本悬殊）。
- **图嵌入**：node2vec / **EGES** 引入 作词-作曲-演唱者 异构图谱，解决交互稀疏歌的冷启动；MetaPDM = 音频/歌词 embedding + User-Embedding + SideInfo-Graph-Embedding 深度融合。

### 4.3 调控怎么落进推荐链路（三层干预，回答"运营怎么和算法共存"）
1. **召回层**：内容池服务（精选池/垂类池/冷启池），作为主召回的补充通路。
2. **排序层**：内容价值分作为特征或与模型分**线性加权**成最终排序分；支持线性策略 / 动态非线性策略 / **EE-UCB 模型**（播放量 < 阈值 N 时给 UCB 置信上界倾斜探索，稳定后按实际收益）。
3. **重排层**：精准投放系统强插（借鉴广告投放系统思路）。
- **实测收益**：准入歌曲数 +10%+；价值分做排序特征 → 人均时长 +10%、完播 +20%；音乐人内容播放占比 +47%。

### 4.4 架构要点
召回重构为 **DAG 算子化**（拉画像/向量召回/过滤/粗排/截断/归并都是节点，业务方配图即可上线新召回路径）；TME 自研 **Cube Studio**（Kubeflow 底座，内置 MIND/YoutubeNet/DIN/PLE）；Lambda 架构（Spark/Hive 批 + Flink 流），Flink 用户流水加秒级窗口聚合层降 TPS。

### 4.5 知识图谱
歌曲为点、专辑/歌手/音色等相同特征连线 → 相关性多角度计算，服务于个性电台/每日30首；本土化标签（国风/城市民谣/大众流行）。

## 五、序列建模与跳过率预测（学术+工业结合，展示深度）

### 5.1 MSSD 与跳过率预测
- **MSSD**（Spotify Music Streaming Sessions Dataset，WSDM Cup 2019 Skip Prediction Challenge）：1.6 亿收听 session、370 万 track 含音频特征，任务 = 预测用户会不会跳过 session 中的某首歌。这是音乐序列建模的标准数据集。
- 序列模型演进线：**Markov → GRU4Rec（2016，session-based 开山）→ SASRec（2018，自注意力）→ BERT4Rec（双向）→ 多兴趣（MIND）→ 因果建模（CSRec 2024）**。
- RecSys'24 实证：**SASRec 在音乐序列上稳定优于 BERT4Rec**（单向比双向更契合"下一首"决策）；引入**负反馈对比学习**（把 skip 作为负样本信号进 loss），HR/MAP 全面提升，且能可靠地把"历史上被 skip 的歌"降权。
- **Playlist Continuation**：歌单续写 = 用 Word2Vec（歌单当"句子"、歌当"词"，400 维）+ CNN 音频 embedding 初始化 SASRec/BERT4Rec 的 item embedding，**冷启动场景（无交互新歌）显著受益**——音频嵌入把内容侧信息带进序列模型。

### 5.2 音乐序列建模的特有处理
- session 内上一首的**完成度/跳过时机**作为特征进模型（不只是"播过"这个 0/1）。
- 探索行为要区分"用户主动搜来听的"vs"算法推的"（MSSD 论文指出：算法驱动 session 占比高时，模型可能学到的是老算法本身而非用户意图——**和你学过的"曝光数据复刻"是同一个坑**）。

## 六、多平台差异化（横向对比，展现视野）

| 平台 | 特色做法 |
|---|---|
| **Pandora** | Music Genome Project：音乐家**人工标注每首歌 450+ 维音乐属性**，基于标签做电台（人工基因 + thumbs up/down） |
| **Apple Music** | **人工编辑策展 + 算法**混合；Discovery Station 只推没听过的歌；Shazam 数据直接进编辑决策；Automix 无缝衔接 |
| **YouTube Music** | 跨生态信号（音频+视频观看行为）、800 亿信号规模、文本生成歌单、Samples 短视频竖滑发现新歌 |
| **网易云** | 歌单为底层架构（国内第一个）；**评论语义分析**判断偏好；深度时序网格实时建模求"惊喜感" |
| **QQ音乐** | 知识图谱 + 本土流派标签 + 精细化运营调控体系（上文第四节） |
| **Spotify** | BaRT bandits + 三支柱 + 完整场景产品矩阵 |

**共性结论**：没有一个"统一音乐推荐算法"，是**一栈式体系**——共享用户建模层，不同入口（首页/电台/歌单/每日推荐/相似歌曲）各有各的逻辑和目标函数。

## 七、多场景/多终端（万声业务的直接对位点）

万声 = B2B2C 承接 OPPO/vivo/小米**手机系统内置音乐 App**，触达全球十亿级终端、数亿用户，覆盖手机/AIoT/**车载 EVs**。二面必须能讲内置音乐场景的特殊性：

1. **场景碎片化**：手机（短 session、碎片时间）vs 车载（长 session、驾驶安全、BGM 型收听）vs 音箱（背景音）——同一用户在不同终端兴趣表达完全不同，**上下文特征（设备/时段/连接方式）权重极高**。
2. **冷启动更极端**：系统预装 App 首启即冷启动（无登录、无历史），且**换机迁移**是独有问题（新手机 + 老用户的云同步/厂商账号数据打通）。
3. **厂商数据合作**：终端厂商有系统级数据（应用使用/位置/场景），与音乐 App 数据融合是内置音乐相对独立音乐 App 的**独有优势**——你在 OPPO 做过应用商店推荐，这一点你可以讲得比面试官还深。
4. **非 App 入口**：锁屏/负一屏/语音助手点歌——推荐结果可能以"卡片/一句歌名"呈现，点击成本极低 → **曝光廉价、但跳过也廉价，样本噪音更大**。
5. **版权与结算**：B2B2C 模式下版权内容采购成本高，推荐要兼顾"用户体验"与"内容运营目标"（扶持新歌/音乐人）——QQ 音乐那套"精细化调控"就是为这个问题而生的，可直接映射。

## 九、答题模板

### 30 秒版（"讲讲音乐推荐和通用推荐的区别"）
> 音乐推荐有五个本质差异：一是信号不同，核心不是点击而是**切歌时机和完播**——Spotify 用 30 秒规则、QQ 音乐对切歌时机单独建模；二是负反馈权重极高，前 30 秒切歌是最重负信号；三是消费是 session 连续流，序列建模是主场；四是音频内容可建模，新歌冷启动靠音频 embedding 兜底；五是场景约束特殊——版权、艺人疲劳、车载/手机多终端上下文。我在 OPPO 做过系统级推荐，万声做的内置音乐正好是这两个方向的交点。

### 2 分钟版（"怎么给万声做音乐推荐"）
> 整体我会沿用召回-粗排-精排-重排框架，但按音乐特性改四处：**召回**上，行为向量（SASRec 类序列模型 + 空闲池化多兴趣）+ 音频内容向量（新歌冷启动兜底）+ 歌单 Word2Vec 三路并行，FAISS 检索；**排序**上，目标函数从 CTR 改成"完播/有效播放（30 秒）/收藏/加歌单"多目标，切歌时机作为连续特征而非 0/1，用 ESMM/PLE 建模；**重排**上加艺人打散、同流派疲劳度、以及运营扶持位（参考 QQ 音乐的 EE-UCB 探索机制：新歌播放量低时按置信上界倾斜探索，稳定后按实际收益）；**场景**上，手机/车载/音箱分别建模上下文，车载重 continuity 和长 session。冷启动上，系统预装没有用户历史，可以用厂商账号数据迁移 + 语言>歌手>流派的试探序（QQ 音乐实证）+ 音频相似度兜底。评估上除了离线 AUC，重点看人均播放时长、skip rate、次留和"惊喜感"类探索指标。

## 十、高频追问 & 易错点

**追问预演**：
1. "切歌怎么建模？" → 不是 0/1 标签，是时机连续变量 + 环境上下文；QQ 音乐 Logistic 综合歌手/流派/时机；Spotify 30 秒阈值分档（<30s 重负、30s-完播中性偏正、完播强正）。
2. "新歌没数据怎么推？" → 音频 embedding（MFCC/深度音频特征）+ NLP 元数据/歌词/乐评 + 歌手/流派图谱（EGES）+ 小流量 EE 探索（UCB）。
3. "怎么避免推荐越来越窄？" → 探索机制（epsilon/UCB）+ 惊喜感比例（Discover Weekly 30% 计划外）+ 多兴趣召回（MIND）覆盖用户多面性。
4. "多目标怎么排？" → 有效播放/时长为主目标，收藏/加歌单为中短期价值，skip 为显式负目标；防"全推熟悉歌"（时长指标天然偏好保守）要混入探索流量。

**易错点**：
- 别把音乐推荐说成"就是 CTR 排序"——完播/时长目标下，最优解往往不是"最像上一首"。
- 别忽略**重复消费**：音乐与电商不同，同一首歌会被反复听（复播率是忠诚度信号，不是去重对象）——"个性化电台"的本质是老歌 + 少量新探索，不是永远推新。
- 版权约束是硬性过滤层（下架/地区限制/会员限制），要在召回前置。

## 十一、字节系音乐推荐：抖音/汽水音乐/Resso（"以短带长"路线）

### 11.1 核心打法：把歌当短视频推（与所有传统音乐 App 根本不同）

- **推荐单元不是整首歌，是"黄金片段"**：15-60 秒副歌/高光片段进推荐流，抓耳优先——"前 3 秒决定划不划走"的短视频逻辑直接平移到音乐。
- **复用抖音推荐引擎**：双塔召回（用户/内容向量余弦匹配）+ RankMixer 排序（MoE 多专家，音乐风格/视觉场景各有专家）——就是你学过的抖音判别式 Scaling 那套架构。
- **短反馈闭环**：session 内实时反馈影响下一首（刷视频的实时性带进听歌），远快于 Spotify 的周更歌单节奏。

### 11.2 信号体系（短视频化的听歌）

| 信号 | 判定 |
|---|---|
| 听满 30 秒 | 正向兴趣 |
| **前 5 秒划走** | 负反馈，同风格降权 |
| 单曲循环 3 次+ | 强化歌手/风格标签 |
| <15 秒切歌 | 影响很小（短切噪音大，权重压低） |

冷启动：新号前 20 首是平台热曲，约 50 首后混入小众标签；首启只让选 3-5 个歌手/风格标签；约 14 天模型收敛。探索/利用比例约 15%/85%（第三方分析口径，非官方）。

### 11.3 双端联动与"以短带长"（字节独有的数据飞轮）

- 链路：抖音刷到 BGM → 点音符 →「用汽水音乐听完整版」→ 自动加入"我喜欢"。第三方分析称汽水约 82% 流量来自抖音生态、TOP1000 热歌 86% 源自抖音（二级来源，面试引用时说"据行业分析"）。
- **版本匹配技术**：抖音上的"副歌 15 秒版"自动关联完整母带，且支持**从副歌位置开始播放**——需要音频指纹对齐 UGC 短音频 ↔ 长音频，这是字节独有的工程资产。
- **版权回流**：抖音音乐人平台自动识别归档创作者上传音频，勾选授权后 <24 小时在汽水可播（传统唱片分发 2-6 周）→ 新歌冷启动速度碾压。
- **热歌引擎**：每条 BGM 有独立数据池（使用人数/收藏/完播/翻拍量），平台按音频聚合流量倾斜 → 神曲自然涌现，抖音成"神曲创造机"。

### 11.4 SAMI 音频理解中台（字节海外团队 ISMIR 2021 七篇，技术厚度担当）

| 能力 | 模型 | 用途 |
|---|---|---|
| 音乐标签化 | 半监督 Music Tagging Transformer（噪声学习+半监督，超 ResNet） | Resso/抖音/剪映的曲风/相似性推荐 |
| 时频理解 | SpectTNT（时频 Transformer + 残差） | 旋律提取/结构分析/音画匹配 |
| 语种识别 | 多模态（log-Mel + 50层 ResNet + 元数据） | Resso 多地区多语种留存（已证实有效） |
| 通用表征 | CLMR（对比学习，极少标注） | 标签/节奏提取的前置，降标注成本 |
| 结构分析 | 高光/循环片段检测（ICASSP'22 verse/chorusness 多任务） | 剪映智能延长、**推荐选"最抓耳段落"** |
| 音源分离 | 143 层 ResUNet（人声分离 8.98dB） | 人声/伴奏替换、物料制作 |
| 和弦识别 | NADE 自回归蒸馏 | AI 作曲前置 |

→ 关键洞察：**"推荐哪一段"和"推荐哪首歌"一样重要**——结构分析找到高光片段，这是字节推荐效果好的隐性功臣。

### 11.5 对万声的启示（二面谈资，重点）

1. **数据范式对比**（一句话讲清四种路线）：Spotify=协同过滤+音频、网易云=社区+歌单、字节=短视频跨域喂养、**万声=终端厂商生态数据**。万声没有短视频数据源，但有 OPPO/vivo/小米的**系统级终端数据**（应用使用/场景/设备）——跨域喂养的思路可复用，数据源换成终端生态。
2. **可借鉴的三件便宜事**：①黄金片段推荐（不需要重训模型，用高光检测把"从副歌开始播"做成产品体验）；②热歌引擎（按 BGM 使用量聚合的数据池，系统音乐 App 内"铃声/视频配乐"场景天然适用）；③短反馈闭环（session 内实时更新兴趣，比日级更新便宜且有效）。
3. **字节的教训**：茧房效应（用户连点两周"喜欢"，热歌占比从 40% 涨到 75%+）——纯行为流驱动、无社区/编辑内容制衡，探索不足；万声做内置音乐反而有"运营位+厂商诉求"的天然制衡，别只学算法不吸取教训。
