## 二、发现的主要问题

### ① Confluence 导出的 MIME + quoted-printable（最严重）

188 篇 / 1361 万字。文件是 Confluence 导出的邮件格式：

```
Subject: Exported From Confluence
Content-Type: multipart/related; boundary="----=_Part_19594_..."
Content-Transfer-Encoding: quoted-printable
<html ...><p>=E4=BA=91=E4=B8=8A=E9=87=8D=E6=8E=92...</p></html>
```

正文被 HTML 标签和 `=E4=B8=AD` 转义双重包裹，**等于完全没解析**。

虚胖验证：《云上重排无量模型开发.doc》标称 10.0 万字 → 解码后真实内容 **3741 字**，缩水 93%。

> 注：`kb_fix_confluence.py` 此前检测为 0，是因为文件路径在用户整理目录期间失效，脚本从未真正跑通过。

### ② 腾讯文档 JSON 未展开

90 篇。content 字段里塞着 JS 对象字面量，内层还有一层 JSON 字符串：

```js
{ content: [ { type: 'text', text: '{"content":"...\\n..."}' } ] }
```

导致《Constitutional AI 调研》《DeepSpeed-Chat 调研》《PPO 调研》等 LLM/RLHF 方向资料全部不可读。

### ③ 220 个文件压根没入库

主要是 `08_解码文本/` 下的 txt（178 个）和 `02_我的笔记/01_程序化广告/` 的 part01-17。
原因：`kb_ingest.py 运行 --限制 N` 按 rel_path 排序扫全库，总是先扫到已入库的文件，未入库的轮不上。

### ④ "网络请求失败"幽灵文档（16 篇）

当年抓取 Confluence 时网络失败，只存了个标题：

## 六、复用经验（下次别踩坑）

1. **入库 ≠ 解析**。统计"万字"没有意义，必须做内容结构审计（是否含 `Content-Transfer-Encoding`、`{"content"` 等标记）。
2. **中文占比判据要先压空白**。Confluence 导出文本塞满空行，直接算中文占比会误杀可救文档（我就是靠这个多救回 11 篇）。
3. **不要用 `unicode_escape` 解 JSON 转义**，会把 UTF-8 中文打成 latin-1 乱码（`è°ç妍`）。必须用 `json.loads`。
4. **动数据库前先备份**。本次备份 350MB，修复出错可回滚。
5. **"检索 0 次"的结论不可靠，先确认文档有没有被正确解析**。本轮最大教训：MMoE 在"82 篇原文检索 0 次"的结论来自编码垃圾时代；解码+OCR 后铁证如山（技术攻坚奖 + 答辩 PPT），直接推翻面试口径。**做任何"原文无据"判断前，必须先跑一遍质量审计**。
6. **大 PPT 别先入为主判"图片容器"**：50MB PPT 只有 83B 是提取器 bug；XML 直提（`<a:t>` 标签 + notesSlides 备注）能拿到 195~481 字，media 大的才需 OCR。分层处理：XML 直提 → 快提文字层 → 图片 OCR。
7. **macOS 原生 Vision OCR 中文效果好**，装 `pyobjc-framework-Vision pyobjc-framework-Quartz` 即可用；比 tesseract 中文包强（本机 tesseract 无中文包）。
