# 专题 11 · 生成式推荐与语义 ID（2026-09-16）

> 对方痛点：JD「生成式大模型技术模块」「关注业界前沿大模型推荐进展」；基础模型线整体。C 档（个人项目无 RQ-VAE），但 JD 明写生成式大模型——**必须按深读口径准备**。

## 一、技术谱系（2023-2025，讲得出脉络=前沿跟进合格）

**LLM4Rec 三阶段**（→ 推荐的 LLM 化探索）：
1. LLM Embeddings + RS（LLM 当特征抽取器，离线预生成）
2. LLM Tokens + RS（LLM 产 token/标签进召回或特征）
3. LLM as RS（LLM 直接生成推荐——尚未生产可用）

**生成式推荐三路线**（与专题 08 呼应）：
| 代表 | 阶段 | 核心 |
|---|---|---|
| **Google TIGER**（2023.5） | 召回 | **语义 ID（RQ-VAE 离散化 item）** + T5 自回归生成候选——开山之作 |
| **Meta GR**（2024.2） | 精排 | HSTU 架构，万亿参数验证推荐 Scaling Law，M-FALCON 推理 |
| **百度 COBRA / 字节 HLLM·RankMixer** | 混合 | 稀疏 embedding 与生成式结合 |
| **快手 OneRec**（2025.6） | 端到端 | Encoder-Decoder + MoE + DPO/奖励模型，召排一体直接生成列表 |
| **美团 MTGR**（2025.5） | 精排 | 混合式：保留交叉特征 + HSTU（见专题 08） |

**语义 ID 关键技术点**（被深挖时）：
- RQ-VAE：item 表征 → 残差量化 → 多层 codebook → 语义 ID 元组；层级 = 粗到细。
- **RQ-VAE vs RQ-KMeans 选型**：码本碰撞率高（相似 item 挤同一码字）时 RQ-KMeans 更稳；碰撞会让生成式检索候选塌缩。
- 碰撞处理：同码字 item 按流行度区分；codebook 尺寸与层数是核心超参。

## 二、我的嫁接（C 档 → B 档话术）

- **诚实底座**：个人项目是 LLM 评估/重排/agent 路线，没有 RQ-VAE——**不冒领**。
- **试验田话术**：「我的个人项目就是现成的试验田——多源内容有干净的 item 表征输入，若做语义 ID，第一步是 item 侧离散化（RQ-VAE 先试，碰撞率高换 RQ-KMeans），做生成式召回与现有 embedding 召回的对齐实验，看语义 ID 的泛化收益（长尾 item）vs 精度损失。」
- **腾讯经历衔接**：多品类统一排序时评估过语义离散化方向（MMoE-Group/Special/Skill 分组门控 = 同期多目标架构演进探索），说明架构演进敏感度。

## 三、面试三段答法

1. 「谱系我全跟过」：TIGER→Meta GR→OneRec→MTGR 的演进逻辑（先召回后精排再端到端）。
2. 「语义 ID 的本质」：把 item 空间从「记忆问题」变成「生成问题」——ID 碰撞与泛化是 trade-off 核心。
3. 「若由我落地」：试验田第一步（上面话术）+ 先离线对齐实验再谈上线。

## 四、追问防御

- 「OneRec 为什么能端到端？」→ Encoder-Decoder + 生成候选直接过精排目标训练 + RL 对齐业务指标；但丢交叉特征的业务代价要会算（MTGR 的教训）。
- 「语义 ID 在广告场景（非推荐）有什么不同？」→ 广告 item=广告主/计划，语义结构弱于内容 item，先验更依赖行为共现——这是个能展示思考的开放点。
- **金句**：「生成式推荐把『从一亿个候选里选』变成『直接说出答案』——前提是答案的词表（语义 ID）先学会说话。」
