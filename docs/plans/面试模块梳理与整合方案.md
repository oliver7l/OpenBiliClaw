## 一、一句话诊断

**「面试模块」其实不是"一个模块有点乱"，而是三个互不相关的子系统共用了同一个名字和同一段 URL 命名空间，各自的数据又散在 2 个 DB 里、文件层还叠着归档与重复目录。**

三套子系统：

| # | 子系统 | 干什么 | 代码位置 | 数据位置 | 前端入口 | 文档 |
|---|--------|--------|----------|----------|----------|------|
| **A** | **岗位备战**（job-prep） | 读求职知识库：岗位/检索/数字/项目/速记卡/日志/建档 | `interview/{engine,routes,cli}.py` | `求职知识库/` 文件 + `knowledge.db` + `interview.db` 裸表(question/concept/number/project/log) | 桌面「✅待办」+ **移动端整个面试页** + CLI | `docs/modules/interview.md` |
| **B** | **题目研习**（study） | 题库/队列/阅读计划/掌握度/统计/反问话术/弹药阅读 | `api/_interview_routes.py`(817行) + `interview/questions/` | `interview_questions.db`(iq_*) + 读 `03_岗位弹药库/` 文件 + `interview.db`(ammo_*/rebuttals) | 桌面 8/10 个子标签 | `docs/interview-reading-tracker.md` |
| **C** | **面试复盘**（review） | 复盘记录/搜索/统计 | `interview/review_{routes,service,store,models}.py` | `interview.db`(interview_reviews 3行) | 桌面「📝复盘」 | 无独立文档 |

三者的 **API 全部挂在 `/api/interview`** 下（A、B 甚至用了同一个 `APIRouter(prefix="/api/interview")`），
路径恰好不撞车所以"能跑"，但从 URL 上完全分不出谁是谁。

## 二、问题清单（按严重度）

### P1 ★★★ 题目数据有三套表示，分散在 2 个 DB，互不相通

| 表 | 位置 | 行数 | schema 关键字段 | 谁在用 |
|---|---|---|---|---|
| `question` | `interview.db` | 25 | `topic, direction, company, answer_loc`（**文件指针**） | A 的 `/card` `/topics` 速记卡 |
| `interview_questions` | `interview.db` | 199 + FTS | `company, position, category, question, answer, want_to_hear, source_path` | **无人消费**（导入后无读取方） |
| `iq_questions` | `interview_questions.db` | 51 | `title, answer, category, difficulty, source, tags`（**无 company**） | B 的今日待读/队列/全部题目/统计 |

三张表都叫"面试题"，字段各不同，数据不重叠（25 条指针 / 199 条岗位题库 / 51 条淘天题）。
**从知识库 md 解析出的 199 条题，前端根本看不到。**

### P2 ★★★ 两个"面试题导入脚本"同名不同库

| 脚本 | 读 | 写 |
|---|---|---|
| `src/openbiliclaw/interview/questions/import_questions.py` | 硬编码 15+ 题（淘天生成式推荐） | `data/interview_questions.db` → `iq_questions` |
| `scripts/import_interview_questions.py` | `03_岗位弹药库/**/*.md` | `data/interview.db` → `interview_questions` |

名字几乎一样、用途相反、目标库不同 —— 极易误用。且第二个脚本产出的数据**没有消费方**（见 P1）。

### P3 ★★ `interview.db` 表命名三种风格并存

- 裸名（早期知识库表）：`question` / `concept` / `number` / `project` / `todo` / `log`
- 前缀名：`interview_questions` / `interview_scripts` / `interview_reviews` / `interview_rebuttals` / `interview_recordings`
- ammo 系：`ammo_doc` / `ammo_fts` / `ammo_reading`

其中 `question`(25，指针表) 与 `interview_questions`(199，题干表) **名字撞车概念**，最容易误读。

### P4 ★★ 代码分层不一致

- A 的路由在包内 `interview/routes.py` ✅
- C 的路由在包内 `interview/review_routes.py` ✅
- **B 的路由却在包外 `api/_interview_routes.py`（817 行，全项目最大端点文件之一）**，
  而它的 store 却留在 `interview/questions/` —— 同一子系统的路由与数据层被拆到两个顶层目录。

`interview/` 包内也因此混装三套东西：`engine/routes/cli`(A) + `questions/`(B) + `review_*`(C)。

### P5 ★★ 03_岗位弹药库文件层乱

- **归档目录还在原地**：`字节面试_2026-09-03_已合并归档_2026-09-09/`（16 个文件）内容已并入
  `字节面试-2026-09-03-今日头条数据科学/05_合并自旧目录_2026-09-03/`，属冗余残留。
- **两个索引文件并存**：`README.md`（更新于 2026-09-04，只列 6 个岗位）与
  `00_岗位弹药库总索引.md`（内容同源）。README 已严重过期（现有 9 个 `-面试准备` 目录）。
- **目录编号不统一**：多数为 `01/02/03`，但大宇无限多 `04_广告知识库/`、
  比亚迪多 `05_入职资料/`、GoodLuckStudio 多 `05_面试记录/`、万联易达多 `03_面试复盘/`。
- **散落文件**：`万联易达-面试准备/产联社-产品体验与思考-面试速用.md` 游离在编号子目录之外。
- **空壳目录**：`腾讯-推荐算法-2026秋招/01_岗位与公司信息/`（0 文件），且无 `-面试准备` 后缀 → 前端不可见。
- **13 个根级文件平铺**：清单类（Boss/百度/华为/智联/未覆盖/明日投递/打招呼话术/新增可投岗位）
  与索引类（README/00_总索引）与 `投递作战台.html` 混在一起。

### P6 ★ 前端单页 10 个子标签混两域

桌面端 `#interviewSubtabbar`：备战(待办/公司岗位/弹药库) + 研习(今日待读/待看队列/全部题目/学习统计/反问话术)
+ 复盘(复盘) 无分组地排成一条。

### P7 ★ 文档双份且互相不知道对方

`docs/modules/interview.md` 只描述 A，`docs/interview-reading-tracker.md` 只描述 B，
**没有任何一处说明"面试模块 = A+B+C"**。

### P8 ☆ 零星

- `ammo_reading` 仅 1 行（万声科技 1 条），表在 `iterview.db` 而 A 的弹药读取又是文件直读，职责重叠。
- 移动端 `web/js/views/interview.js` 只实现了 A，与桌面端能力不对齐（这一条是设计取舍，可保留）。

## 三、目标架构

### 3.1 命名分区（URL 上一眼可辨）

```
/api/interview/job/*       ← A 岗位备战（原 /api/interview/{status,jobs,search,...,todos,...}）
/api/interview/study/*     ← B 题目研习（原 /api/interview/{today,queue,questions,stats,...}）
/api/interview/review/*    ← C 面试复盘（原 /api/interview/reviews/*）
```

**向后兼容（✅ 已实现为「双挂载别名」而非 307 重定向）**：三份 router 本体**不带 prefix**，
注册时把同一份 router `include_router` **挂两次**——新前缀进 OpenAPI，旧前缀
`include_in_schema=False`。重定向方案被否决：307 虽保方法但不保 body，POST/PUT 会踩坑；
双挂载零 handler 复制、POST 全兼容、摘除只需删 3 行。前端切换完成后即可摘除旧前缀。

### 3.2 数据层归一

> ⚠️ **前置约束（尊重既有决策）**：`docs/changelog.md` 记录三层架构重构期 1 已把
> `interview_questions.db`（`iq_*`）定性为**「活跃刷题系统，不合并」**（iq 双轨定性）。
> 因此本方案**不合并该库**，只处理下面第 2 条的"孤儿表"。

1. **保留双轨**：`interview_questions.db`（B 的活跃刷题库：`iq_questions`/`iq_queue`/`iq_records`/`iq_plans`/`iq_daily`）**维持现状**。
2. **处置孤儿表**：`interview.db.interview_questions`（199 行，从 `03` 题库 md 解析）目前**没有任何消费方**。
   两条路二选一：
   - (a) **接线**：让 B 的「全部题目」页把它作为第二个题库源展示（有价值，199 条岗位真题不再沉没）；
   - (b) **退役**：确认无用后删除该表 + FTS，并把 `scripts/import_interview_questions.py` 一并归档。
   → ✅ **已按 (a) 落地（期 1）**：新增 `GET /api/interview/kb-questions`（支持 company/category/q 筛选），
   桌面「全部题目」页加「📖 追踪题库 / 📚 岗位题库」双源切换，199 条岗位真题只读可见。
3. **去歧义**：`interview.db` 内裸表 `question`(25) / `concept` / `number` / `project` / `todo` / `log`
   与 `interview_questions`(199) 概念撞车——✅ 已在 `docs/modules/interview-overview.md` 中逐表标注归属为
   A 的「知识库只读表族」。
4. **消重名脚本**：✅ 已完成，`interview/questions/import_questions.py` → `seed_iq_questions.py`
   （并在两处文档与 pyproject 同步引用）。
5. **顺带修**：`scripts/kb_sync_ammo.py` 的 `derive_company_kind` 对**根级文件**取

### 期 2 为何曾缓做 → 后来为何重启（2026-09-14）

> **状态：已被推翻。** 用户于同日决定重启期 2 并已完成（见上「期 2 · API 分区 ✅」）。
> 下面保留当时的评估，用于说明成本最终是怎么被化解的——关键就是兼容策略从
> **307 重定向**换成**双挂载别名**：重定向方案的「永久 legacy 路由层」成本仍在，但
> 双挂载只是 3 行 `include_router`，不复制 handler、不破坏 POST，成本几乎归零。

期 2 是唯一改动 **URL 契约**的一期，当时的评估：

- **收益**：仅「URL 上能一眼看出属于哪个子系统」——本项目的 API 消费者只有自家桌面端/移动端，
  没有第三方按 URL 集成的场景。
- **代价**：
  1. 64 条端点要换前缀（A 的 `/jobs` 会变成 `/api/interview/job/jobs`，语义反而更差）；
  2. 为不破坏旧调用，需保留一层 legacy 兼容路由；
  3. 要同步改桌面端（`API_BASE` 常量拆成三个）+ 主 SPA（`web/js/api.js` 22 处）+ 全部测试路径断言；
  4. 移动端无法在本机端到端验证，回归风险最高。
- **重启时的实际化解**：第 1 条叠词被接受（仅 `/job/jobs` 一处）；第 2 条改用双挂载
  （成本 3 行、无重定向语义坑）；第 3 条实测**调用面远小于预估**——`web/js/views/interview.js`
  走 `api.js` 封装零改动，桌面端只有 1 个常量 + 6 处硬编码，仓库内**没有独立移动端客户端**；
  第 4 条随之消失（双挂载保证旧前缀字节级等价，无需端到端验证移动端）。
